Design a Document Extraction Pipeline

A pipeline that ingests uploaded documents (payslips, IDs, bank statements, invoices), extracts structured fields with vision LLMs, flags inconsistencies across documents, and routes uncertain cases to human reviewers. Based on the reported prompt "process 10K monthly uploads and flag inconsistencies."

Understanding the Problem

A lender, a rental platform or an HR onboarding product asks applicants to upload proof: an ID, three recent payslips, a bank statement. Today staff read each one and type numbers into a form. The product wants this automated: extract the fields, check that the documents agree with each other and with what the applicant declared, and only send a person the cases that actually need judgment.

This is the most common "LLMs in the enterprise" shape, and a favorite with founding-engineer and solutions-engineer interviews because it tests whether you know where the model ends and deterministic code begins. The LLM reads messy documents; code validates, reconciles and decides. The interesting problems are trust (when can we skip the human?), reliability (no document lost, no double processing, provider outages), compliance (these are some of the most sensitive documents people own) and cost per document.

Functional Requirements

  1. Users should be able to upload documents (PDFs and photos) attached to a case, such as a loan application.
  2. The system should classify each document and extract a typed set of fields per document type (for a payslip: employer, employee name, pay period, gross pay, deductions, net pay).
  3. The system should flag inconsistencies within a document (net ≠ gross − deductions), across documents (name on payslip ≠ name on ID), and against declared data (declared income vs payslips).
  4. Reviewers should be able to see flagged cases with the source image and highlighted fields, correct values, and approve or reject.
  5. Client systems should be able to get results through an API and webhooks.

Below the line: forgery and image-tampering detection as a full product (we'll mention signals), credit decisioning, training custom OCR models.

Non-Functional Requirements

  1. Scale: 10K documents/month today, designed for 1M/month (≈ 0.4 docs/s average, ~2 docs/s at peak).
  2. Latency: results within a few minutes (p95 < 5 min) for applicants waiting in a flow; overnight is fine for backfills.
  3. Accuracy: auto-accepted fields must be right ≥ 99% of the time (precision matters more than coverage); inconsistency flags should have high recall, since a missed mismatch costs more than a false alarm.
  4. Durability: no uploaded document is lost, and each is processed exactly once in effect (no duplicate results or double-billed reviews).
  5. Security and compliance: encryption, least-privilege access, audit trails, retention limits, data residency, deletion on request.

10K documents a month is about 14 per hour. Say so: "At this volume a single worker could do it; I'll design for 100× because the hard parts here are correctness, trust and compliance, not throughput." Interviewers reward candidates who don't over-scale small numbers and who spend their time where the risk is.

The Set Up

Core Entities

  • Case: the unit of decision (an application), with declared data (name, income, address) and status.
  • Document: blob key, content hash, MIME type, page count, detected type, processing state.
  • Extraction: per document, versioned: field values, per-field confidence, source location (page, bounding box or quoted text), model and prompt version.
  • Finding: a rule result: rule ID, severity, documents and fields involved, explanation.
  • Review task: assigned reviewer, decisions, corrections (which become labels), timestamps.

API

POST /cases                         { declared: {...} }                 → { caseId }
POST /cases/{id}/documents          { filename, contentType, sha256 }   → { documentId, uploadUrl }  // presigned PUT, ~5 min TTL
POST /documents/{id}/complete                                           → 202  // client confirms upload; enqueues processing
GET  /cases/{id}                    → { status, documents[], extractions[], findings[] }
POST /webhooks                      { url, events: ["case.completed", "case.needs_review"] }

// Reviewer tool
GET  /review/tasks?queue=…          → next task (leased for 15 min)
POST /review/tasks/{id}/decision    { corrections: {...}, outcome: "approve" | "reject" | "request_reupload" }

Extraction schema, per document type

Payslip {
  employer_name: string, employee_name: string,
  pay_period_start: date, pay_period_end: date, pay_date: date,
  gross_pay: Money, total_deductions: Money, net_pay: Money,
  currency: ISO4217,
  _evidence: { field → { page, quote } }      // where each value came from
}

Schema-constrained output (structured outputs / JSON mode with a schema) guarantees the result parses (barring refusals or truncation at the token limit). It doesn't guarantee the values are right, which is what the rest of the design is about.

High-Level Design

1) Users can upload documents

The client asks the Upload API for a presigned URL and uploads the file directly to an encrypted blob store, so large files never pass through our servers. The API records the document in the Jobs DB with its SHA-256 hash; a duplicate hash on the same case returns the existing document instead of creating a new one (idempotent uploads). When the client confirms, the API enqueues a processing message. Before anything else, a scanner checks file type and malware, and normalizes inputs: PDFs split into pages, photos de-skewed and resized to a sensible resolution.

2) The system classifies and extracts fields

Extraction workers pull from the queue and run each document through a small state machine, recording progress in the Jobs DB so a crash resumes at the last completed step:

  1. Classify and split. A cheap, fast model (or a small vision classifier) labels each page: payslip, passport, driver's license, bank statement, invoice, other. Multi-document PDFs (three payslips scanned together) are split by page ranges. Unknown types go straight to review.
  2. Extract. A vision-capable LLM gets the page images, the OCR text if available, and the schema for that type, and returns structured JSON with an evidence quote per field. Calls go through a Model Gateway that handles retries, fallbacks and budgets.
  3. Normalize. Deterministic code parses dates and money into canonical forms, normalizes names (case, diacritics, ordering), and maps currencies.

3) The system flags inconsistencies

Validation is code, not a prompt. Three layers of rules run over the normalized extractions:

LayerExamplesHow
FieldDate is valid; amount positive; ID number format; passport MRZ check digitsSchema types, regexes, checksum algorithms (MRZ check digits are defined in ICAO Doc 9303)
Documentgross − deductions = net (± rounding); pay period ends before pay date; ID not expiredArithmetic and date logic with tolerances
Case (cross-document)Same person on ID and payslips; consistent employer across payslips; payslip net pay appears as a deposit on the bank statement; declared income within X% of payslip-derived income; payslips are the 3 most recent monthsEntity matching plus a rules engine over the case's facts

Each failed rule creates a Finding with an explanation that cites the documents and fields. An LLM can turn findings into a readable summary for reviewers, but the decision that a mismatch exists comes from code you can test.

4) Reviewers resolve flagged cases

Cases with findings or low-confidence fields go to a review queue. The review tool shows each field next to the highlighted region of the source image, pre-filled with the extracted value. Reviewers correct and approve. Tasks are leased (so two reviewers don't work the same case) and every action is written to an audit log. Corrections are stored as labels, which feed evaluation and threshold tuning.

5) Clients get results

When a case reaches a terminal state, results and findings are written to the results store and a webhook fires (signed, retried with backoff, idempotent by event ID). Clients can also poll GET /cases/{id}.

Potential Deep Dives

1) OCR, vision LLM, or both?

Bad Solution
OCR plus regexes and templates per layout

Challenges: payslips come in thousands of layouts from different payroll providers; templates break on every new one, and photos taken at an angle wreck positional rules. Maintenance never ends.

Good Solution
OCR text into a text LLM with a schema

Approach: run OCR, give the text to an LLM with the target schema, get JSON back.

Challenges: OCR flattens tables and loses layout, so the model confuses year-to-date totals with this period's amounts, or columns with rows. Handwriting and stamps are lost.

Great Solution
Vision LLM with layout-aware OCR as a second signal, specialized parsers where they exist

Approach: send page images to a vision LLM with the schema, plus OCR text (with coordinates) as an extra input. Require an evidence quote per field and check that it appears in the OCR text; a value with no supporting text is suspect. For highly structured parts, use deterministic parsers: the MRZ on passports and many IDs encodes name, number, birth date and expiry with check digits, so parse it and compare to what the model read from the visual zone. For the few highest-volume layouts, a cached prompt with examples of that layout improves accuracy cheaply.

Challenges: images are token-heavy (on Claude, one token per 28×28-pixel patch, so a 1000×1400 page is ~1,800 tokens on current models; see vision docs); downscale to the smallest resolution that preserves accuracy on your eval set, and keep OCR costs in the budget.

2) How do we know when to trust an extraction without a human?

This is the core of the design: the auto-accept rate drives cost, and auto-accept precision drives risk.

Bad Solution
Ask the model to rate its own confidence

Challenges: self-reported confidence from an LLM is poorly calibrated; it says 0.95 for wrong answers often enough that you can't set a threshold on it.

Good Solution
Deterministic validators as the gate

Approach: auto-accept when every field passes type, checksum and arithmetic rules and no cross-document rule fires.

Challenges: many fields have no checksum (employer name, pay period). A plausible but wrong value sails through.

Great Solution
Combine independent signals into per-field confidence, calibrated on labeled data

Approach: for each field, collect signals: validator pass/fail, evidence quote found in OCR text, agreement between two independent extractions for critical fields (two models, or vision vs OCR+text), token log-probabilities where the provider exposes them, and document quality (blur, crop). Fit a simple calibrated model on reviewer-labeled data that maps signals to the probability the field is correct. Pick a threshold per field and document type that meets the precision target (≥ 99%) on a held-out set, and route everything below it to review. Track auto-accept rate and post-hoc error rate (via audited samples of auto-accepted cases) weekly.

Challenges: dual extraction doubles model cost; apply it only to fields that drive decisions (income, name, ID number). Thresholds must be re-tuned after any model or prompt change, which the eval gate enforces.

3) How do we check consistency across documents?

  • Entity matching: names differ legitimately (middle names, initials, transliteration, maiden names). Normalize, then use token-based fuzzy matching with thresholds; treat "J. Smith" vs "John Smith" as a soft match, "John Smith" vs "Jane Doe" as a hard mismatch. Escalate soft matches only when other evidence is weak.
  • Income reconciliation: annualize per pay frequency (weekly, biweekly, monthly) before comparing; match payslip net pay to bank deposits within a date window and an amount tolerance.
  • Completeness and recency: "three consecutive recent payslips" is a rule over pay periods, not something to ask a model.
  • Fraud signals: PDF metadata (editing software, creation after the pay date), font inconsistencies, arithmetic that's off by suspiciously round amounts, duplicates of documents seen in other cases (perceptual image hashes). These are separate detectors that raise findings; an LLM is not a reliable forgery detector.

Don't let the LLM decide "consistent: yes/no" across a whole case in one prompt. It's untestable, it can't explain itself reproducibly, and regulators and auditors will ask why a case was flagged. Extract facts with the model; decide with versioned rules.

4) How do we make processing reliable?

Bad Solution
Process synchronously inside the upload request

Challenges: model calls take seconds to tens of seconds and sometimes fail; a timeout loses work, and retries from the client duplicate it.

Good Solution
Queue with retries and a dead-letter queue

Approach: at-least-once delivery, exponential backoff on transient errors, a dead-letter queue after N attempts with alerting.

Challenges: at-least-once means duplicates: two workers may extract the same document and write two results or create two review tasks.

Great Solution
Idempotent state machine plus a gateway that absorbs provider outages

Approach: each document has a state (uploaded → classified → extracted → validated → done | needs_review) with conditional updates (compare-and-set on the version), so a duplicate message finds the step done and exits. Writes are keyed by (documentId, step, pipelineVersion). The Model Gateway retries with jitter, opens a circuit breaker on a failing provider, and falls back to a second model that has passed the same extraction evals. Because the latency SLO is minutes, the queue itself is the outage buffer: during a long outage, work waits and drains later instead of failing. Backfills and re-extraction after a prompt change go through providers' batch APIs, which are typically discounted around 50% (Claude batch processing).

Challenges: fallback models extract slightly differently; record the model version on every extraction and use per-model thresholds.

5) How do we protect the data?

  • Storage: encrypt blobs and extracted fields at rest with KMS-managed keys (per-tenant keys for enterprise customers); presigned URLs with short TTLs; buckets never public.
  • Least privilege: workers can read only documents they're processing; reviewers see only cases assigned to them, with the review UI showing only the fields they need. Every view and export is audit-logged.
  • Logs and traces: never log raw field values or images; log document IDs and hashes. Redact PII in traces used for debugging.
  • Model providers: use enterprise terms with no training on your data and zero or limited retention where available (check feature eligibility: Claude's Batch API, for example, keeps results for 29 days and isn't covered by zero data retention, so keep ZDR-only documents out of batch backfills); pin the processing region for data residency (EU documents processed in the EU).
  • Retention and deletion: keep source documents only as long as the business and regulators require, then delete blobs, extractions and derived labels; support deletion requests (for example under GDPR) across all stores, including eval sets built from production data.

6) How do we evaluate and improve accuracy?

  • Golden set: a few hundred labeled documents per type, stratified by layout, image quality (scans, phone photos, glare) and language, including deliberately inconsistent cases.
  • Metrics: field-level accuracy after normalization (exact match for IDs, tolerance for money, normalized match for names), document-level "all critical fields correct", finding recall and precision, auto-accept rate and auto-accept precision, review rate, cost and latency per document.
  • Gates: any prompt, model or pipeline change runs the golden set and can't regress auto-accept precision or finding recall (see Evaluation).
  • Flywheel: every reviewer correction is a new label. Sample auto-accepted cases for audit too, or you'll never learn about confident mistakes.

7) What does it cost, and how does it scale to 1M documents a month?

// Model cost per document (Sonnet 5.5 list prices: $2 / M input, $10 / M output; check current pricing)
classify:   1 page thumbnail on a small model                     ≈ $0.001
extract:    2 pages × ~1,800 image tokens + ~1,000 prompt/OCR tokens ≈ 4,600 in × $2/M  = $0.0092
            ~400 output tokens × $10/M                                              = $0.0040
dual extraction on critical fields (~30% of docs)                              ≈ $0.004
retries and fallbacks (~10%)                                                   ≈ $0.002
                                                                     total ≈ $0.02 / doc

// Human review cost
review rate 15% × 2 min per review × $30/hour                                  ≈ $0.15 / doc

Review dominates model cost by about 7×. The most valuable optimization is raising the trustworthy auto-accept rate, not shaving tokens. That's the insight to say out loud.

1M docs / month ÷ 2.6M s ≈ 0.39 docs/s average; peak ~5× ≈ 2 docs/s
in-flight model calls (Little's law): 2 docs/s × ~2 calls × ~8 s ≈ 32 concurrent
token rate: 2 docs/s × ~5K tokens ≈ 10K tokens/s ≈ 600K tokens/min   // check provider rate-limit tier; split across providers
storage: 1M docs × ~1 MB ≈ 1 TB / month → lifecycle to cold storage, delete at retention

Workers autoscale on queue depth; interactive cases go on a higher-priority queue than backfills, so a bulk re-extraction never delays an applicant. Review staffing is the real scaling constraint: at a 15% review rate, 1M documents is 150K reviews a month, about 5,000 reviewer-hours, which is why every point of auto-accept rate is worth engineering effort.

What is Expected at Each Level?

Mid-level

Presigned uploads, a queue and workers, an LLM extracting to a JSON schema, basic validation, a review queue, and webhooks. Notices that LLM output must be validated.

Senior

Clear split between model extraction and rule-based decisions; vision plus OCR with evidence; calibrated per-field confidence and thresholds tied to a precision target; idempotent state machine, DLQ, provider fallback; PII handling; field-level evals and a correction flywheel; cost math showing review dominates.

Staff+

Frames auto-accept rate at a fixed precision as the business metric and designs the system around moving it safely; audit sampling of auto-accepted cases, per-model thresholds and gated rollouts, data residency and deletion across eval sets, review workforce capacity planning, and fraud detection as a separate signal pipeline.

LLM System Design · Core Concepts

Inference & Serving

How a model turns a prompt into tokens on real hardware, why memory bandwidth rather than compute usually sets the limit, and the serving techniques (batching, paging, speculation, quantization, parallelism, disaggregation) that decide cost and latency.

Almost every LLM design question eventually becomes a serving question. "How many users can one server handle?", "Why does the first token take two seconds when someone pastes a long document?", "How would you halve the cost?" all have answers that come from a handful of mechanisms inside the inference engine. You don't need to write CUDA kernels to answer them, but you do need to reason from first principles: bytes moved, FLOPs done, and memory held.

This page goes deeper than the Fast Track overview. It's essential for infrastructure-flavored interviews (the inference batching prompt reported at AI labs, "design a high-concurrency inference API") and useful in product interviews whenever you decide between a hosted API and self-hosting.

The forward pass in one picture

A decoder-only transformer turns a sequence of token IDs into a probability distribution over the next token. The engineer's view:

  1. Tokenize and embed. Text becomes token IDs; each ID looks up a vector of size d_model (8,192 for a 70B Llama-class model).
  2. N transformer blocks (80 for Llama 3 70B). Each has an attention layer, where every token looks at all previous tokens through their keys (K) and values (V), and an MLP layer, which holds most of the parameters. Nearly all compute is matrix multiplication against weights.
  3. LM head and sampler. The last hidden state is projected to vocabulary logits; temperature, top-p and any grammar constraints pick one token.
  4. Repeat. The new token is appended and the model runs again. Each pass produces exactly one token per sequence (speculative decoding, below, bends this rule).

Two rules of thumb do most of the work in interviews:

FLOPs per token  ≈ 2 × parameters             // one multiply + one add per weight
bytes per decode step ≈ weight bytes + KV bytes of every sequence in the batch

For mixture-of-experts (MoE) models, use active parameters for FLOPs (a token only visits a few experts) but total parameters for memory (all experts must be resident). DeepSeek-V3 has 671B total and 37B active parameters per token (DeepSeek-V3 Technical Report), which is why MoE models are cheap to compute but expensive to hold.

Prefill vs decode: two different workloads

Arithmetic intensity and the roofline

Every GPU has a compute ceiling (FLOP/s) and a memory ceiling (bytes/s from HBM). The arithmetic intensity of a workload is FLOPs done per byte read. Below the GPU's "ridge point" you're memory-bound; above it you're compute-bound.

ridge point = peak FLOP/s ÷ memory bandwidth

H100 SXM, BF16 dense:  989 TFLOP/s ÷ 3.35 TB/s ≈ 295 FLOPs per byte
H200 SXM, BF16 dense:  989 TFLOP/s ÷ 4.8 TB/s  ≈ 206 FLOPs per byte
B200,     BF16 dense: ~2,250 TFLOP/s ÷ 8 TB/s  ≈ 281 FLOPs per byte

Now compare the two phases for a model with FP16 weights (2 bytes per parameter):

  • Prefill pushes all T prompt tokens through each weight matrix at once. FLOPs ≈ 2 × params × T; bytes ≈ 2 × params. Intensity ≈ T. A 2,000-token prompt sits far above the ridge: compute-bound.
  • Decode pushes one token per sequence. With a batch of B sequences, intensity ≈ B (ignoring KV reads, which make it worse). At B = 1 the GPU does 1 FLOP per byte while it could do ~295: memory-bound, with tensor cores more than 99% idle.

This single fact explains why batching is the biggest lever on cost: a decode step reads all the weights once whether it serves 1 sequence or 64, so extra sequences ride almost free until either KV reads or compute catch up.

The decode speed ceiling

Because decode is memory-bound, the fastest a single stream can go is roughly bandwidth divided by the bytes read per step:

max tokens/s per stream (batch 1) ≈ aggregate HBM bandwidth ÷ weight bytes

Llama 3 70B, FP16 (≈140 GB), tensor-parallel over 8 GPUs:
  8 × H100 (26.8 TB/s)  → 5.2 ms/step → ≤ ~190 tok/s
  8 × H200 (38.4 TB/s)  → 3.6 ms/step → ≤ ~270 tok/s
  8 × B200 (64 TB/s)    → 2.2 ms/step → ≤ ~460 tok/s
  8 × H100, FP8 weights (70 GB) → 2.6 ms/step → ≤ ~380 tok/s

Real engines reach perhaps 60–80% of this bound because of kernel efficiency and the all-reduce communication that tensor parallelism adds every layer. The bound is still the right first estimate, and it tells you that quantizing weights speeds up low-batch decode almost linearly.

With a batch, the KV cache joins the bytes read each step:

step time ≈ (weight bytes + Σ over batch of context_len × KV bytes/token) ÷ bandwidth

8 × H100, Llama 3 70B FP16, batch 64, 2K-token contexts:
  KV read = 64 × 2,048 × 320 KB ≈ 42 GB
  step ≈ (140 + 42) GB ÷ 26.8 TB/s ≈ 6.8 ms
  aggregate ≈ 64 ÷ 6.8 ms ≈ 9,400 tok/s, per user ≈ 147 tok/s   // lower bound on step time

Compare that with batch 1 (~190 tok/s total): about 50× the throughput for a ~25% slowdown per user. That is the throughput-latency trade-off the Inference Batching breakdown charts.

Prefill time

prefill time ≈ 2 × params × prompt_tokens ÷ (peak FLOP/s × utilization)

Llama 3 70B, 2,000-token prompt, 8 × H100 at ~50% MFU:
  2 × 70e9 × 2,000 = 2.8e14 FLOPs ÷ (8 × 989e12 × 0.5) ≈ 71 ms
Same model, 100,000-token prompt: ≈ 3.5 s, plus attention's quadratic term

So short prompts barely register, while very long prompts dominate TTFT and steal compute from everyone else's decode steps. That motivates chunked prefill, prefix caching and disaggregation, all covered below.

The KV cache in depth

The Fast Track gave the formula; here is how architecture choices change it. Per token, per layer, the model stores one key and one value vector for each KV head:

KV bytes per token = 2 × layers × kv_heads × head_dim × bytes_per_value

Other levers that shrink or bound the cache:

  • KV quantization: FP8 KV halves memory with small quality loss on most models; INT4 KV is more aggressive.
  • Sliding-window or local attention on some layers caps those layers' cache at the window size. Several open model families interleave local and global layers for this reason.
  • Hybrid architectures that replace some attention layers with state-space or linear-attention layers keep a fixed-size state instead of a per-token cache for those layers.
  • Offloading: spill cold KV blocks to CPU DRAM or SSD and bring them back on reuse, trading PCIe or network bandwidth for HBM.

PagedAttention and prefix sharing

Early servers reserved one contiguous KV region per request sized for its maximum length, wasting most of it. vLLM's PagedAttention splits the cache into fixed-size blocks (16 tokens by default) addressed through a per-sequence block table, exactly like virtual memory pages (Kwon et al., SOSP 2023):

  • No fragmentation: blocks are allocated on demand from a free list, so waste is at most one partial block per sequence.
  • Sharing: two sequences that start with the same tokens (same system prompt, parallel samples, beam search) point to the same physical blocks with a reference count, and copy on write when they diverge.
  • Prefix caching across requests: keep finished requests' blocks around, keyed by a hash of their tokens (vLLM's automatic prefix caching). A new request whose prompt starts with a cached prefix skips that part of prefill entirely.

SGLang's RadixAttention organizes cached prefixes as a radix tree of token sequences with LRU eviction, which makes multi-call programs (agents, few-shot templates, tree-of-thought) reuse KV automatically (Zheng et al., SGLang). The design lesson for interviews: prompt structure is a serving decision. Put stable content first so prefixes match, and route requests that share a prefix to the replica that holds it.

Scheduling: who runs on the next step

The scheduler decides, every iteration, which sequences are in the batch. The generations of batching (static, dynamic, continuous) are in the Fast Track; continuous, iteration-level scheduling comes from Orca (OSDI 2022) and is now standard. The details interviewers probe:

Admission and the token budget

Each step has a token budget (for example 2,048–8,192 tokens) shared between decode tokens (one per running sequence) and prefill tokens for newly admitted requests. A request is admitted only when there are enough free KV blocks for its prompt plus some headroom for growth.

Chunked prefill

Without it, admitting a 50K-token prompt means one giant prefill step during which every other user's stream freezes. Chunked prefill splits long prompts into budget-sized chunks interleaved with decode steps, so inter-token latency stays smooth (Sarathi-Serve, OSDI 2024). The cost is slightly higher TTFT for the long prompt.

Preemption

Sequences grow one block at a time, so the cache can fill mid-generation. The scheduler then preempts the lowest-priority (often most recent) sequences by either swapping their blocks to CPU memory or recomputing them later from the prompt. Recompute is usually cheaper for short contexts; swap for long ones. Frequent preemption is a signal you're over-admitting.

Priorities and fairness

Production schedulers add priority classes (interactive over batch, paid over free), per-tenant fairness, and deadline awareness: drop or deprioritize requests whose client has disconnected or whose deadline has passed.

Speculative decoding

Decode wastes compute at small batch sizes, so spend it on guessing. A cheap draft proposes γ tokens; the target model checks all of them in one forward pass (which costs about the same as generating one, since it's memory-bound); a rejection-sampling rule keeps the longest accepted prefix plus one corrected token. The output distribution is provably identical to the target model's (Leviathan et al., 2023).

α = probability each draft token is accepted, γ = draft length, c = draft cost ÷ target cost

expected tokens per target pass = (1 − α^(γ+1)) ÷ (1 − α)
speedup ≈ (1 − α^(γ+1)) ÷ ((1 − α) × (γ·c + 1))

α = 0.8, γ = 4, c = 0.05:  tokens/pass = (1 − 0.8^5) ÷ 0.2 ≈ 3.36
                           speedup ≈ 0.672 ÷ (0.2 × 1.2) ≈ 2.8×

Speculation helps most when the GPU is memory-bound (small batches, latency-sensitive traffic). At large batch sizes the server is closer to compute-bound and verifying rejected drafts wastes real FLOPs, so gains shrink or turn negative. Good engines adapt the draft length to load.

Sizing walk-through for Llama 3 70B at FP16: 140 GB of weights won't fit on one 80 GB H100. TP=2 fits the weights with only ~20 GB left for KV (about 60K tokens total, a handful of conversations). TP=4 leaves roughly 150 GB and TP=8 roughly 435 GB for KV and also lowers step time, which is why 70B-class models are usually served at TP=4–8 within one node, then replicated. At FP8 the same model fits on two GPUs with healthy KV room.

Prefill/decode disaggregation

Prefill wants big compute bursts; decode wants steady, memory-bound batches. Running both on the same GPUs means a long prefill disturbs everyone's token stream, and you can't size hardware or parallelism for each separately. Disaggregation runs them on separate pools and ships the KV cache between them:

  • DistServe showed that optimizing goodput with separate pools could serve up to 7.4× more requests or meet 12.6× tighter SLOs than colocated serving in their experiments (Zhong et al., OSDI 2024). Splitwise (Patel et al., ISCA 2024) made the same argument for hardware heterogeneity.
  • Mooncake, Moonshot AI's serving platform for Kimi, adds a KV-centric design: a distributed KV pool across the cluster's DRAM and SSD so prefixes are reused across requests and nodes (FAST 2025).
  • Open-source orchestration now packages this: NVIDIA Dynamo (disaggregated serving, KV-aware routing, KV offload across memory tiers) and llm-d (Kubernetes-native, built around vLLM, with an inference-aware scheduler).

The cost is moving KV. Do the math before proposing it:

8K-token prompt on Llama 3 70B: 8,192 × 320 KB ≈ 2.6 GB of KV
  over one 400 Gb/s RDMA link (≈ 50 GB/s) → ≈ 52 ms
  over NVLink inside a node (hundreds of GB/s) → a few ms

Disaggregation pays off at scale, with long prompts and strict inter-token SLOs. For a small deployment, chunked prefill on colocated GPUs is simpler and usually enough.

The serving stack around the engine

KV-aware routing

Round-robin load balancing destroys prefix-cache hit rates: the second turn of a conversation lands on a replica that has never seen the first. Better routers score replicas by expected cache overlap (hash of the prompt's leading blocks, or a session ID) and current load (queue length, free KV blocks), and pick the best combination. Pure session affinity creates hot spots, so cap per-replica load and fall back to the least-loaded replica. Kubernetes has a standard hook for this (the Gateway API Inference Extension), used by llm-d.

Autoscaling

  • Don't scale on GPU utilization. "Utilization" reports whether a kernel is running, not how much of the chip is used; a memory-bound decode loop looks 100% busy.
  • Scale on queue depth / waiting requests, KV cache utilization, and TTFT p95 against the SLO. Scale down slowly; GPUs are expensive to re-acquire.
  • Keep a headroom buffer because new replicas take minutes, and shed or downgrade low-priority traffic during the gap (see Gateways, Routing & Reliability).

Cold starts and model loading

140 GB of weights from object storage at ~1–2 GB/s (parallel reads) → 70–140 s
from local NVMe at ~5–7 GB/s                        → 20–30 s
+ engine init, CUDA graph capture, warm-up          → seconds to minutes

Mitigations: pre-stage weights on node-local disk, stream weights straight into GPU memory with parallel loaders, keep a minimum number of warm replicas, and use engine "sleep" modes that offload weights to CPU memory and wake in seconds. Cold start is why serverless GPU platforms charge a premium for low latency and why you size headroom rather than relying on instant scale-up.

Inference in System Design Interviews

When to bring it up

  • Capacity or cost questions: "Each 8×H100 node holds about 1.3M tokens of KV for a 70B model, so at 4K tokens per active conversation that's ~300 concurrent streams per node before batching slows anyone below our TPOT target."
  • Latency complaints: "TTFT is queue plus prefill; at 2K tokens prefill is ~70 ms, so if we're seeing two seconds, we're queueing, which usually means we're out of KV memory, not compute."
  • Self-host vs API: "At our volume a single fine-tuned 8B model on a few GPUs handles classification for a fraction of the API cost, so I'd move that step in-house and keep the frontier API for final answers."
  • Long-context features: "Long prompts are expensive to hold, not just to process; this is where prefix caching and KV quantization pay off."

How to introduce it

  1. State the workload: requests/s, input and output tokens, latency SLOs (TTFT, TPOT), and whether traffic is interactive or batch.
  2. Size memory first: weights at the chosen precision, then KV per token × concurrent tokens. Pick the parallelism that fits with KV headroom.
  3. Estimate step time and throughput with the bandwidth formula; derive tokens/s per node and nodes needed.
  4. Name the engine features you rely on: continuous batching, paged KV, prefix caching, chunked prefill.
  5. Add the cluster layer: prefix-aware routing, autoscaling on queue and KV metrics, admission control and priorities.
  6. Offer optimizations with trade-offs: FP8, speculative decoding for latency, disaggregation for strict SLOs at scale.

Common deep-dive questions

Why is generating one token so much slower than processing one prompt token?

Prefill processes all prompt tokens in parallel with high arithmetic intensity; decode must read every weight for each single new token, so it's bound by memory bandwidth. Strong answers quote the ridge point and the bandwidth-bound tokens/s ceiling.

A user pastes a 100K-token document and everyone's stream freezes. What happened and how do you fix it?

Bad Solution
Add more GPUs

Challenges: the freeze happens on whichever replica takes the request; more replicas just spread the problem.

Good Solution
Chunked prefill with a per-step token budget

Approach: split the long prefill into chunks interleaved with decode steps so other streams keep moving; cap prompt size per tier.

Challenges: the long request's TTFT grows, and a burst of long prompts still steals a large share of compute.

Great Solution
Chunked prefill plus long-context routing, prefix caching, and disaggregation at scale

Approach: route long-context requests to a dedicated pool (or a prefill pool in a disaggregated setup) so decode SLOs on the main pool are protected; cache the document's KV so follow-up questions skip prefill; price long context to reflect its cost.

Challenges: more pools to capacity-plan; KV transfer bandwidth must be provisioned.

How do you cut serving cost per token in half?

In rough order of effort: raise batch size until TPOT hits the SLO; FP8 weights and KV; prefix caching with prefix-aware routing; shorten outputs and prompts; route easy requests to a smaller or distilled model; move to newer GPUs with more bandwidth per dollar. Mention measuring quality after each step.

How does speculative decoding interact with load?

It trades spare compute for latency. Great at low batch; diminishing or negative at high batch. Expect adaptive draft lengths or turning it off under load.

How would you route requests across 50 replicas to maximize cache hits without hot spots?

Hash the leading prompt blocks (or session ID) to a preferred replica, score candidates by cache overlap minus a load penalty, cap per-replica queue length, and fall back to least-loaded. Track hit rate and per-replica queue skew.

When would you not self-host?

Low or spiky volume, need for frontier quality, small team, or no on-call capacity for GPUs. Self-hosting is an operational commitment, not just a cost line.

Summary

  • Decode is memory-bound, prefill is compute-bound. Bandwidth ÷ bytes per step gives the speed ceiling; batching is the main cost lever.
  • KV cache is the capacity limit. Know the formula and how GQA, MLA, FP8 KV and paging change it.
  • The scheduler sets the user experience: continuous batching, chunked prefill, preemption and priorities, measured by goodput against TTFT and TPOT SLOs.
  • Optimizations trade something: speculation trades compute for latency, quantization trades a little quality for memory and speed, disaggregation trades KV transfer for steadier latency.
  • The cluster layer matters as much as the engine: prefix-aware routing, metric-driven autoscaling, cold-start planning.

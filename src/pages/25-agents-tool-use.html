Agents, Tools & MCP

How tool calling works on the wire, how to structure an agent loop that terminates, which multi-agent architectures are worth their cost, how to design tools a model can use well, and how MCP, skills and durable execution fit into a production agent platform.

Agent questions are now the most common "new" prompt in LLM system design rounds: design a coding agent, a research agent, a support agent that can issue refunds, an internal ops assistant. Interviewers are rarely testing whether you know a framework. They are testing whether you understand that an agent is a loop around a stateless model, and that every interesting property of the system (correctness, cost, latency, safety, reliability) is decided by the code around that loop: what goes into the context, which tools exist, who authorizes them, when the loop stops, and what happens when something crashes halfway.

This page goes one level below the Fast Track summary. You'll learn the exact message contract behind function calling, the main agent architectures and when each wins, tool design principles that measurably improve agent accuracy, the Model Context Protocol in enough depth to discuss transports and auth, and how to make long-running agents durable, bounded and affordable. Security for agents gets its own page: Guardrails & Security.

How tool calling actually works

A model never executes anything. "Tool use" (also called function calling) is a structured conversation protocol: you describe tools with JSON Schema, the model replies with a request to call one, your code executes it and sends back the result as a message, and the model continues. Everything else in this page is built on that contract.

The message contract

Provider APIs differ in field names but share the same shape. A request carries the conversation plus tool definitions:

// request (shape shared by Anthropic, OpenAI, Gemini; field names vary)
{
  "model": "...",
  "system": "You are a support agent for ACME...",
  "tools": [{
    "name": "get_order",
    "description": "Look up one order by its ID. Returns status, items, total and refund eligibility. Use when the customer mentions an order number.",
    "input_schema": {
      "type": "object",
      "properties": { "order_id": { "type": "string", "pattern": "^ORD-[0-9]{8}$" } },
      "required": ["order_id"]
    }
  }],
  "messages": [{ "role": "user", "content": "Where is order ORD-00412345?" }]
}

// response: the model asks for a tool call and stops
{ "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "Let me look that up." },
    { "type": "tool_use", "id": "toolu_01A", "name": "get_order", "input": { "order_id": "ORD-00412345" } } ] }

// next request: append the assistant turn, then the result as a user-side message
{ "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01A", "content": "{\"status\":\"shipped\",\"eta\":\"2026-11-21\"}" } ] }

Three details interviewers like to probe:

  • The tool definitions are prompt tokens. Names, descriptions and schemas are serialized into the context on every call. Fifty verbose tools can cost tens of thousands of tokens before the user says anything, which matters for cost, latency and prompt caching (see Caching for LLMs).
  • The model can be wrong about arguments. It may invent an order ID, pass a string where you wanted an integer, or call a tool that doesn't fit. Your runtime validates against the schema and returns a helpful error as the tool result rather than crashing.
  • The ID links call and result. With parallel calls the model emits several tool_use blocks in one turn and you must return one tool_result per ID, in a single follow-up message (OpenAI Chat Completions instead takes one role: "tool" message per call ID).

Parallel tool calls are a large latency win for read-heavy agents: five independent lookups in one turn cost one model round trip instead of five. Execute them concurrently in your runtime, with a per-call timeout, and return partial failures as error results rather than failing the whole turn.

Structured outputs vs tools

If code consumes the answer, you don't need an agent; you need structured output. Most providers now support schema-constrained decoding ("strict" mode), where the server masks tokens that would violate the JSON Schema, so the output always parses. Two caveats: strict modes support a subset of JSON Schema (recursive or very large schemas may be rejected or slow to compile on first use), and a parseable object can still be wrong. Validate business rules (amount ≤ order total, date in the future) in code. Tool inputs can usually be made strict the same way, which removes a whole class of "malformed arguments" retries.

What the runtime owns

The model proposes; the runtime disposes. For every tool call your executor should:

  1. Validate arguments against the schema and business rules.
  2. Authorize against the end user's permissions, not the agent's service account. The model is never the authorization layer.
  3. Classify the side effect (read, reversible write, irreversible or external) and require confirmation where policy says so.
  4. Execute with a timeout and an idempotency key for writes.
  5. Shape the result: truncate, paginate, strip noise, mark it as untrusted content, and return errors as instructive text (is_error: true) so the model can recover.
  6. Record the call, arguments, result size, latency and cost in the trace.

The agent loop

Put the contract in a loop and you have an agent. The loop itself is a dozen lines; the guards around it are the design.

def run_agent(task, tools, budget):
    messages = [system_prompt(tools), user(task)]
    for step in range(budget.max_steps):                  # hard cap #1
        if budget.tokens_used > budget.max_tokens: return stop("token budget")
        if clock() > budget.deadline:               return stop("time budget")

        reply = llm.call(messages, tools, max_tokens=4096)  # retried with backoff on 429/5xx
        messages.append(reply)
        if reply.stop_reason == "end_turn":
            return verify_and_finish(reply)               # code checks the result, not the model

        results = []
        for call in reply.tool_calls:                     # run independent calls concurrently
            if loop_detector.repeated(call):              # same call + same args N times
                results.append(error(call, "You already tried this. Change approach."))
                continue
            if policy.needs_approval(call):
                await approval(call)                      # durable wait, see below
            results.append(executor.run(call))            # validate, authorize, timeout, truncate
        messages.append(tool_results(results))
        messages = compact_if_needed(messages)            # see Context Engineering
    return stop("step budget")

Say this in the interview: "The model decides when it thinks it's done; the platform decides whether it is done." A coding agent's run succeeds when the orchestrator's own test run passes, not when the model says "all tests pass."

Workflows first, agents second

Anthropic's Building effective agents separates workflows (LLM calls orchestrated by predefined code paths) from agents (the model chooses its own steps). Most production "agents" are mostly workflow with one agentic step inside. The five workflow patterns, covered with diagrams in Common Patterns:

PatternShapeExample
Prompt chainingFixed sequence of calls with checks between themOutline → check outline → write draft
RoutingClassify, then send to a specialized prompt or modelRefund vs technical vs sales tickets
ParallelizationSectioning or voting across concurrent callsRun three guardrail checks at once
Orchestrator–workersA model splits work dynamically and delegatesMulti-file code change, research fan-out

The rule of thumb: if you can draw the flowchart, write the flowchart in code. Use an agent only for the part where the number and order of steps truly depend on what the model discovers.

Single agent or multi-agent?

The honest answer is "single agent until you can show why not." Two well-known write-ups frame the trade-off:

  • Anthropic's multi-agent research system found an orchestrator with parallel sub-agents outperformed a single agent by 90.2% on their internal research eval, and that token usage alone explained about 80% of performance variance on BrowseComp. The price: agents use about 4× the tokens of chat, and their multi-agent system about 15×. They note it fits breadth-first, parallelizable queries with high-value answers, and fits poorly where agents must share context or depend on each other, such as most coding.
  • Cognition's Don't Build Multi-Agents argues the opposite failure: sub-agents working from partial context make conflicting decisions (one builds a Mario-style background, another a mismatched bird), so for coherent long tasks they prefer one agent with good context compression.

Both are right about different workloads. Use sub-agents as context isolation for read-heavy exploration ("find every call site of parse_date and report back in 200 words") and keep writes and final decisions in one agent that holds the full picture.

Designing tools agents can use

Tool design is the highest-leverage, most under-discussed part of agent systems. A tool is a contract between deterministic software and a non-deterministic caller that reads your descriptions literally. Anthropic's Writing effective tools for agents distills what they learned building Claude Code and MCP integrations:

  • Fewer, higher-level tools. Don't mirror your REST API one endpoint per tool. Instead of list_users, list_events and create_event, offer schedule_event that finds availability and books it. Instead of read_logs, offer search_logs that returns the relevant lines with context.
  • Namespace related tools (jira_search, jira_create_issue) so the model can tell overlapping tools from different servers apart.
  • Return meaningful context, not internals. Names, titles and short summaries beat UUIDs and MIME types. Offer a response_format parameter (concise or detailed) so the agent can ask for IDs only when it needs them for a follow-up call.
  • Be token-efficient by default. Paginate, filter and truncate with sensible defaults, and say so in the result ("showing 20 of 312; refine with status or since"). The post notes that Claude Code caps tool responses at 25,000 tokens by default.
  • Write errors for the model. "Invalid date" is useless; "start_date must be ISO 8601 like 2026-11-19; you sent '19/11'" lets the agent self-correct in one step.
  • Prompt-engineer the descriptions. Describe tools the way you'd brief a new teammate: when to use it, when not to, what the parameters mean (user_id, not user), and what it returns. Small description changes produced large accuracy gains in Anthropic's evals.
  • Evaluate tools with agents. Build realistic multi-step tasks, run the agent, read the transcripts, and let the model itself suggest description and schema fixes.

Platform engineers should add three properties the model can't see but your system depends on:

  • Idempotency: every write accepts an idempotency key (derive it from run_id + step_id) so a retried step doesn't refund twice.
  • Dry run / preview: risky tools expose a preview that returns the exact change ("will email 4,312 recipients") for approval before commit.
  • Risk metadata: tag each tool read-only, reversible or irreversible, and internal or external, so policy and approval rules are data, not prompt text.
// weak: mirrors the API, ambiguous, returns everything
{ "name": "query", "description": "Runs a query",
  "input_schema": { "properties": { "q": { "type": "string" } } } }

// strong: task-shaped, constrained, cheap by default, explicit about side effects
{ "name": "crm_find_accounts",
  "description": "Search customer accounts by name, domain or owner. Read-only. Returns up to `limit` matches with name, domain, plan and owner. Use before crm_update_account to get the account_id.",
  "input_schema": { "type": "object",
    "properties": {
      "text":  { "type": "string", "description": "Name or domain fragment, e.g. 'acme' or 'acme.com'" },
      "plan":  { "type": "string", "enum": ["free", "team", "enterprise"] },
      "limit": { "type": "integer", "minimum": 1, "maximum": 50, "default": 10 },
      "response_format": { "type": "string", "enum": ["concise", "detailed"], "default": "concise" } },
    "required": ["text"] } }

Large tool sets: tool search and code execution

Accuracy and cost both degrade as you add tools: every definition is in context on every call, and similar tools get confused. Connecting a handful of MCP servers can mean a hundred tools. Three techniques scale past that:

  • Tool search with deferred loading. Mark most tools as deferred; the model initially sees a small search tool plus a few always-on tools, searches by keyword or description when it needs a capability, and only matching definitions are loaded. Anthropic exposes this as a tool search tool with defer_loading (regex and BM25 variants) and reports large token savings and accuracy gains on big tool libraries (Advanced tool use). Keep the 3–5 most-used tools loaded, and keep deferred tools out of your cached prefix so loading one doesn't invalidate the cache.
  • Routing to sub-agents. Give each specialist sub-agent only its domain's tools.
  • Programmatic tool calling. Let the model write code that calls tools inside a sandbox and returns only the final result. Fetching 200 expense records to sum them then costs a few hundred tokens of output, not 200 tool results in context. Cloudflare's "Code Mode" for MCP applies the same idea.

The Model Context Protocol (MCP)

Before MCP, every AI application wrote its own integration for every data source: N apps × M tools. MCP standardizes the interface so any host can use any server, turning that into N + M. Anthropic open-sourced it in November 2024; OpenAI, Google, Microsoft and most agent tooling adopted it during 2025, and it is now governed under the Linux Foundation's Agentic AI Foundation.

Roles and primitives

  • Host: the user-facing application (an IDE, a CLI agent, a chat app). It owns the model, the user's consent and the security policy.
  • Client: a connector inside the host, one per server connection.
  • Server: a program that exposes capabilities, either local (launched by the host) or remote (a web service).

The 2026-07-28 revision: stateless MCP

Early MCP was session-oriented: an initialize handshake, a session ID header, and per-connection state, which made remote servers awkward to run behind ordinary load balancers. The 2026-07-28 specification removed protocol-level sessions and the Mcp-Session-Id header, dropped the initialize handshake so each request stands alone, removed SSE stream resumability, required Mcp-Method and Mcp-Name headers on Streamable HTTP POSTs (so gateways and WAFs can route and meter without parsing JSON bodies), made list endpoints such as tools/list independent of the connection so they can be cached, added a server/discover call for version and capability discovery, and replaced the GET stream and resource subscriptions with a single subscriptions/listen stream. Long-running operations moved out of the core into a formal Tasks extension, alongside the MCP Apps extension for interactive UI. For system design this means a remote MCP server is now an ordinary stateless HTTP service: horizontally scalable, cacheable at the edge, and fronted by standard API gateway infrastructure. Any state you need lives in your own store, keyed by user or task, not in the connection.

Authorization

Remote MCP servers use OAuth 2.1. The MCP server is a resource server; a separate authorization server issues tokens. The essentials:

  • The client discovers the authorization server from the server's Protected Resource Metadata (RFC 9728), runs an authorization-code flow with PKCE, and requests a token bound to that specific server with resource indicators (RFC 8707), so a token for server A is useless at server B.
  • Clients identify themselves with Client ID Metadata Documents (a URL that hosts the client's metadata) where supported, with Dynamic Client Registration as a legacy fallback in the 2026 revision (spec, WorkOS summary).
  • No token passthrough. A server that calls a downstream API must obtain its own token for that API rather than forwarding the user's MCP token; otherwise you get a confused deputy.
  • Scopes should be narrow and tool-shaped (issues:read, not repo), and tokens short-lived.

Running MCP in production

  • An MCP gateway in front of approved servers: allowlist, version pinning, per-tool enable/disable, auth brokering, rate limits, logging of every call.
  • Review tool descriptions as code. They are instructions to your model, so a malicious or compromised server can inject through them (tool poisoning) or change them after approval (a rug pull). See Guardrails & Security.
  • Treat tool results as untrusted content, exactly like web pages.
  • Measure per-tool call counts, error rates, latency and result sizes; drop or merge tools the model never uses or misuses.

A2A: agent-to-agent

MCP connects an agent to tools; Google's Agent2Agent (A2A) protocol connects agents to other agents, possibly built by different vendors. An agent publishes an Agent Card (capabilities, endpoint, auth requirements); a client agent sends it tasks that can be long-running and stream updates and artifacts back. A2A became a Linux Foundation project in June 2025 with AWS, Cisco, Google, Microsoft, Salesforce, SAP and ServiceNow as launch partners (Linux Foundation). In interviews, mention it when the prompt involves cross-organization agent collaboration; for a single product, internal sub-agents are just function calls.

Skills: packaged procedural knowledge

Tools give an agent abilities; skills give it know-how. A skill is a folder with a SKILL.md file (YAML frontmatter with a name and description, then Markdown instructions), optionally with scripts and reference files. Anthropic shipped the format in October 2025 and published it as an open standard at agentskills.io in December 2025; many coding agents now load the same format.

The design idea is progressive disclosure: only names and descriptions sit in the context at startup (a few dozen tokens each); the full instructions load when a task matches; bundled files and scripts load only if the instructions point to them. That lets an agent carry hundreds of procedures ("how we write migrations", "how to fill the quarterly tax form") without paying for them on every call. Related ideas: project instruction files such as AGENTS.md or CLAUDE.md that are always loaded, and slash-command prompts. A useful interview line: "MCP gives access, skills give procedure, the system prompt gives identity and policy."

State, durability and long-running agents

A chat turn lasts seconds. An agent run can last 30 minutes, wait two days for a human approval, and make 200 calls to flaky external services. If the process holding the loop crashes, what happens? "It restarts from the beginning" is wrong: you pay for the tokens twice and you may repeat side effects.

Durable execution

Durable execution engines (Temporal, Restate, Inngest, AWS Step Functions, DBOS) let you write the loop as ordinary code while the engine records every step's result in an event history. Model calls and tool calls run as activities with timeouts and retry policies. If a worker dies, another worker replays the history, skipping completed activities by reusing their recorded results, and continues from the first incomplete step. Agent frameworks offer lighter versions: LangGraph persists graph state at each node with checkpointers; agent SDKs persist sessions. Choose by how much you need: a checkpoint table keyed by run_id is enough for short runs; multi-hour, multi-day or approval-heavy runs justify a workflow engine.

The model call itself is non-deterministic. In a replay-based engine it must run as an activity (whose recorded result is reused on replay), never inline in workflow code, or replays will diverge.

Side effects: idempotency and sagas

  • At-least-once is the reality. A tool call can succeed and the acknowledgement can be lost. Every write needs an idempotency key so a retry is a no-op downstream.
  • Outbox: when a step must update your DB and notify another system, write both to your DB in one transaction and publish from the outbox.
  • Sagas: multi-step business actions (book flight, book hotel, charge card) record a compensating action for each completed step, so a failure halfway can undo what was done rather than leave a half-booked trip.

Human in the loop

  • Model the approval as a durable wait (a workflow signal or a row the run polls), with a timeout and a default (usually cancel). The worker shouldn't hold memory or a sandbox while waiting.
  • Show the exact action: tool, arguments, preview of effects, and why the agent wants it. Bind the approval to a hash of those arguments, so the agent can't change them after approval.
  • Tier by risk to avoid approval fatigue: auto-approve reads, approve-once-per-session for routine writes, always approve irreversible or external actions (payments, emails to customers, production deploys).
  • Let the human steer, not just approve: messages sent during a run are injected at the next step.

Cost, latency and concurrency

Agent token math

Agent cost grows faster than linearly with steps, because every step re-sends the whole growing context. A worked example, using $2 per million input tokens and $10 per million output tokens (Sonnet 5.5 list prices):

Run: 30 steps. Fixed prefix (system + tools + task) = 8,000 tokens.
Each step adds ~1,500 tokens (300 model output + 1,200 tool result).

Input at step i = 8,000 + 1,500 × i              (i = 0..29)
Total input     = 30 × 8,000 + 1,500 × (0+1+…+29)
                = 240,000 + 652,500 = 892,500 tokens   # quadratic in steps
Output          = 30 × 300 = 9,000 tokens

Without caching: 892,500 × $2/M + 9,000 × $10/M = $1.79 + $0.09 ≈ $1.88 per run

With prompt caching (write 1.25×, read 0.05×; only new tokens are written each step):
  writes = 8,000 + 29 × 1,500 = 51,500  × $2.50/M = $0.13
  reads  = 892,500 − 51,500   = 841,000 × $0.10/M = $0.08
  output                                         = $0.09
  total ≈ $0.30 per run  (≈ 6× cheaper)

Three levers follow directly: cache the prefix (keep it stable and append-only), shrink tool results (they're 80% of the growth here), and compact old steps into summaries when context passes a threshold. Multiply by run volume and you get the business case: 100K runs a day is $188K a day uncached versus $30K cached.

Latency

A step costs roughly TTFT + output tokens × TPOT + tool time. At ~1 s TTFT, 300 output tokens at 60 tok/s (5 s), and 1 s of tool time, a 30-step run takes about 3.5 minutes. Levers: parallel tool calls, smaller and faster models for sub-steps (summarizing logs, naming branches), lower reasoning effort on easy steps, speculative prefetching of likely reads, and streaming progress to the user so a long run feels alive. For interactive agents, show the plan and each tool call as it happens.

Running agent fleets

Provider rate limits are per minute on requests, input tokens and output tokens. Size them with Little's law: 2,000 concurrent runs × one model call every 8 s = 250 calls/s; at 40K input tokens per call that's 10M input tokens per second, or 600M per minute. Most of those tokens are cache reads, and some providers don't count cached reads against input-token limits, so check how your provider meters before you buy capacity. Operationally:

  • A token-aware admission controller in the LLM gateway (reserve estimated tokens, reconcile on completion) with per-tenant concurrency caps and priority classes (interactive above background).
  • Back off with jitter on 429s and pause runs during provider outages rather than failing them; durable execution makes pausing free.
  • Cache-aware routing for self-hosted models: keep a run on the replica that holds its prefix.
  • Separate quotas for sandboxes (CPU minutes) and model tokens; either can be the bottleneck.

Memory for agents

Agents need three kinds of state beyond the transcript: a scratchpad for the current task (a to-do list the agent rewrites, which also keeps it on track), notes files that survive compaction or a new session (progress logs, decisions), and long-term memory about the user or project retrieved by relevance. Mechanisms (compaction thresholds, memory tools, what to keep verbatim) are covered in Context Engineering & Memory.

Computer-use and browser agents

When no API exists, an agent can operate a GUI: the model receives screenshots (and sometimes an accessibility tree), returns actions such as click, type and scroll, and the loop repeats. Anthropic's computer use (October 2024) and OpenAI's Operator / computer-using agent (January 2025) popularized the pattern. Design implications: each step is slow (a screenshot is image tokens, and a task can take hundreds of steps), so prefer APIs, DOM-level browser tools or recorded scripts when available; run the browser or desktop in an isolated VM with no saved credentials; treat every page as hostile input (web pages are the classic indirect injection vector); and require confirmation before purchases, form submissions and logins.

Agents in System Design Interviews

When to bring it up

  • The task has an unknown number of steps. "Investigating a failed deployment could take two queries or twenty, so a fixed pipeline won't work. I'll use an agent loop with read-only tools and budgets."
  • The system must act, not just answer. "Issuing refunds is a write, so the model proposes a refund through a tool and the executor enforces limits and approvals."
  • Integrations are many and changing. "Customers bring their own tools, so I'd accept MCP servers behind a gateway rather than writing custom integrations."
  • And, just as important, when not to: "Ticket classification has a fixed shape, so a single structured-output call with routing is cheaper and more predictable than an agent."

How to introduce it

  1. Justify autonomy. State why a workflow isn't enough, and keep everything else as a workflow.
  2. Define the tools. List 4–8 task-shaped tools with their side-effect class. This is your API design step for the agent.
  3. Draw the loop and its owner. An orchestrator (durable workflow) that calls the model through a gateway and tools through an executor; state in the workflow history, not in memory.
  4. Put guards on it. Budgets, loop detection, verification by code, approvals for irreversible actions.
  5. Manage context. Stable cached prefix, truncated tool results, compaction, sub-agents for exploration.
  6. Close with safety and evals. Least-privilege tools, untrusted-content handling, and a task-based eval suite with deterministic checks (see Evaluation).

Common deep-dive questions

"How do you stop the agent from doing something harmful and irreversible?"

Bad Solution
Tell the model in the system prompt to be careful

Challenges: prompts are suggestions; a confused model or an injected instruction ignores them. The model is not an authorization layer.

Good Solution
Executor-side checks and confirmation for writes

Approach: the executor validates arguments, checks the end user's permissions, and requires user confirmation for any write.

Challenges: confirming everything causes approval fatigue, so users click through; limits live in ad hoc code.

Great Solution
Risk-tiered policy as data, scoped credentials, previews and durable approvals

Approach: tag every tool by side-effect class; a policy engine maps (tool, arguments, user, tenant) to allow, deny or require approval with limits (refunds over $200 need a human). Credentials are scoped to the user and the task and live outside the model's reach. Risky tools offer a dry-run preview; approvals are durable waits bound to an argument hash, with timeouts. Irreversible actions get rate limits and anomaly alerts, and everything is audit-logged.

Challenges: policy maintenance; measure approval rates and tune tiers so humans only see decisions that matter.

"The agent sometimes loops forever or burns $40 on one task. Fix it."

Budgets enforced outside the model (steps, tokens, dollars, wall clock) at the gateway and orchestrator; repetition detection on (tool, args) hashes and repeated errors; a strategy-change message before escalation; better tool errors (most loops are the model retrying a call whose error message doesn't say what to change); and per-task cost dashboards with alerts on the p99. Then look at transcripts of the worst runs and fix the tools or prompt that caused them.

"Single agent or multi-agent?"

Default to one agent. Add sub-agents for parallel, read-heavy exploration where each worker can return a short summary, and accept roughly an order of magnitude more tokens for it. Keep writes and final synthesis in one agent with full context. Quote the trade-off: Anthropic's 90% quality gain on breadth-first research at ~15× tokens versus Cognition's coherence argument.

"How does the agent survive a crash at step 37 of 50?"

The loop runs as a durable workflow; each model and tool call is a recorded activity; on crash another worker replays the history and resumes at step 38 without re-calling the model for steps 1–37. Tool writes are idempotent by key, the sandbox is snapshotted or reconstructible from the recorded actions, and the user's event stream resumes from the last event ID.

"You have 300 internal APIs. How does the agent use them?"

Not as 300 tools. Group them into task-shaped tools per domain, expose them through MCP servers behind a gateway, use tool search with deferred loading so only relevant definitions enter context, and route domain-specific work to sub-agents with narrow tool sets. Evaluate tool selection accuracy as its own metric.

"How do you evaluate an agent?"

Task suites with deterministic end-state checks (tests pass, the right record changed, the email draft contains the required fields), run in sandboxes, scored on success rate, cost per successful task, steps and time. Add trajectory checks (did it call a forbidden tool, did it ask for approval), run each task several times because agents are stochastic, and track pass@k and consistency. Details in Evaluation.

Summary

  • Tool calling is a message protocol: schemas in, structured call out, result back as a message. The runtime validates, authorizes, executes, shapes and logs; the model only proposes.
  • Prefer workflows; add agentic loops only where the steps are truly unknown. Default to one agent; use sub-agents for parallel read-heavy exploration and accept the token bill.
  • Design tools for the model: few, task-shaped, namespaced, token-efficient, with instructive errors. Add idempotency keys, previews and risk metadata for the platform.
  • MCP standardizes integrations; since the 2026-07-28 revision remote servers are stateless HTTP services secured with OAuth 2.1 and audience-bound tokens. Skills package procedure with progressive disclosure; A2A connects agents across vendors.
  • Long runs need durable execution, idempotent side effects, durable approvals and budgets enforced outside the model. Agent cost is roughly quadratic in steps; prompt caching and smaller tool results are the biggest levers.

Question Breakdown · Hard

Design Copilot-style Code Autocomplete

Inline "ghost text" code suggestions that appear as a developer types, like GitHub Copilot completions or Cursor Tab. The LLM system design question where the latency budget is measured in hundreds of milliseconds.

Understanding the Problem

As a developer types in their editor, the tool predicts what comes next (the rest of the line, or the next few lines) and shows it as faint inline text. Tab accepts it; typing anything else dismisses it. Unlike chat or agents, nobody asked for this suggestion: it competes with the developer's own typing, so a suggestion that arrives late or is wrong is worse than none. That inverts the usual LLM trade-offs: small, fast models beat big, smart ones; latency is a correctness requirement; and the most important decision is often whether to show anything at all.

It is also a serving problem at enormous request volume. Cursor reports its Tab model handles over 400 million requests per day (Cursor, Improving Cursor Tab with online RL). Each request is small, but there are a lot of them, and most are thrown away before the user sees them.

Functional Requirements

  1. As a developer types, the editor should show inline suggestions (single-line or multi-line) at the cursor, which they can accept fully, accept word by word, or ignore by continuing to type.
  2. Suggestions should use context from the current file (code before and after the cursor) and from related files in the project.
  3. The system should be able to suggest the next edit elsewhere in the file, based on the edits the developer just made.
  4. Organization admins should be able to set policy: enable per org or repo, exclude files from ever being sent, and block suggestions that match public code.

Below the line: chat and agent modes (see Design Claude Code), pre-training the model, billing.

Non-Functional Requirements

  1. Latency: a suggestion visible within ~300 ms (p50) and ~600 ms (p95) of the developer pausing; after that the developer has usually typed on and the suggestion is stale. These are targets, not published figures; quantify them in your interview.
  2. Never block the editor: typing must stay fluid; under failure the system shows nothing rather than freezing or showing errors.
  3. Scale: ~2M daily active developers, ~1B requests/day, peaks around 3× average during working hours in each region.
  4. Quality: measured by acceptance rate and by characters accepted and retained in the code; showing fewer, better suggestions beats showing more.
  5. Privacy: code sent only as needed for the request; for business customers, prompts and suggestions are not retained or used for training; excluded files and secrets never leave the machine.
  6. Cost: completions are bundled into a per-seat price, so each request must cost a small fraction of a cent.

The Set Up

Core Entities

  • CompletionRequest: request id, document URI and language, cursor position, prefix, suffix, context snippets, editor state (single-line vs block position), client settings.
  • Suggestion: text, range to replace, model version, a confidence score, shown and accepted flags.
  • ContextSnippet: source (open tab, recent edit, symbol definition), file path, text, relevance score.
  • TelemetryEvent: shown, accepted (full or partial), rejected, and retained-after-N-seconds, keyed by request id, with no code by default.
  • OrgPolicy: enabled scopes, content exclusions, public-code filter, data retention setting.

API

Capacity estimate

2M developers × 500 requests/day      = 1B requests/day ≈ 11.6K req/s avg, ~35K peak
prompt ≈ 2K tokens, output ≈ 30 tokens (single line ~10, a block ~80)

prefill: 1B × 2K  = 2T tokens/day   ≈ 23M tokens/s
decode:  1B × 30  = 30B tokens/day  ≈ 350K tokens/s
→ input outweighs output ~70:1. This is a prefill-bound workload.

prefill compute for an assumed 7B-parameter model: 2 × 7e9 FLOP/token
  23M tok/s × 14 GFLOP = 3.2e17 FLOP/s
  H100 ≈ 989 TFLOP/s dense BF16; at ~50% utilization ≈ 0.5e15 FLOP/s
  → ~650 GPUs of prefill at average load with no caching (~3× at peak); ~130 if 80% of prompt tokens hit a prefix cache

The model size is an assumption for the math; the point is the shape. Consecutive requests from one developer share almost the whole prompt (the file changed by a few characters), so prefix caching with session-affine routing is the biggest cost lever, the same idea as in Caching for LLMs but at keystroke granularity.

High-Level Design

1) Showing suggestions as the developer types

Most of the latency budget is won or lost in the editor extension, before any network call:

  • Trigger rules: request after a short pause in typing, not on every keystroke; skip positions where completions are rarely accepted (middle of an identifier, inside a string literal in some languages) and decide line vs block mode from the cursor position (a block is only worth generating at the start of an empty function body or after a comment).
  • Debounce and cancel: each keystroke resets a timer of a few tens of milliseconds and cancels any in-flight request. Only one request per editor is ever live.
  • Typed-through cache: if the ghost text is return a + b and the developer types ret, keep showing urn a + b without a new request. A small LRU of recent (prompt hash → suggestion) entries also covers backspacing and undo.
  • Streaming render: show the first line as soon as it is complete; extend with later lines as they stream.

2) Gathering context

The model sees a fill-in-the-middle (FIM) prompt: the code before the cursor (prefix), the code after it (suffix), and sentinel tokens telling it to generate the middle (Bavarian et al., Efficient Training of Language Models to Fill in the Middle). Before FIM, Copilot only sent the prefix; GitHub reports FIM gave a 10% relative increase in accepted completions in A/B tests (GitHub blog).

Context from other files is added as commented snippets ahead of the prefix. GitHub's "neighboring tabs" technique uses files open in the editor and reported a 5% relative increase in acceptance (same post). A reverse-engineering analysis of an earlier Copilot client found it sliced each open file into fixed-size windows and picked the window with the highest Jaccard similarity (set overlap of tokens) to the code near the cursor (copilot-explorer; based on an older build, so treat the details as illustrative). The assembler fills a fixed token budget in priority order: prefix nearest the cursor, suffix, then retrieved snippets, dropping the lowest-value pieces first.

3) Serving the model

Requests go to the nearest region. An edge proxy authenticates, rate limits per user and applies org policy; a router sends each developer's requests to the same GPU replica so their prompt prefix is already in that replica's KV cache; the replica runs a small FIM model with continuous batching. Generation stops early on stop sequences and on structural signals (end of line in line mode; a dedent or closing bracket that ends the block in block mode). A post-processor trims text that duplicates the suffix (the model re-writing the closing brace that already exists) and balances brackets.

4) Org policy and next-edit suggestions

Policy is enforced twice: on the client (excluded paths are never read into a prompt) and at the edge (the server rejects requests for disabled repos). Before tokens leave the server, filters check for secrets and, if the org enabled it, for long matches against an index of public code. Next-edit suggestions reuse the same pipeline with a different prompt (recent edit history) and model, covered in deep dive 4.

Potential Deep Dives

1) How do we hit a ~300 ms budget?

One reasonable budget for a single-line suggestion after the developer pauses:

StageBudgetHow
Debounce~50 msShort timer; long enough to skip mid-burst keystrokes
Context gathering (client)≤ 20 msIncremental: snippet windows precomputed per open file, updated on edit
Network to regional edge20–60 msRegional serving; persistent HTTP/2 connection, no TLS handshake per request
Queue + prefill20–50 msSmall model; most of the prompt hits the prefix cache
Decode first line (~15 tokens)75–150 ms~100–200 tokens/s per stream on a small model
Post-process + render< 10 msShow the first line as soon as it's complete
Total≈ 200–340 ms
Bad Solution
A frontier chat model, called on every keystroke

Challenges: TTFT alone is often over a second; per-stream decode is slower; cost per request is orders of magnitude too high; and most requests are obsolete before they return.

Good Solution
Small FIM model, debounced requests, streaming, regional serving

Approach: a model trained for FIM on code, served close to users, with client-side debounce and streaming. GitHub reports its custom completions model delivered a 35% latency reduction and 3× token throughput over the previous one (GitHub blog).

Challenges: cancelled requests still burn GPU time if the server keeps generating; every request re-processes a 2K-token prompt from scratch.

Great Solution
Make cancellation real, make prefill nearly free, make decode speculative

Approach:

  • End-to-end cancellation: an HTTP/2 stream reset propagates through the proxy to the inference server, which evicts the sequence from the running batch at the next step. Requests whose deadline has passed are dropped from the queue instead of served.
  • Session-affine prefix caching: consistent hashing on user + file routes consecutive requests to the replica holding their KV cache. Prompt ordering matters: in the usual prefix-suffix-middle order, an edit at the cursor invalidates the cached suffix. The FIM paper's suffix-prefix-middle (SPM) variant puts the suffix first, so as the developer types, the prompt grows by appending and the cache keeps hitting.
  • Speculative decoding: code is repetitive, so drafting tokens by copying from the prompt (n-gram or "prompt lookup" drafting) or from a tiny draft model lets the main model verify several tokens per step. See Inference & Serving.
  • Load shedding, not queueing: under overload, return "no suggestion" immediately. A late suggestion has zero value, so a deep queue only wastes GPU time.

Challenges: affinity fights load balancing (a hot replica must spill users to others and accept cache misses); speculative decoding gains shrink at high batch sizes.

2) Which context goes into a 2K-token prompt?

Bad Solution
Only the text above the cursor in the current file

Challenges: the model can't see the code below (it duplicates closing braces or the next function) or the types and helpers defined in other files, so it invents names.

Good Solution
FIM prefix and suffix plus similar windows from open tabs

Approach: the setup in the high-level design: Jaccard-ranked windows from open files, added as comments above the prefix.

Challenges: open tabs are a weak proxy for relevance; the definition of the function being called is often in a file that isn't open.

Great Solution
Multi-source retrieval with per-source budgets, tuned by acceptance A/B tests

Approach: combine several cheap, local sources: definitions of symbols near the cursor from the language server (signatures of the functions and types being used), recently edited regions (the developer is probably continuing that work), similar windows from open and recently viewed files, and imports. Each source gets a share of the budget, and the assembler drops lowest-scored snippets first. Everything is computed incrementally on the client so it fits in ~20 ms; no repo-wide index is required, though one can be added. The budget split and ranking are tuned by online experiments on acceptance and retained characters, not by intuition.

Challenges: more context means more prefill cost per request and more data leaving the machine; each source must respect content exclusions.

3) When should we show nothing?

A wrong suggestion costs the developer attention. Cursor's team frames it as an expected-value problem: if a suggestion is accepted with probability p, showing it is only worth it above a threshold, and they trained their model with online reinforcement learning so it makes 21% fewer suggestions with a 28% higher accept rate (Cursor).

Bad Solution
Always show whatever the model returns

Challenges: noisy suggestions train developers to ignore the feature; acceptance falls and so does trust.

Good Solution
Heuristics plus a confidence threshold

Approach: suppress in low-value positions; drop suggestions whose mean token log-probability is below a tuned cutoff; drop empty or whitespace-only and suffix-duplicating outputs.

Challenges: log-probability is poorly calibrated across languages and contexts.

Great Solution
Learn the show/no-show decision from acceptance data

Approach: either a lightweight classifier on request features (position, language, recent accept history, model confidence) predicting acceptance, or, as Cursor did, train the generator itself with a reward that penalizes shown-and-rejected suggestions so it learns to abstain. Retrain frequently from fresh telemetry.

Challenges: training on your own model's shown suggestions is a feedback loop (you only learn about suggestions you showed); keep an exploration slice and evaluate offline before shipping.

4) How do we predict the next edit, not just the next characters?

Much of coding is editing: rename a parameter and the call sites need the same change. GitHub's next edit suggestions and Cursor Tab predict both where the next edit is and what it is, using the developer's recent edits as input. GitHub found general-purpose models didn't meet its quality and latency bar and trained a custom model for it (GitHub blog).

Bad Solution
Run the completion model at every candidate location

Challenges: N requests per keystroke, and a completion model has no idea what you just changed.

Good Solution
A separate edit model fed with recent diffs

Approach: the prompt holds the last few edits as diffs plus a window of the file; the model outputs a rewritten region; the client diffs it against the file and renders the change with a "Tab to jump" affordance.

Challenges: two models and two serving stacks to maintain; the edit model's outputs are longer, so latency is higher.

Great Solution
One model trained on real edit sequences, served on the same stack

Approach: train on (edit history → next edit) pairs mined from real editing sessions with consent, then refine with RL on acceptance. Serve it on the same affinity-routed, prefix-cached fleet; the edit history is append-only, so it caches well. Only show edits within a window around the cursor, and require the region to still match before applying.

Challenges: collecting edit data raises privacy questions; edits that jump far away are disorienting, so UX limits matter as much as model quality.

5) How do we serve 35K requests/s cheaply?

  • Regional pools sized to each region's working-hours peak; follow-the-sun autoscaling, with a floor of warm capacity because model load time is minutes.
  • Continuous batching with short max-token limits keeps per-step latency stable; separate pools for line and block modes keep long block generations from slowing single-line ones.
  • Cache hit rate is the cost metric: track prefix-cache hit rate per replica alongside utilization; rebalance users when a replica's cache thrashes.
  • Admission control: per-user rate limits (a runaway client or script must not consume a replica) and priority for paid tiers.
  • Graceful degradation: on regional failure, fail over to the next region only if its latency is within budget; otherwise show nothing. See Gateways, Routing & Reliability.

6) How do we measure quality?

Bad Solution
Acceptance rate alone

Challenges: easy to game by showing only trivial suggestions; says nothing about whether accepted code survived.

Good Solution
Acceptance plus retained characters and latency

Approach: track the share of shown suggestions accepted, and characters accepted and still present after some time (GitHub's custom model post reports 20% more accepted-and-retained characters and a 12% higher acceptance rate), alongside p50/p95 latency and cancellation rate.

Great Solution
Offline FIM evals, online A/B with guardrails, and per-segment views

Approach: an offline harness masks spans in held-out repositories (ideally your customers' languages and frameworks, never training data) and scores exact match, whether the result compiles, and whether tests pass, in the style of public infilling and repository-level benchmarks. Every model, prompt or context change then runs as an online A/B with guardrail metrics (latency p95, error rate, cost per request) and is sliced by language, IDE and request type, because an average can hide a regression in one language. See Evaluation.

Challenges: telemetry must not contain code; measure retention with hashes and lengths, not content.

7) How do we meet enterprise privacy requirements?

  • Minimize what leaves the machine: content exclusions applied client-side; a local secret scanner strips keys and tokens from prompts.
  • Zero retention for business tiers: prompts and suggestions are processed in memory and discarded; logs carry ids, sizes and timings, not code; no training on customer code without opt-in.
  • Data residency: route to in-region pools for customers who require it, which constrains failover options.
  • Public-code filter and audit: optional blocking of suggestions that match public code, and admin-visible usage audit logs. See Guardrails & Security.

What is Expected at Each Level?

Mid-level

Debounced client requests to a hosted model, prefix + suffix prompt, streaming ghost text, a basic latency target. Mentions cancelling stale requests and that a smaller model is needed.

Senior

A quantified latency budget; FIM and multi-source context with a token budget; real cancellation through to the GPU; capacity math showing the workload is prefill-bound and that session-affine prefix caching is the main lever; acceptance and retained-characters metrics.

Staff+

Learned show/no-show decisions and the feedback-loop risk; next-edit prediction as a product and model strategy; SPM ordering and speculative decoding; regional capacity planning with load shedding; enterprise privacy and residency trade-offs; an eval program that gates every model and context change.

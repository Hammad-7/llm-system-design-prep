Question Breakdown · Medium

Design an Internal Repo Discovery Service

A company-wide portal where any employee, remote or on site, can search the company's GitHub repositories in natural language, read what each one does, see who owns it, and contact the owners to use or contribute to it. Representative of "design an internal developer portal", "make our repos discoverable" and "LLM-powered enterprise search" prompts.

Understanding the Problem

A company has a few GitHub organizations with tens of thousands of repositories. Nobody knows what exists. An engineer who needs to send SMS from a new service either builds it again or asks around in Slack until someone remembers that notify-gateway does exactly that, and that the person who wrote it left last year. The company wants one place where you type "is there something that sends text messages to customers?", get the right repo with a short explanation of what it does and how to use it, see the owning team and the people to talk to, and send them a message in one click.

It looks like the support RAG assistant, but the corpus is small and the read traffic is tiny. Three things make it a real design problem:

  • The data lives in a system you don't own. GitHub is the source of truth. You keep a derived copy in sync through webhooks and API calls, within GitHub's rate limits, and webhooks can be missed, duplicated or arrive out of order.
  • Ownership is the most valuable field and the least reliable one. CODEOWNERS files are missing or stale, teams get reorganized, people leave. Showing a departed engineer as the owner is worse than showing nothing.
  • Most repos describe themselves badly. Empty READMEs, names like svc-2, no topics. Natural-language search only works if something reads the code and writes the description the author never did. That's where the LLM earns its place.

The interviewer is usually testing whether you put the LLM on the write path, not the read path. Summarizing 50K repos once (and again only when they change) is cheap and makes search fast and good. Calling a big model on every search is slow, expensive, and doesn't fix the underlying problem: the index has nothing useful to match against.

Functional Requirements

  1. Employees should be able to search repositories with natural-language questions or keywords, and narrow results by language, team, status (active, deprecated, archived) and recency.
  2. Employees should be able to open a repo page showing what it does, its tech stack, how to use it, recent activity, docs links and related repos.
  3. Employees should see each repo's owners (team and people) and be able to contact them with an intent: "I want to use this", "I want to contribute", or a question.
  4. The catalog should stay in sync with GitHub: new, renamed, transferred, archived and deleted repos, and changes to READMEs and ownership files, appear within minutes.

Below the line: full-text code search across every file (integrate GitHub code search or Sourcegraph rather than rebuilding it), per-user repository authorization (designed for now, added later in deep dive 7), a "chat with this repo" assistant, and dependency graphs between services.

Non-Functional Requirements

  1. Scale: 20K employees, 50K repos across several GitHub orgs (about 15K active), growing 20% a year.
  2. Latency: search p95 under ~800 ms including natural-language parsing; repo pages under ~300 ms.
  3. Freshness: metadata changes (new, renamed, archived, deleted) searchable within 2 minutes at p95; regenerated AI summaries within 15 minutes of a README or manifest change; a departed employee removed from owner cards within an hour.
  4. Availability: 99.9% for search and repo pages; reads keep working, with a staleness banner, when GitHub or the model provider is down.
  5. Access: every employee, from the office, home or a hotel, through company SSO, with no VPN requirement. Nobody outside the company.
  6. Cost and limits: stay well inside GitHub API rate limits, including during the initial backfill and org-wide change storms.

Back-of-the-envelope

Say this out loud: "Read QPS is tiny and the index fits on one machine. I won't spend time sharding search. The hard parts are keeping a derived copy of GitHub correct, getting ownership right, and making badly documented repos findable." Interviewers reward candidates who notice that the scaling problem here is correctness and freshness, not throughput.

The Set Up

Core Entities

  • Repo: keyed by GitHub's numeric repository ID (stable across renames and transfers), plus org, name, description, topics, visibility, archived flag, default branch, languages, last push time, custom properties, and the content hashes of the files we index.
  • Repo profile: the AI-generated card: one-line purpose, summary, tech stack, how to use it, inferred status, plus the hashes, model and prompt version it was generated from.
  • Ownership claim: (repo, principal, source, confidence, last verified). A repo has several claims from different sources; a resolver picks what to show.
  • Person and Team: employee ID, GitHub login, email, Slack ID, manager, active flag; team with members and a Slack channel. Synced from the identity provider and HR system, not from GitHub alone.
  • Contact request: requester, repo, intent, message, routed-to, status, response time.

Key everything by the repository's numeric ID, never by org/name. Repos get renamed and transferred between orgs all the time; a name-keyed catalog ends up with duplicates, broken links and owner data attached to the wrong repo.

API

Returning parsed is a deliberate product choice: the UI shows the filters the model inferred as editable chips ("Language: Python ×", "Team: Payments ×"), so a wrong guess is visible and one click away from being fixed.

High-Level Design

1) Getting the data out of GitHub

The catalog authenticates as a GitHub App installed on each org with read-only permissions (metadata, contents, members). A backfill crawler lists every repo the installation can see and fetches, for each one: metadata, topics, languages, the README, CODEOWNERS, an optional catalog-info.yaml, dependency manifests (package.json, go.mod, pyproject.toml…), the top-level directory tree, and the authors of recent commits. It writes all of it to the Catalog DB (Postgres), which is the system of record for everything the portal shows. Deep dive 1 covers why an App and not a service-account token.

2) Keeping the catalog in sync

  1. The App subscribes to webhooks. The webhook receiver verifies the X-Hub-Signature-256 HMAC, records the X-GitHub-Delivery ID, puts the event on a queue and returns 2xx immediately. GitHub treats a delivery as failed if you don't respond within 10 seconds, so the receiver does nothing slow.
  2. Sync workers treat each event as a hint that a repo changed. They re-fetch that repo's current state from GitHub and upsert it, instead of applying the event payload. Deep dive 2 explains why that one decision removes most ordering bugs.
  3. A reconciler sweeps all repos on a schedule using conditional requests, catching anything the webhooks missed.

3) Enriching repos with AI

When a sync changes the hash of a file we care about, the repo goes on an enrichment queue. An enrichment worker builds a compact input (README truncated to a few thousand tokens, the directory tree, manifests, the description and topics, a few representative source files for repos with no README) and asks an LLM for a structured profile:

RepoProfile {
  purpose: string,       // "Sends SMS and push notifications via Twilio"
  summary: string,       // 3–5 sentences for someone outside the team
  kind: service | library | cli | infra | pipeline | docs | experiment,
  stack: string[],       // ["Go", "gRPC", "Postgres", "Twilio"]
  how_to_use: string,    // install / call / deploy, if the repo says
  status_hint: active | maintenance | deprecated | unknown,
  keywords: string[]     // what people will type: "texts", "OTP", "notify"
}

The worker then embeds the profile and the README chunks and writes the vectors next to the repo. Profiles are keyed by (repoId, inputHash, promptVersion, model), so an unchanged repo is never summarized twice and a prompt change regenerates everything predictably.

4) Searching in natural language

  1. A query parser (a small, fast model with structured output) splits the question into filters and a semantic query. "python services the payments team touched this year" becomes { language: "Python", kind: "service", team: "payments", pushedAfter: "2026-01-01", text: "payments services" }. In parallel, the raw query is embedded.
  2. The search index runs a hybrid query with the filters applied: BM25 over name, description, topics, profile and README; vector search over profile and chunk embeddings. Results are merged with reciprocal rank fusion.
  3. A reranker scores the top ~50 using the query plus signals: activity, archived or deprecated penalties, whether the repo has a verified owner, how many other repos depend on it.
  4. The API hydrates owners and profiles from the catalog cache and returns results with a one-line "why this matched".

5) Showing owners

An ownership resolver combines several sources (explicit catalog file, a required org property, CODEOWNERS, GitHub team permissions, commit history) into a ranked owner list with a source and confidence for each entry, then joins GitHub logins to the people directory to get names, Slack IDs, managers and whether the person still works here. Deep dive 5 covers the precedence rules.

6) Contacting owners

The contact service takes an intent and a message, routes it to the owning team's Slack channel (or a direct message to the primary owner if the team has no channel), threads replies back, and escalates to the next owner if nobody responds within a set time. An LLM can draft the message from the requester's search and the repo profile ("I'm building X and want to use your SMS client; is the gRPC API stable?"), which the requester edits before sending.

7) Access for everyone, remote or on site

The web app and API sit behind an identity-aware proxy that authenticates every request against the company IdP (OIDC/SAML SSO). Access depends on who you are, not which network you're on, so remote and office employees get the same experience with no VPN. The same API backs a Slack bot ("/repo sms gateway") and an MCP server, so coding agents can find internal libraries before writing new ones.

Potential Deep Dives

1) How should the service authenticate to GitHub?

Bad Solution
An engineer's personal access token

Challenges: the catalog sees whatever that person can see (often too much), its API calls share their personal rate limit, and the integration breaks the day they change teams or leave. Audit logs attribute every call to a human who didn't make it.

Good Solution
A dedicated machine user (service account) with a fine-grained token

Approach: create a bot user, add it to the orgs with read access, give it a fine-grained token scoped to read-only permissions, store the token in a secrets manager.

Challenges: it consumes a paid seat, the token is long-lived (a leak is valuable to an attacker), rotation is manual, the rate limit is a single user's, and webhooks have to be configured separately on every org.

Great Solution
A GitHub App with least-privilege permissions

Approach: register an App with read-only Metadata, Contents and Members permissions and install it on each org. The service holds the App's private key in a KMS or secrets manager, signs a short JWT, and exchanges it for an installation access token that expires after one hour; a token cache refreshes it a few minutes early. Webhook subscriptions come with the App, so one configuration covers every installed org. Installation tokens get their own rate limit (5,000 requests/hour minimum, up to 12,500 as the org grows, 15,000 on GitHub Enterprise Cloud; see REST rate limits), and calls are attributed to the App in audit logs. The same model works for GitHub Enterprise Server, with one App per instance.

Challenges: the private key is now the crown jewel: keep it in a KMS, never on disk, rotate it on a schedule, and alert on token creation from unexpected hosts. Org admins must approve installation and every permission increase, which is a feature.

2) How do we keep the catalog in sync without missing or misapplying changes?

Bad Solution
Poll every repo every few minutes

Challenges: 50K repos × ~5 calls each every 5 minutes is 3M calls an hour, hundreds of times the rate limit. Even polling once a day, the backfill-sized load lands on GitHub every day and freshness is a day.

Good Solution
Webhooks that apply payloads directly

Approach: on a repository event with action renamed, update the name; on a push, read the changed files from the payload and update them.

Challenges: GitHub does not automatically redeliver failed webhook deliveries; a receiver outage silently loses events. Events can arrive out of order (a "renamed" can be processed after a later "edited"), duplicates happen (manual or API redeliveries), and payloads can be partial or capped at 25 MB. Applying payloads makes your catalog drift from GitHub in ways nobody notices.

Great Solution
Events as invalidation hints, fetch-latest workers, and a reconciler

Approach:

  • Fetch, don't apply. An event only means "repo 12345 changed". The worker re-reads that repo's current state from GitHub and upserts it. Order no longer matters: whichever worker runs last writes the latest truth. Writes are conditional on GitHub's pushed_at/updated_at being newer than what's stored, so a slow worker can't overwrite fresh data with stale data.
  • Dedupe and debounce. Drop deliveries whose X-GitHub-Delivery ID you've already processed (redeliveries keep the same ID). Coalesce events per repo over a short window (say 30 s), so 40 pushes during a merge train become one sync.
  • Filter early. For push events, ignore non-default branches and check the commits' added/modified/removed file lists; only pushes that touch watched files trigger a content fetch. That cuts content fetches by roughly 20×.
  • Reconcile. A nightly job lists every repo and re-checks it with conditional requests (ETags). A 304 Not Modified doesn't count against the primary rate limit when the request is authorized (GitHub best practices), so the sweep is cheap. It also lists failed deliveries and redelivers them through the API (possible for the past 3 days, per handling failed deliveries). Alert when the reconciler finds many changes the webhooks missed.
  • Rate budget. All GitHub calls go through one client with a token bucket per installation and three priorities: webhook syncs, then reconciliation, then backfill. When an org-wide bot opens 5,000 dependency bumps in ten minutes, backfill pauses and freshness for humans is protected.

Challenges: deleted and transferred repos can't be "fetched": a 404 means deleted, made private to the App, or moved to an org without the installation. Tombstone the repo, hide it from search, and keep its ownership history for a while in case it reappears under the same ID.

3) What do we cache, and how do we invalidate it?

There are many caches here, and the trick is that most of them shouldn't need invalidation at all. Use three strategies and pick per layer: content-addressed keys (the key changes when the input changes, so stale entries are simply never read), TTLs shorter than the freshness SLO (staleness is bounded and acceptable), and explicit invalidation only where staleness is harmful.

CacheKeyInvalidationWhy
AI repo profilerepoId + hash of inputs + prompt version + modelNone: content-addressedThe most expensive thing to compute; recomputed only when an input really changes
Query embeddingnormalized query + embedding model versionNone; LRU evictionSame text always embeds the same
Query parse (LLM)normalized query + parser prompt version + dateTTL 24 h"this year" and "last month" depend on today's date
Search resultsquery + filters + pageTTL 60 sYou can't know which queries a repo change affects; a 60 s TTL sits inside the 2-minute SLO
Repo card / page (Redis)repo:{id}, value carries the catalog versionDelete on change via the outbox, plus 10-minute TTL as a safety netRename, archive and owner changes should show up right away
People directoryperson:{id}Deprovision event deletes immediately; TTL 1 h otherwiseA departed owner on a card sends requests into a void
GitHub responsesURL + ETagConditional request on every read304s are free against the rate limit
Search index itselfrepoId documentOutbox → indexer upsert; full rebuild behind an alias swapThe index is a cache of Postgres, not a second source of truth

Two details interviewers like to probe:

  • Keeping Postgres and the index consistent. Don't write to Postgres and then to the search index from the same worker; if the second write fails, they diverge forever. Use a transactional outbox: the catalog update and an outbox row commit in one transaction, and an indexer tails the outbox (or the database's change stream) to upsert the search document and delete the Redis key. Redelivery is safe because upserts are idempotent and carry the catalog version.
  • The stale-set race. Request A reads repo 12345 (old version) from a replica; the indexer then updates the row and deletes the cache key; request A writes the old value back into the cache. Now the stale value lives until TTL. Fix it by storing the catalog version in the cached value and only writing when it's newer (a small compare-and-set script in Redis), or by populating the cache only from the primary after invalidation. The 10-minute TTL bounds the damage if anything slips through.

When the schema, the embedding model or the chunking changes, don't update the live index in place. Build a new index in the background from Postgres, run the search eval set against it, then flip the alias. Rollback is flipping it back.

Saying "we'll invalidate the search cache when a repo changes" is a trap: one repo change can affect the results of thousands of different queries, and you can't enumerate them. A short TTL that fits inside the freshness SLO is the honest answer, and it's cheap because search traffic is tiny.

4) How do we make natural-language search actually find the right repo?

Bad Solution
Keyword search over names and descriptions

Challenges: "something that sends text messages" doesn't match notify-gateway, whose description is empty and whose README says "Twilio wrapper". Keyword search only works for people who already know the name, which are exactly the people who don't need the portal.

Good Solution
Embed READMEs and do vector search

Approach: chunk each README, embed the chunks, return repos whose chunks are nearest to the query embedding.

Challenges: many repos have no README or a template one, so they're invisible. Filters in the question ("Python", "owned by payments", "still maintained") get blurred into the embedding instead of applied. Exact names and acronyms ("PCI", "OTP") match poorly. Archived prototypes with nice READMEs outrank the maintained production service.

Great Solution
Write-time enrichment, structured query parsing, hybrid retrieval and signal-aware reranking

Approach:

  • Enrich at write time. The LLM profile gives every repo a purpose, a summary and synonyms, even when the README is empty, by reading the tree, manifests and a few source files. This is the single biggest quality win and costs a few hundred dollars once.
  • Parse the query. A small model turns the question into filters plus search text with a strict JSON schema; the filter values are validated against known teams, languages and statuses, and anything unrecognized is dropped back into the text. Skip the model entirely for short queries that exactly match a repo name.
  • Hybrid retrieval. BM25 for exact names, acronyms and error strings; vectors for paraphrases; merge with reciprocal rank fusion (see Vector Search and RAG Deep Dive).
  • Rerank with signals. A cross-encoder (or a small LLM) scores query–profile relevance; a simple ranker combines it with activity, archived and deprecated penalties, verified ownership, number of dependents and an "officially supported" flag from the platform team. Collapse forks and template copies into their source.
  • Explain. Show the inferred filters as chips and a one-line reason per result, generated from the matched fields, not by a model at query time.

Challenges: LLM profiles can be confidently wrong about what a repo does. Generate them only from repo content, show "AI-generated from README and code" on the card with a link to the source, let owners edit or pin their own description (which then wins), and spot-check faithfulness with a judge against the inputs.

5) Who owns this repo?

Bad Solution
Show the top committers

Challenges: the top committer is often a dependency bot, someone who left, or the intern who wrote it three years ago. Activity is evidence about who knows the code, not who is responsible for it.

Good Solution
Parse CODEOWNERS

Approach: read CODEOWNERS (GitHub looks in .github/, the root, then docs/, and uses the first one it finds) and take the owners of the catch-all pattern.

Challenges: many repos don't have one, CODEOWNERS describes who reviews which paths rather than who owns the service, and it lists GitHub handles and teams that may no longer exist.

Great Solution
Layered sources with precedence, a people-directory join, and ownership health

Approach: collect claims from every source and resolve them in a fixed order:

  1. Explicit catalog file (catalog-info.yaml, the Backstage descriptor format) with an owner team and lifecycle.
  2. An org custom property such as owning-team, which org admins can make required for all repositories, so every new repo has an owner from day one (custom properties).
  3. Owner override set in the portal, audit-logged.
  4. CODEOWNERS catch-all owners.
  5. GitHub teams with admin or maintain permission on the repo.
  6. Inferred from recent human commit and review activity, excluding bots, shown separately as "people who know this code".

Join every GitHub login to the people directory, which syncs from the IdP (SCIM) and the HR system: GitHub alone doesn't know someone's real name, manager or that they left yesterday. If a person is inactive, fall back to their team, then to the team's manager. Each owner on the card shows its source ("from catalog-info.yaml", "inferred from commits") and when it was last verified. Track ownership coverage (repos with an active, explicit owner) per org, send orphaned active repos to a triage queue, and ask owners to re-confirm once a quarter with one click in Slack.

Challenges: mapping GitHub logins to employees is the weak link when people use personal GitHub accounts. With SAML SSO on the org, linked identities give you the mapping; with Enterprise Managed Users, accounts come from the IdP directly. Without either, fall back to commit email matching and accept gaps.

Don't ask an LLM who owns a repo. It will produce a confident, plausible name. Ownership is a fact that comes from configuration and the directory; the model's job is to describe the code, not to assign responsibility for it.

6) How do we route contact requests so owners don't drown?

  • Team first: send to the owning team's channel rather than DMing the most visible engineer, so the load spreads and requests survive vacations. Fall back to the primary owner, then the manager.
  • Structured intents: "use", "contribute" and "question" render differently and can link to the repo's CONTRIBUTING file or support channel automatically; repos can declare "not accepting contributions" or "deprecated, use X instead", which the portal shows before a message is sent.
  • Dedupe and rate-limit: similar questions about the same repo within a day are grouped; each requester has a daily cap.
  • Escalation and metrics: no reply in two business days moves the request to the next owner. Median response time per team is an ownership-health signal on the repo page.
  • Delivery reliability: requests are stored first, then delivered by a worker with retries and idempotency keys, so a Slack outage delays messages instead of losing them.

7) How do we add authorization later without a rewrite?

Version one shows every employee the catalog of repos the App can see. Decide the policy explicitly: index only repos with internal or org-wide visibility, and let teams exclude sensitive repos (security tooling, acquisitions) with a discoverable=false property. To add per-user permissions later without a rewrite, build three things in now:

  • ACL on every document. Store the repo's visibility and the list of teams with read access on the search document from day one, even if nothing filters on it yet. The team and membership webhooks already keep it fresh.
  • Pre-filter, never post-filter. At query time, add a filter for the user's team IDs (resolved at login from their linked GitHub identity) to the search query itself. Filtering after retrieval breaks pagination, leaks counts ("3 hidden results") and can return empty pages.
  • Permission-aware caches. Once results depend on who's asking, a shared search-results cache leaks data. Add an ACL fingerprint (a hash of the user's sorted team IDs) to the result-cache key; per-repo cards stay shared but are only served after an access check.

More on permission-aware retrieval in Guardrails & Security.

9) How do we know search is working?

  • Golden set: a few hundred real queries (from Slack "does anyone know a repo that…" threads and search logs) with the repos that should rank first, labeled by the owning teams. Track recall@5 and MRR; rerun on every change to prompts, models, ranking or chunking (see Evaluation).
  • Online: zero-result rate, query reformulation rate, click-through on the top 3, and the strongest success signal for this product: a contact request or a clone after a search.
  • Profile quality: owners can flag a wrong summary in one click; sample profiles weekly for an LLM judge to check every claim against the README and code it was generated from.
  • Freshness: time from GitHub event to searchable (p50, p95), webhook-miss rate found by the reconciler, and ownership coverage per org.

What is Expected at Each Level?

Mid-level

A catalog DB filled by a crawler, webhooks for updates, embeddings plus keyword search, a repo page with CODEOWNERS-based owners, SSO in front, and a Slack contact button. Notices that READMEs are often empty.

Senior

GitHub App over service accounts with rate-limit math; webhooks as hints with fetch-latest, dedupe, debounce and a reconciler; LLM enrichment on the write path with content-addressed profiles; query parsing into validated filters, hybrid retrieval and reranking; per-layer cache strategy including the outbox and the stale-set race; layered ownership joined to the directory.

Staff+

Frames ownership coverage and search success (contact after search) as the metrics that matter and designs the org process around them: required custom properties, owner re-verification, orphan triage. Designs ACLs, permission-aware caches and pre-filtering in from day one so authorization is an add-on, plans index rebuilds behind alias swaps with eval gates, and exposes the catalog to agents through MCP so the next "rebuild it from scratch" is caught by a tool, not a person.

Gateways, Routing & Reliability

The layer between your applications and the models they call: token-based rate limits and quotas, model routing, retries, circuit breakers and failover across providers, load shedding, and how to set SLOs for features whose most important dependency you don't control.

An LLM feature depends on a model endpoint that is slow (seconds per call), variable (the same request can take 2 or 20 seconds), metered (every call costs money), shared (your rate limits are per organization, not per service) and, at times, unavailable. Provider status pages show incidents regularly, and during demand spikes even healthy providers return rate-limit (429) and overloaded (503, or 529 on Anthropic's API) errors. If each team calls providers directly, every team reinvents retries, nobody knows who spent what, and an outage takes every AI feature down at once.

The standard answer is an LLM gateway (also called an AI gateway): a proxy that every model call goes through. This page covers what goes in it and the reliability techniques behind it. For the full interview walkthrough of building one, see the LLM Gateway worked example; this page is the concepts toolbox you'd draw on there and in any other design.

Build vs buy

Most teams start with an existing gateway and extend it. Know the landscape well enough to name a couple and say what they're for; feature sets change quickly, so check current docs before relying on a specific capability.

Open source proxy

LiteLLM

Python SDK and proxy server exposing an OpenAI-compatible API over many providers, with virtual keys, budgets, rate limits, fallbacks and spend tracking. A common self-hosted default.

Gateway + platform

Gateway with configurable routing (fallbacks, load balancing, conditional routing), caching, guardrails and observability; open-source gateway core plus a hosted platform.

Hosted proxy at Cloudflare's edge with caching, rate limiting, analytics, logging and dynamic routing with fallbacks.

Kubernetes-native

Envoy AI Gateway

Open-source project built on Envoy Proxy and Envoy Gateway: unified access to providers, upstream auth, and token-based rate limiting, configured as Kubernetes resources.

Hosted router

OpenRouter

A hosted service with one API and one bill across many model providers, with provider routing and fallbacks. You trade control and data-path ownership for convenience.

Build your own (or fork) when you need tight integration with internal auth and billing, custom routing logic, strict data-residency guarantees, or extreme throughput where an extra hop's overhead matters. Even then, keep the gateway thin: a slow or unavailable gateway is now a single point of failure for every AI feature, so run it stateless, replicated across zones, with state in Redis and config in a versioned store.

Token-based rate limiting

Limiting requests per minute is nearly meaningless for LLMs: one request can be 200 tokens, another 200,000. Providers limit you on several dimensions at once, typically requests per minute, input tokens per minute and output tokens per minute, and your gateway should do the same for its clients, plus concurrency (in-flight requests) and spend (dollars per day or month).

Token bucket, counted in tokens

A token bucket holds up to capacity units and refills at a steady rate. Each request withdraws its cost; if there isn't enough, it's rejected (or queued). For LLMs the unit is model tokens, so a 50K-token request withdraws 50K. Buckets allow short bursts up to capacity while enforcing the long-run rate.

The output problem: reserve, then reconcile

You know input tokens before the call (count them with the tokenizer or the provider's token-counting endpoint), but output tokens only after it finishes. Charging nothing up front lets one client launch 500 parallel long generations and blow through the limit; charging after the fact makes limits unenforceable. The standard pattern:

  1. Estimate cost = input tokens + max_tokens (conservative), or input + the p95 output length for this route (tighter, occasionally overruns).
  2. Reserve that amount atomically. If the bucket is short, reject with 429 and a Retry-After computed from the refill rate.
  3. Forward and stream.
  4. Reconcile when the call ends (including on cancel or error): refund reserved − actual, or debit the overrun.

Mirror the provider's own accounting where it matters: Anthropic, for example, doesn't count cache-read tokens toward its input-token limit, so a bucket that counts them will throttle earlier than the provider does (Claude rate limits).

-- reserve.lua: atomic token-bucket reservation in Redis
-- KEYS[1] = bucket key, e.g. "tpm:{tenant}:{key}"
-- ARGV = capacity, refill_per_sec, now_ms, cost
local cap, rate, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + math.max(0, now - ts) / 1000 * rate)   -- refill
if cost > cap then return {-1, 0} end                                  -- can never fit: 413 / lower max_tokens
if tokens < cost then
  redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
  return {0, math.ceil((cost - tokens) / rate)}                         -- reject, Retry-After seconds
end
redis.call('HSET', KEYS[1], 'tokens', tokens - cost, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) + 60000)
return {1, 0}                                                           -- reserved

-- reconcile.lua: refund (delta > 0) or charge an overrun (delta < 0); may go negative briefly
-- tokens = min(cap, tokens + (reserved - actual))

Running the check and debit in one Lua script avoids the race where two gateway instances both read "enough tokens" and both proceed. At very high request rates, shard buckets by key and keep hot keys' buckets local with periodic sync, accepting slight over-admission.

Concurrency limits

Token rates don't stop a client from holding 1,000 streams open for minutes each, which ties up your provider concurrency and, on self-hosted models, GPU KV memory. Add an in-flight limit per key: a counter (or Redis sorted set of request IDs with lease timestamps) incremented on start and decremented on completion, with leases that expire so crashed requests don't leak slots forever.

Hierarchical quotas and priority

  • Hierarchy: the organization's provider limit is divided into team budgets, team budgets into keys, and keys optionally into end users. A request must fit at every level. Unused budget can be lent (borrowable quotas) with the owner able to reclaim it.
  • Priority tiers: when the shared upstream limit is tight, interactive traffic should be admitted before batch jobs, and paid before free. Implement with separate buckets per tier and a scheduler that drains higher tiers first, or weighted fair queuing so low tiers still make progress.
  • Adapt to the upstream: the gateway also has to stay inside your provider limits. Read the provider's rate-limit headers (remaining tokens and reset times), and when 429s appear, reduce concurrency multiplicatively and increase it additively when they stop (AIMD, like TCP congestion control).

Model routing

Routing decides which model and which provider serve each request. It's the biggest cost lever after caching, and the riskiest for quality, so every routing change should go through an eval gate (see Evaluation).

StrategyHow it decidesStrengthWeakness
Static rulesBy feature/route, tenant plan, input length (long inputs → long-context model), language, data residencyPredictable, easy to auditCoarse; leaves savings on the table
Classifier routerA small model or classifier predicts difficulty or task typePer-request choice at low costNeeds labeled data; misroutes hard requests to weak models
CascadeTry the cheap model; validate (schema, confidence, verifier); escalate on failureCheap model handles most traffic; quality floor from the validatorEscalated requests pay twice and take longer
Learned routerTrained on preference data to predict when the strong model's answer is meaningfully betterBest cost/quality frontier when trained on your trafficTraining data, drift, harder to explain
Latency/cost-awareChoose among equivalent deployments by current latency, error rate and priceAbsorbs regional slowdownsRequires equivalence; can oscillate without damping

RouteLLM is the standard reference for learned routing: routers trained on human preference data reduced cost by more than 2× without substantially compromising quality on benchmarks like MT Bench (Ong et al., 2024); the LMSYS team reported cost reductions of up to 85% on MT Bench while keeping 95% of GPT-4's quality (RouteLLM repo). Treat such numbers as benchmark-specific; your traffic decides your savings.

New models enter through shadow traffic (send a copy of real requests, compare offline, don't show users) and then a canary (a small percentage of real traffic, watching quality, latency and cost) before the routing table changes.

Prompt portability

Failover to another provider is only real if the request works there. Models differ in tool-call formats, structured-output support, context limits, tokenizers (the same text is a different number of tokens), system-prompt handling and refusal behavior. Make portability concrete:

  • Keep a canonical internal request format and per-provider adapters in the gateway.
  • Maintain per-model prompt variants where needed, versioned together.
  • Run each route's eval suite against every model in its fallback chain, on every prompt change, so you know the fallback's quality before the outage, not during it.

Handling failures

Classify errors first

Retries with backoff, jitter and budgets

  • Exponential backoff with full jitter: wait a random time between 0 and min(cap, base × 2attempt). Jitter prevents synchronized retry waves from many clients (AWS Architecture Blog: Exponential Backoff and Jitter).
  • Retry budgets: cap retries at a fraction of traffic (for example, retries may add at most 10% to request volume over a minute). Without a budget, an overloaded provider receives 3× the traffic exactly when it can least handle it.
  • Retry at one layer only. If the SDK, the gateway and the app each make up to three attempts, one failure becomes 27 calls.
  • Never retry a stream after tokens reached the user; mark the message incomplete instead (see API Design & Streaming). The gateway can retry transparently only before the first byte is forwarded.

Timeouts for streaming calls

A single total timeout doesn't work for LLMs: a legitimate long answer takes 60 seconds, while a stuck connection also takes 60 seconds. Use separate timeouts:

connect timeout          2 s     // can't reach the provider
time-to-first-token     10 s     // chat; much longer for reasoning models that think before emitting
inter-token (idle)      15–30 s  // stream stalled mid-answer
total                   by route // e.g. 120 s chat, 15 min agent step, none for batch

Set them per route and per model from observed latency distributions (p99.9 plus margin), not globally.

Circuit breakers

A circuit breaker per (provider, model, region) stops sending traffic to a failing backend. When its error rate (or p99 latency) over a rolling window crosses a threshold, it opens: requests fail fast and go straight to the fallback, so users don't each wait out a timeout. After a cooldown it goes half-open and lets a few probe requests through; success closes it, failure reopens it. Breakers also protect the provider: a struggling backend gets breathing room instead of a retry storm.

Fallback chains

A typical chain, from least to most degraded:

  1. Same model, another region or cloud. Many frontier models are served by the model maker and by major clouds (for example, Claude via Anthropic's API, Amazon Bedrock, Google Cloud and Microsoft Foundry). Same weights, so the same prompts and quality.
  2. Equivalent model from another provider. Needs portable prompts and a tested eval score.
  3. Smaller or self-hosted model. Lower quality; only for routes where that's acceptable.
  4. Cached or canned response. A semantic-cache hit, a "we're busy" message with a retry button, or a non-AI fallback path (show search results instead of a generated answer).

Log every fallback with the reason, and alert when fallback traffic exceeds a threshold: a silent fallback to a weaker model is a quality incident even if availability looks perfect.

Hedged requests

For tail latency, send a second, duplicate request if the first hasn't responded by roughly its p95 latency, and use whichever answers first, cancelling the other. In Google's measurements, hedging after 10 ms cut the 99.9th-percentile latency of a Bigtable benchmark from 1,800 ms to 74 ms while adding only about 2% more requests (Dean & Barroso, The Tail at Scale). For LLMs, hedging is expensive, because each duplicate pays for prefill and decode, so reserve it for short, cheap, latency-critical calls (classification, routing, guardrail checks, embeddings) and cancel losers immediately.

Load shedding and graceful degradation

When demand exceeds capacity, whether your own GPUs or your provider allowance, something has to give. Decide what in advance:

  • Admission control: reject early (fast 429/503 with Retry-After) when queue depth or, for self-hosted models, KV-cache utilization crosses a threshold. A fast rejection beats a 90-second timeout.
  • Shed by priority: batch and free-tier traffic first, then lower-value features, protecting the core interactive path.
  • Degrade instead of failing: lower max_tokens, reduce reasoning effort, disable expensive tools (web search), retrieve fewer chunks, or route to a smaller model with a banner. Each degradation is a feature flag you can flip during an incident.
  • Queue with honesty: for non-interactive work, accept into a durable queue and show an estimated completion time.

Capacity: on-demand vs provisioned

On-demand API capacity is shared, so it's subject to rate limits and overload errors when the provider is busy. Major providers and clouds also sell provisioned or reserved throughput (dedicated capacity at a fixed price per unit of time), and some offer priority tiers. The decision is a utilization calculation:

reserved cost per hour  = R
on-demand cost per hour at the same peak throughput = D   (if fully used)
break-even utilization  = R / D

if R / D = 0.6: reserve capacity for the baseline you're confident runs above 60% utilization,
                and spill bursts over to on-demand (with fallbacks for 429s)

Reserved capacity also buys predictability: guaranteed throughput and steadier latency for your most important route. A common pattern is reserved capacity for the interactive baseline, on-demand for bursts, and the batch API for offline work.

SLOs and error budgets for LLM features

Define service-level indicators that match what users feel, including quality, since an LLM feature can be "up" and still wrong:

SLIExample SLO
Availability: completed responses ÷ attempts (excluding client errors)99.9% monthly
Time to first token, p95< 1.5 s for chat
Inter-token latency, p95< 80 ms (≈ 12+ tokens/s, faster than reading)
End-to-end latency, p95, for synchronous calls< 3 s for classification
Quality: sampled LLM-judge pass rate, schema-valid rate, refusal rate≥ 95% pass on sampled traffic; < 1% invalid JSON
Fallback rate< 2% of requests served by a fallback model

A 99.9% monthly availability SLO allows about 43 minutes of failure per 30 days. If your single provider's track record is worse than your target, no amount of retrying fixes it; you need a second independent path. Two providers each available 99.5% of the time give 1 − 0.005² ≈ 99.997% combined, but only if failures are independent (they often share cloud regions or traffic surges), failover is fast, and the fallback is good enough to count as "available." Be honest about those caveats in an interview.

Security and governance at the gateway

  • Keys: provider keys in a secret manager, readable only by the gateway; teams get scoped, revocable virtual keys; block direct egress to provider APIs from application networks so the gateway can't be bypassed.
  • PII redaction: detect and mask personal data before it leaves your network when policy requires, and restore placeholders in responses where needed.
  • Data residency: route EU tenants to EU endpoints; enforce it in the router, not in app code.
  • Retention: log metadata always; log prompt and response bodies only where policy allows, with redaction and access controls.
  • Budgets: hard spend caps per key, alerts at 50/80/100%, and anomaly detection on sudden spend spikes (a leaked key or a runaway agent loop).

Gateways and Reliability in System Design Interviews

When to bring it up

  • Whenever the design calls an external model. "All model calls go through a gateway that handles keys, token quotas, retries and fallbacks, so the app code stays simple."
  • Multi-tenant products. "Rate limits are per tenant in tokens, with reserve-then-reconcile, because request counts don't reflect cost."
  • Availability requirements. "Our 99.9% target is higher than a single provider's history, so the chain is: same model in a second cloud, then an evaluated alternative model."
  • Cost questions. "The router sends easy requests to a small model, gated by evals."

How to introduce it

  1. Place the gateway in the high-level diagram between services and providers.
  2. State the limit dimensions (TPM, concurrency, spend) and the reserve-then-reconcile mechanism.
  3. Describe the routing policy and how new models are evaluated before routing to them.
  4. Walk through a failure: error classification, retry budget, breaker, fallback chain, user-visible behavior.
  5. Close with SLOs, including quality and fallback rate.

Common deep-dive questions

"Your primary model provider has a regional outage. What happens?"

Bad Solution
Retry until it works

Challenges: users wait for timeouts on every request; retries multiply load on a failing provider; nothing serves users for the length of the outage.

Good Solution
Retry with backoff, then fall back to another provider

Approach: on 5xx, retry twice with jittered backoff; if it still fails, send the request to a second provider's comparable model.

Challenges: every request still pays the retry delay before falling back; the fallback's prompt behavior and quality are unknown until the outage.

Great Solution
Breakers, a tested fallback chain, and honest degradation

Approach: per-(provider, model, region) circuit breakers open within seconds based on rolling error rates, so requests skip straight to the fallback with no added latency. The chain prefers the same model hosted in another cloud (same prompts, same quality), then an alternative model whose eval scores on this route are tracked continuously. Retries happen only at the gateway, under a retry budget, and never after tokens reach the user. Capacity for the fallback is pre-arranged (quota on the second provider is requested in advance). Dashboards show fallback rate and quality on fallback traffic; lower-priority features degrade or shed first.

Challenges: paying for idle fallback quota; keeping prompt variants and evals current for every model in the chain; cross-provider data agreements.

"Design token-based rate limiting for our public API."

Cover: dimensions (input TPM, output TPM, concurrency, daily spend) per key with tier-based limits; a Redis token bucket with an atomic Lua reserve; estimating output from max_tokens and reconciling on completion or cancel; 429 with Retry-After and rate-limit headers on every response; hierarchical limits (org → key); priority between interactive and batch; how you stay within your own upstream provider limits (AIMD on 429s); and what happens if Redis is unavailable (fail open with local per-instance limits for a short time, or fail closed for free tiers).

"Users complain that p99 latency is 40 seconds."

Break latency down first: queueing at the gateway, TTFT, decode time (output length), tool calls and retries. Typical fixes: per-route timeouts so stuck streams fail fast; breakers so a slow region is skipped; hedging for short calls; capping max_tokens and asking for concise output; routing long-input requests to deployments with prompt caching; and checking whether retries are compounding across layers.

Summary

  • Put every model call behind a gateway: one place for keys, quotas, routing, reliability, caching, policy and cost tracking.
  • Rate-limit in tokens and concurrency, not just requests; reserve input + max_tokens atomically and reconcile on completion.
  • Route by rules first, then cascades or learned routers, always behind eval gates; test every fallback model before you need it.
  • Classify errors; retry only transient ones, with jittered backoff, a retry budget and at one layer; never after tokens are shown.
  • Use separate connect, TTFT, idle and total timeouts; circuit breakers per provider, model and region; hedging only for cheap calls.
  • Plan load shedding and degradation in advance, and set SLOs that include quality and fallback rate, not just uptime.

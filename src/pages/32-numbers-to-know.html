Numbers to Know

The reference figures and formulas behind capacity, latency and cost estimates for LLM systems, followed by five fully worked estimates you can adapt in an interview.

Classic system design has its "latency numbers every programmer should know." LLM systems add a new set: tokens per word, KV bytes per token, GPU bandwidth, dollars per million tokens. Interviewers rarely care whether you remember an exact figure; they care whether you can turn a product requirement into tokens per second, then into GPUs or dollars, and spot which number drives the design.

Prices and hardware specs move fast. Figures here are rounded and were checked in November 2026. Hardware specs come from vendor datasheets; API prices are given as bands. Quote orders of magnitude in interviews, and check the official pricing pages before using a number for a real budget.

Throughput and cost

Formulas

API cost per request = in_tokens × in_price + out_tokens × out_price
                     − cached_in_tokens × in_price × (1 − cache_read_multiplier)

decode throughput (per replica) ≈ batch × 1 ÷ step_time
step_time ≈ (weight bytes + KV bytes read) ÷ HBM bandwidth     // lower bound
prefill time ≈ 2 × params × prompt_tokens ÷ (FLOP/s × MFU)      // MFU ~40–60%

self-hosted $ per 1M output tokens = (GPUs × $/GPU-hour) ÷ (tokens/s × 3,600) × 10^6 ÷ utilization

Example: one 8×H100 node at $3 per GPU-hour costs $24/hour. If it sustains 5,000 output tok/s at your latency SLO, that's 18M tokens/hour, or $1.33 per 1M output tokens at 100% utilization, and $3.33 at a more realistic 40% average utilization. GPU rental prices vary widely by provider, commitment and generation, so treat $/GPU-hour as an input to state, not a constant.

The estimation method

  1. Start from users and actions, not requests: DAU × actions per user per day.
  2. Convert to requests/s (÷ 86,400) and apply a peak factor.
  3. Convert to tokens/s, separately for input and output, and note how much input is cacheable.
  4. Split by phase: input tokens drive prefill compute (or API input cost); output tokens drive decode time, KV residency and output cost.
  5. Turn into GPUs or dollars, add headroom (N+1 replicas, 30–50% for spikes), then sanity-check against something you know.

Say your assumptions out loud and round aggressively (2,000 not 1,873). The interviewer is grading whether the number changes a decision: "that's $3M a month on the frontier API, so routing 70% of turns to a small model is worth the complexity."

Worked estimates

1) GPUs for a 1M-DAU chat product on a self-hosted 70B model

Traffic:   1M DAU × 10 messages/day = 10M requests/day ≈ 116 req/s, peak ×3 ≈ 350 req/s
Tokens:    input 2,000 (history; ~50% prefix-cached), output 400
Decode:    350 × 400 = 140K output tok/s at peak
           realistic node (8×H100, FP16, TPOT ≤ 30 ms) ≈ 5,000 output tok/s
           → 140K ÷ 5K ≈ 28 nodes
Prefill:   350 × 2,000 × 50% uncached = 350K tok/s
           2 × 70e9 × 350e3 ≈ 4.9e16 FLOP/s ÷ (8 × 989e12 × 0.5 ≈ 4e15 per node) ≈ 12 nodes of compute
           decode leaves most compute idle, so chunked prefill absorbs much of this on the same nodes
KV check:  concurrent streams ≈ 350 req/s × (400 ÷ 30 tok/s ≈ 13 s) ≈ 4,700
           per node ≈ 4,700 ÷ 30 ≈ 160 streams × ~2.4K tokens ≈ 380K tokens ≪ 1.3M capacity ✓
Answer:    ~30–40 nodes at peak + headroom ≈ 40–45 nodes (320–360 H100s)
Cost:      40 × 8 × $3 ≈ $960/hour at peak; autoscaled average ~half ≈ $350K/month

Sanity check against an API: 10M requests/day at a mid-tier price ($2 in, $10 out per million) is roughly $40K/day of uncached input (less with caching) plus $40K/day of output, around $2.4M/month. That gap is why high-volume products move some traffic to self-hosted or smaller models, though the comparison only holds if the open model meets the quality bar.

2) Monthly cost of a RAG support assistant on an API

Traffic:   50K conversations/day × 4 turns = 200K turns/day ≈ 6M turns/month
Per turn:  system prompt + tool definitions 3K (cached) + retrieved chunks 3K
           + history 1K + question 100 ≈ 7.1K input; 300 output
Price:     mid-tier $2/M in, $10/M out (Sonnet 5.5), cache reads 0.05×
Input:     3K × 0.05 + 4.1K = 4.25K effective × $2/M ≈ $0.0085
Output:    300 × $10/M ≈ $0.003
Extras:    query rewrite on a small model, embeddings, rerank ≈ $0.001
Per turn ≈ $0.0125 → per conversation ≈ $0.05 → ≈ $75K/month

Levers, in order of impact: cut retrieved context (better reranking, fewer chunks), route simple FAQ turns to a small model, shorten answers, raise the cached share of the prompt. See the support assistant breakdown.

3) Embedding and storing a 50M-document corpus

Corpus:    50M docs × 2,000 tokens = 100B tokens
Chunks:    500-token chunks, 10% overlap → ≈ 220M chunks
API cost:  100B × $0.02/M ≈ $2,000 (≈ $1,000 via batch)
Rate:      at 10M tokens/min of quota → 10,000 min ≈ 7 days   // quota, not dollars, is the constraint
Self-host: 2 × 335M params × 100e9 tokens ≈ 6.7e19 FLOPs
           ÷ (989e12 × 30% MFU ≈ 3e14) ≈ 2.2e5 s ≈ 62 H100-hours → a few hours on 16 GPUs
Storage:   220M × 1,024 × 4 B ≈ 900 GB float32; ≈ 225 GB int8; ≈ 28 GB binary
           + HNSW graph (~30–60 GB) + chunk text (~400 GB) + metadata

Decisions this drives: shard the index (or use a disk-based index with quantized vectors in RAM), keep full-precision vectors on disk for rescoring, and plan re-embedding (a model upgrade means paying all of this again). See Embeddings & Vector Search.

4) Cost of one coding-agent run

Run:       40 steps; context grows 10K → 80K (average 45K input per step); 500 output per step
Input:     40 × 45K = 1.8M tokens
  no caching:     1.8M × $2/M ≈ $3.60
  with caching:   ~90% of each step's input is a cache hit
                  1.8M × (0.9 × 0.05 + 0.1 × 1.25) ≈ 0.31M effective ≈ $0.61
Output:    40 × 500 = 20K × $10/M ≈ $0.20
Total ≈ $0.81 per run with caching vs ≈ $3.80 without; sandbox minutes are cents

Input dominates and grows roughly quadratically with step count because every step resends the history. That is why agents rely on prompt caching, tool-output truncation, compaction and sub-agents (Context Engineering, Design Claude Code).

5) Voice agent latency budget

Target: reply audio starts < ~1 s after the user stops talking (humans: ~200 ms gaps)

End-of-turn detection (VAD + endpointing)   200–500 ms   // the biggest, most tunable chunk
Final STT transcript                        100–300 ms   (overlaps with endpointing when streaming)
LLM time to first token                     300–700 ms   (small/fast model, short prompt, cached prefix)
First sentence of text (~15 tokens)          ~100–300 ms
TTS time to first audio                     100–250 ms
Network (client ↔ server, both ways)         50–150 ms
Total ≈ 0.9–2.2 s naive; ≈ 0.7–1.0 s with streaming at every stage and tight endpointing

Every stage must stream into the next. Speech-to-speech models collapse STT, LLM and TTS into one model and remove some of these hops. See Real-time Voice Agent.

Numbers in System Design Interviews

When to estimate

  • Right after non-functional requirements, when scale shapes the architecture: "Let me size this quickly, because whether we need a GPU fleet or an API budget changes the design."
  • When choosing between options: model tiers, self-host vs API, RAG vs long context.
  • When the interviewer pushes on cost or latency in a deep dive.

How to keep it fast

  1. Memorize a few anchors: 4 chars/token, 10^5 s/day, H100 = 80 GB and 3.35 TB/s, 70B FP16 = 140 GB, 320 KB KV/token for 70B, output ≈ 5× input price, cache reads ≈ 0.05–0.1×.
  2. Write the chain on the board (users → req/s → tokens/s → GPUs or $) so the interviewer can follow and correct assumptions.
  3. Compute only what decides something. If the answer is "fits on one node" or "costs $500/month," move on.
  4. Finish with the implication: "so prompt caching is mandatory," "so we need to shard the index," "so the small model handles the first pass."

Common mistakes

  • Counting requests instead of tokens (one agent request can be 100× a chat turn).
  • Forgetting that conversation history makes input grow every turn.
  • Sizing GPUs by compute when KV memory or bandwidth is the binding constraint.
  • Using sparse TFLOP/s figures from marketing material.
  • Ignoring rate limits and quotas, which often bind before budget does.

Summary

Convert everything to tokens, split input from output, and know the handful of hardware anchors that turn tokens into seconds and dollars. Then let the numbers drive decisions: caching, routing, sharding, self-hosting. For the mechanisms behind these figures read Inference & Serving; for where they show up in practice, see the worked examples.

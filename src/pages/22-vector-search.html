Embeddings & Vector Search

How text becomes vectors, how approximate nearest-neighbor indexes actually work, and how to size, filter, shard and migrate a vector index in a production design.

Almost every retrieval, memory, semantic-cache and recommendation feature in an LLM system ends in the same operation: "find the stored vectors closest to this one." In interviews that operation usually gets one box labeled "vector DB" and no further thought. That is where strong candidates separate themselves. The box hides a model choice, an index algorithm with tunable recall, a memory bill that can reach terabytes, a filtering problem that silently breaks multi-tenant apps, and a migration problem every time you change embedding models.

This page goes one level below the Core Concepts summary. By the end you should be able to explain how HNSW finds neighbors, size an index for 10 million or 1 billion vectors, pick a filtering and tenancy strategy, and describe how to swap embedding models without downtime. Retrieval pipelines built on top of this (chunking, hybrid fusion, reranking) are covered in RAG in Depth.

What embeddings are

An embedding model is a neural network (usually a transformer encoder) that maps an input (a query, a chunk of text, an image, a code snippet) to a fixed-length vector of floats. It is trained, typically with contrastive learning on query–passage pairs, so that inputs with related meaning land near each other. "How do I reset my password" and "forgot login credentials" end up close; "reset the router" ends up further away even though it shares a word.

Three properties matter for system design:

  • The vector space is model-specific. Vectors from two different models (or two versions of the same model) are not comparable. Changing models means re-embedding the whole corpus. This is the root of the migration problem below.
  • Queries and documents may be embedded differently. Many retrieval models expect a prefix or a separate mode for queries vs passages (asymmetric search). Getting this wrong quietly costs recall.
  • Embeddings compress meaning, not exact tokens. An error code like E-4012, a SKU or a rare surname may not survive the compression. That is why production retrieval is almost always hybrid (see hybrid search below).

Distance metrics and normalization

The three metrics you'll see are cosine similarity (angle between vectors), dot product (angle and magnitude) and Euclidean (L2) distance. If vectors are L2-normalized to unit length, all three give the same ranking: cosine equals dot product, and squared L2 distance equals 2 − 2·cosine. Most text embedding models are meant to be used with cosine, so the usual practice is to normalize at write time and use dot product (the cheapest to compute) at query time. Use whatever metric the model card says; using L2 on unnormalized vectors from a cosine-trained model degrades results.

Exact vs approximate search

Exact (brute-force, "flat") search compares the query with every stored vector. Cost is N × d multiply-adds per query: for 10M vectors at 1,024 dims that's about 10 billion operations, hundreds of milliseconds to seconds per query on CPU depending on hardware (less with batched queries or GPUs). It's perfectly fine for small sets (up to roughly 100K–500K vectors, or a single tenant's slice of data) and it gives perfect recall, which makes it the ground truth for measuring everything else.

Beyond that, you use an approximate nearest neighbor (ANN) index, which examines a small fraction of the vectors and returns most of the true neighbors. The quality metric is recall@k: of the true top-k neighbors (from brute force), what fraction did the index return? Production systems usually target 0.9–0.99. Every ANN index exposes a knob that trades recall against latency, and the right setting depends on your data, so you measure it.

Keep ANN recall and retrieval quality separate in your head. ANN recall measures whether the index found the vectors brute force would have found. Retrieval quality measures whether those vectors were the relevant documents. A perfect index on a weak embedding model still retrieves the wrong chunks.

HNSW in depth

Hierarchical Navigable Small World graphs (Malkov & Yashunin) are the most widely used index in pgvector, Qdrant, Weaviate, Elasticsearch/OpenSearch, Redis, Milvus and most others. Understand this one well.

How it works

  1. A layered graph. Every vector is a node in layer 0 and is linked to its closest neighbors. Each node is also promoted to higher layers with exponentially decreasing probability, so layer 1 has a fraction of the nodes, layer 2 a fraction of that, and so on. Higher layers are sparse, so their links span long distances, like an express train.
  2. Greedy search from the top. A query starts at a fixed entry point in the top layer, repeatedly moves to whichever neighbor is closest to the query, and when no neighbor is closer, drops down a layer and continues. Each layer narrows the region. On layer 0 it does a wider best-first search, keeping a candidate list of size efSearch, and returns the best k.
  3. Inserts run the same search to find a new node's neighbors on each layer it belongs to, then link it in and prune neighbor lists to stay within the degree limit.

Search touches roughly logarithmically many nodes, which is why HNSW stays in the low milliseconds at tens of millions of vectors.

The three knobs

ParameterWhat it controlsTypical valuesEffect of raising it
MMax links per node (layer 0 usually allows 2·M)16–64Better recall, especially in high dimensions; more memory; slower builds

For reference, pgvector's defaults are m = 16, ef_construction = 64 and hnsw.ef_search = 40 (pgvector README). efSearch is the knob you tune: plot recall@10 against p99 latency for a few values on a held-out query set and pick the knee of the curve.

Memory

HNSW wants the vectors and the graph in RAM. The Faiss guidelines give a per-vector cost of about d × 4 + M × 2 × 4 bytes for float32 vectors (Faiss wiki):

vectors: d × 4 bytes          // float32
graph:   M × 2 × 4 bytes      // ~2M neighbor ids of 4 bytes on layer 0; upper layers add little

d = 1,024, M = 16:  4,096 + 128 = ≈ 4.2 KB per vector
10M vectors      ≈ 42 GB before metadata, replicas and headroom

The graph is small next to the raw vectors at typical dimensions, which is why compressing the vectors (quantization, below) is the main memory lever.

Updates and deletes

  • Inserts are online but cost an ANN search plus link updates each, so bulk loads are much slower than for IVF. Bulk-building a fresh index and swapping it in is often faster than inserting millions of rows one by one.
  • Deletes are usually tombstones. Removing a node would break paths through it, so most implementations mark it deleted, skip it in results, and repair or rebuild later. Heavy delete churn leaves dead nodes that still cost memory and traversal time, and recall can drift. Plan periodic compaction or rebuilds, and monitor recall over time rather than measuring it once.
  • Updates to a vector are delete plus insert.

Other index families

IVF: cluster, then search a few clusters

Inverted file indexes run k-means to produce nlist centroids, assign each vector to its nearest centroid's list, and at query time scan only the nprobe closest lists. The Faiss guidelines suggest nlist between roughly 4·√N and 16·√N. Raising nprobe raises recall and latency. IVF builds fast, uses less memory than HNSW (no graph), and pairs naturally with compression. Its weaknesses: it needs a training step on representative data, and if the data distribution drifts after training, clusters become unbalanced and recall drops until you retrain.

Quantization: shrinking each vector

MethodHowBytes for d = 1,024Notes
float32Baseline4,096Exact distances
float16 / bfloat16Half precision2,048Near-lossless for retrieval; easy win (pgvector halfvec)
Scalar (int8)Map each dimension's range to 256 buckets1,0244× smaller, small recall loss; needs calibration data for ranges
Product quantization (PQ)Split the vector into m sub-vectors; replace each with the id of its nearest of 256 learned centroids64 (m = 64)32–64× smaller; distances approximate, so rescore top candidates with full vectors
BinaryKeep only the sign of each dimension; compare with Hamming distance12832× smaller and very fast; works well only for some models, and needs rescoring

The common pattern is search compressed, rescore exact: run the ANN search over compressed vectors held in RAM, fetch, say, the top 100–400 candidates' full-precision vectors from disk or a cheaper tier, recompute exact distances, and return the top k. Hugging Face and mixedbread measured binary quantization alone retaining about 92.5% of retrieval performance, rising to around 96% with rescoring, at a 32× memory reduction (Embedding Quantization). Your model may behave differently; measure.

DiskANN: graphs on SSD

DiskANN (Microsoft, NeurIPS 2019) keeps a graph index (Vamana) and full vectors on SSD and only PQ-compressed vectors in RAM. Search navigates using the in-memory compressed vectors and reads full vectors from SSD for the final candidates. The paper indexed a billion points on a single machine with 64 GB of RAM and an SSD while keeping high recall at millisecond latencies. Disk-based indexes are how you get to billion scale without a terabyte of RAM; the cost is SSD reads per query (higher and less predictable latency than in-memory HNSW).

GPU indexes

For very high query throughput or fast index builds, GPU indexes such as NVIDIA's CAGRA (in the cuVS library, used by Milvus and Faiss) build and search graph indexes on the GPU. They shine with large query batches (offline deduplication, recommendation candidate generation, re-indexing a whole corpus) and are usually overkill for interactive RAG, where a single query per request and CPU HNSW are plenty.

Filtering

Real queries are never "nearest vectors in the whole corpus." They are "nearest vectors for tenant 42, that this user can read, updated after January." How the engine combines the filter with ANN search decides whether you get correct results.

  • Pre-filtering evaluates the metadata filter first, then searches only matching vectors. With brute force over the subset it's exact, but if the filter matches millions of rows it's slow, and you can't use the global graph directly because skipping non-matching nodes disconnects it.
  • Post-filtering runs ANN for the top k (or k × some factor), then drops non-matching results. It's fast but wrong for selective filters: if tenant 42 owns 0.1% of the corpus, the global top 100 likely contains zero of their documents, and the user gets "no results." Over-fetching helps only up to a point.
  • Filtered traversal (in-filter) applies the predicate during graph search: non-matching nodes can still be used for navigation but are not returned, and search continues until it has k matches. This is what Qdrant's filterable HNSW does; pgvector's iterative index scans (added in 0.8.0) reach a similar result differently, filtering after each index scan and continuing until enough rows match. Research like ACORN builds denser graphs so that the subgraph of matching nodes stays navigable for arbitrary predicates; Weaviate ships an ACORN-based filter strategy. Good engines also have a query planner that switches to pre-filter brute force when the filter is very selective (a few thousand matches), because exact search over a tiny set is both fast and perfect.

Permission filtering must happen inside the search, never after generation. If you post-filter by ACL, you either leak documents into the prompt or return empty results. Say this explicitly in any multi-tenant or enterprise RAG interview.

A common hybrid: namespace per tenant for the long tail, dedicated capacity for the largest customers. Systems built on object storage (turbopuffer, LanceDB) make millions of mostly-idle namespaces cheap because cold data lives in S3 and only hot namespaces are cached on SSD or in memory; the trade-off is slower first queries on cold namespaces.

Scaling: sharding and replication

When one node can't hold the index or serve the QPS, you scale like any search system:

  • Sharding for size. Split vectors across shards, either randomly/by hash (every query fans out to every shard, and each returns a local top-k that a coordinator merges) or by a partition key such as tenant (queries hit one shard, but shards can become unbalanced). Random sharding is simpler and keeps load even; tail latency is set by the slowest shard, so keep shard count modest and over-fetch slightly per shard.
  • Replication for QPS and availability. Each shard has replicas; queries load-balance across them. Adding replicas raises throughput linearly; adding shards does not (every query still hits all of them).
  • Separating writes from reads. Heavy ingestion competes with queries for CPU. Many systems buffer writes into a small fresh segment searched by brute force or a small index, then merge into the main index in the background (log-structured, like Lucene segments). This is why newly written vectors are sometimes not visible for a few seconds: ask about freshness requirements.

Storage math, worked

10 million chunks

10M × 1,024 dims × 4 bytes        = 41 GB raw float32
HNSW graph (M = 16): 10M × 128 B  = 1.3 GB
metadata (ids, tenant, ACL, ~200 B) = 2 GB
                                  ≈ 44 GB → fits one large-memory node
with float16 vectors              ≈ 24 GB
with int8 vectors                 ≈ 14 GB
2 replicas for availability       × 2

Conclusion for the interviewer: 10M chunks is a single-node problem (plus replicas). pgvector on a big Postgres instance or any vector DB handles it. Don't propose a 20-node cluster.

1 billion vectors

1B × 768 dims × 4 bytes           = 3.1 TB raw float32
HNSW graph (M = 32): 1B × 256 B   = 256 GB
                                  ≈ 3.3 TB in RAM for plain HNSW
  → ~14 nodes at 256 GB usable RAM each, ×2 replicas ≈ 28 nodes

PQ, 96 bytes per vector           = 96 GB of codes in RAM
  + full vectors on SSD for rescoring (3.1 TB of NVMe)
  → a handful of nodes, or one DiskANN-style node per few hundred million vectors

Here the interesting discussion is the trade-off between RAM cost and latency: plain HNSW in RAM gives the lowest, most predictable latency; compressed or SSD-resident indexes cut hardware cost by an order of magnitude at the price of rescoring reads and a slight recall loss. Mention Matryoshka truncation too: dropping from 768 to 256 dims cuts the raw vector storage by 3×.

Changing embedding models without downtime

New embedding models arrive constantly, and vectors from the old and new models can't be mixed. A migration is a re-index of the whole corpus:

  1. Create a versioned index (chunks_v2) alongside the serving one. Store the embedding model id and version on every vector so mixed states are detectable.
  2. Dual-write new and changed documents to both indexes, embedding with both models.
  3. Backfill the existing corpus into v2 with a batch job, using cheaper batch APIs or a GPU pool, throttled so it doesn't starve the online embedding path. Make it resumable and idempotent (keyed by chunk id and content hash).
  4. Shadow-read and compare. Run real or golden queries against both and compare recall@k, answer quality in your eval suite, and latency.
  5. Flip the read alias (or a feature flag) to v2, gradually if possible, and keep v1 for a rollback window before deleting it.

Budget it: re-embedding 10M chunks of 500 tokens is 5 billion tokens. At hosted prices of a few cents per million tokens that's on the order of a hundred dollars, so the real cost is engineering time and the temporary doubled storage, not the embedding bill. At billions of chunks it becomes a planned project.

Hybrid search: sparse, dense and late interaction

  • BM25 (lexical, sparse). Classic inverted-index scoring by term frequency and rarity. Exact matches on identifiers, names, error codes and rare terms. Cheap and well understood.
  • Learned sparse (SPLADE). A model produces sparse term weights, including expansion terms that weren't in the text, so "car" can match "automobile" while still using an inverted index.
  • Dense. One vector per chunk; strong on paraphrase and meaning.
  • Late interaction (ColBERT). Keep one vector per token and score a document by summing, for each query token, its best match among document tokens (MaxSim). More precise than single-vector dense retrieval, at the cost of storing many vectors per chunk (ColBERTv2 compresses them heavily). Used either as a first-stage retriever in engines that support it (Vespa, some specialized libraries) or as a reranker. The same idea powers ColPali for retrieving page images directly.

Production systems run BM25 and dense in parallel and fuse the rankings (reciprocal rank fusion), then rerank. The fusion and reranking stages are in RAG in Depth.

Vector Search in System Design Interviews

When to bring it up

  • Any semantic retrieval: "Users ask in their own words, so keyword search alone won't find the right article. I'll embed chunks and run hybrid search."
  • Semantic caching and memory: "Long-term memories are embedded so we can retrieve the few relevant ones per turn."
  • Deduplication and clustering: "We embed incoming tickets and cluster them to find recurring issues."
  • When scale numbers appear: if the interviewer says "a billion documents," that is your cue for the storage math and the sharding/compression discussion.

How to introduce it

  1. State what's embedded and with what. "Chunks of ~500 tokens, embedded with a 1,024-dim retrieval model; queries embedded with the same model in query mode."
  2. Size it. One line of math: count × dims × bytes, plus graph overhead. Conclude whether it fits a node.
  3. Pick the index and say how you'll tune it. "HNSW; we tune efSearch against a recall@10 target of 0.95 measured with brute force on a sample."
  4. Address filtering and tenancy. "ACL and tenant filters are applied during the search; large tenants get their own namespace."
  5. Say how it stays fresh and how it evolves. Change-driven upserts, tombstones and compaction, and versioned indexes for model upgrades.

Common deep-dive questions

"Your corpus grows from 10M to 1B vectors. What changes?"

Redo the memory math (≈3 TB float32 at 768 dims), then choose between sharded in-RAM HNSW (fast, expensive) and compressed or SSD-resident indexes with rescoring (cheaper, slightly slower). Add replicas for QPS, discuss fan-out tail latency, and consider Matryoshka truncation or a smaller embedding model.

"How do you make sure tenant A never sees tenant B's documents?"

Bad Solution
Filter results after retrieval

Challenges: post-filtering returns too few results for small tenants and any bug in the filter leaks data into prompts.

Good Solution
Tenant id as a mandatory in-search filter

Approach: every query is built by a server-side retrieval service that injects tenant_id and the user's ACL groups from the auth context; the engine applies them during traversal.

Challenges: still one shared index, so isolation depends on code correctness; noisy neighbors.

Great Solution
Namespace per tenant, ACL filter inside, defense in depth

Approach: physical separation per tenant (namespace or partition), so a missing filter returns nothing rather than someone else's data; document-level ACLs as in-search filters; per-tenant encryption keys where required; tenant id also checked on the returned chunks before prompt assembly; deletion by dropping the namespace.

Challenges: per-namespace overhead with many tenants, solved by object-storage-backed engines or offloading idle tenants.

"How would you upgrade the embedding model?"

Versioned index, dual-write, resumable backfill, shadow evaluation, alias flip, rollback window. Mention the doubled storage during migration and that queries must be embedded with the model matching the index they hit.

"Recall dropped this month but nothing was deployed. Why?"

Candidates: tombstone build-up from deletes, IVF clusters drifting from new data distribution, a partial re-embedding, a new content type the model handles poorly, or filters that became more selective as tenants grew. Show you'd detect it with a scheduled recall check against brute force on a fixed query sample.

Summary

  • Embeddings are model-specific; changing models means a full re-index, so version everything.
  • HNSW is the default: tune efSearch for recall vs latency, budget about 4d + 8M bytes per vector, and plan for tombstones.
  • Memory is the main cost; quantization with rescoring, Matryoshka truncation and SSD-resident indexes are the levers.
  • Filtering is where naive designs break. Filter inside the search, and prefer physical separation for tenants.
  • Do the storage math out loud: 10M vectors is a single-node problem; 1B is a sharding and compression discussion.
  • Hybrid (BM25 + dense) beats either alone; fusion and reranking live in RAG in Depth, and semantic caching in Caching for LLMs.

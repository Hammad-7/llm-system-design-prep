API Design & Streaming

How to shape the API for LLM-backed features: choosing between synchronous, streaming and asynchronous interactions, designing resources and idempotency, making streams resumable and cancellable, handling errors after the first token, and the client-side details that make it feel fast.

LLM calls break the assumptions that most API design advice is built on. A response can take 30 seconds or 30 minutes. It arrives a few characters at a time. It costs real money per request, so a duplicate retry is a billing bug, not just wasted CPU. It can fail halfway through, after the user has already read the first paragraph. And it often isn't a single call at all, but an agent run with tool calls in the middle.

In interviews, the API section of the delivery framework is where you show you understand this. "POST /chat returns the answer" is a mid-level answer. A senior answer picks the right interaction shape, makes retries safe, streams typed events, survives disconnects, and says what happens when generation fails at token 400. This page covers each of those, with sketches you can reuse.

Choosing the interaction shape

The question to ask out loud: "Who consumes this output, and how long does it take?" A person reading for 10 seconds wants streaming. Code waiting on a JSON object wants synchronous. Anything that can outlive an HTTP connection (a deploy, a laptop lid closing) wants an async job with a durable run ID.

Designing the API surface

Stateless vs stateful model APIs

Provider APIs come in two styles, and the same choice appears in your own product's API:

  • Stateless (e.g. Chat Completions, Anthropic Messages): the client sends the full conversation every time. Simple, horizontally scalable, easy to cache and to switch providers. The client (or your backend) owns history storage.
  • Stateful (e.g. OpenAI's Responses API with previous_response_id and stored conversations): the server keeps the conversation and the client references it by ID. Less payload, and the server can run built-in tools, keep reasoning state and resume background work. The costs are server-side storage, retention and privacy obligations (zero-data-retention customers may not be able to store), and tighter coupling to one provider.

For your own product, the usual answer is a stateful public API (clients deal in conversation IDs) backed by stateless calls to model providers (your backend assembles the context each turn). That keeps providers swappable and puts context engineering under your control (see Context Engineering).

A resource model for an LLM product

POST   /v1/conversations                              → { id }
GET    /v1/conversations?cursor=…&limit=20            → { items, next_cursor }
GET    /v1/conversations/{cid}/messages?before=…      → { items, next_cursor }

POST   /v1/conversations/{cid}/messages               // send a user message, start a response
       Idempotency-Key: 7b0c…                          // client-generated, reused on retry
       { content, parent_message_id?, model?, stream: true }
       → 200 text/event-stream                         // or 202 { response_id } if async

GET    /v1/responses/{rid}/events                      // (re)attach to a running stream
       Last-Event-ID: 42
POST   /v1/responses/{rid}/cancel                      → 202
POST   /v1/messages/{mid}/feedback   { rating, reason? }
  • Response as a resource. Giving each generation a response_id lets clients reattach, cancel, and fetch the final result independently of the connection that started it.
  • Branching. Editing a message or regenerating creates a sibling, not an overwrite. Store messages as a tree (parent_message_id) and track the active leaf per conversation.
  • Cursor pagination. Paginate messages by an opaque cursor over (created_at, id), newest first. Offsets break when messages are added while scrolling.
  • Model choice as a parameter. Accept a model alias the product controls ("fast", "best") rather than raw provider model IDs, so you can change the backing model without breaking clients.

Idempotency keys

Mobile networks drop requests constantly. If the client retries POST /messages after a timeout, you must not generate (and bill) twice, or show two answers. The standard fix:

  1. The client generates a UUID per logical send and reuses it on every retry, in an Idempotency-Key header.
  2. The server atomically inserts (tenant, key) → {request_hash, response_id, status} with a TTL of about 24 hours.
  3. If the key exists with the same request hash: return the existing response (or reattach to its stream if it's still generating). If the hash differs: return 409 Conflict, because the client reused a key for a different request.

The same key can double as the optimistic-UI message ID on the client, which makes de-duplication on reconnect trivial.

Request IDs and traceability

Return a request ID on every response (X-Request-Id) and in every stream's first event, and propagate it to model calls, tool calls and logs. When a user reports "the answer was wrong," the request ID is how support finds the trace with the exact prompt, retrieved context and model version (see Observability & LLMOps).

Server-Sent Events in depth

SSE is the default transport for token streaming: a long-lived HTTP response with Content-Type: text/event-stream, made of text events separated by blank lines. It works through most proxies, needs no special server infrastructure, and has reconnection semantics built in.

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no                // tell nginx not to buffer

retry: 3000                          // client reconnect delay (ms)

id: 1
event: response.created
data: {"response_id":"r_9f2","request_id":"req_41a","model":"fast-2026-10"}

id: 2
event: text.delta
data: {"delta":"The refund window"}

id: 3
event: text.delta
data: {"delta":" is 30 days."}

: keep-alive                         // comment line = heartbeat, ignored by clients

id: 4
event: citation
data: {"source_id":"kb_118","title":"Refund policy","span":[0,32]}

id: 5
event: response.completed
data: {"stop_reason":"end_turn","usage":{"input":5210,"cached_input":4096,"output":41}}

Typed events

Don't stream bare text. Typed events let the client render text, tool status, citations and errors differently, and let you add new event types without breaking old clients (clients must ignore types they don't know). Real provider streams are modeled this way: Anthropic's Messages API emits message_start, content_block_start, content_block_delta (with text or partial-JSON deltas), content_block_stop, message_delta (stop reason and usage) and message_stop, plus ping and error; OpenAI's Responses API uses events like response.output_text.delta and response.completed.

Operational pitfalls

  • Proxy buffering. nginx, some CDNs and compression middleware buffer responses, so the user sees nothing for 20 seconds and then the whole answer. Disable buffering for the route (proxy_buffering off or X-Accel-Buffering: no), don't gzip event streams, and flush after each event.
  • Idle timeouts. Load balancers drop idle connections (AWS ALB's default idle timeout is 60 seconds). A model thinking for 90 seconds before its first token looks idle. Send a comment heartbeat every 10–15 seconds.
  • Browser connection limits. Over HTTP/1.1, browsers allow only about six concurrent connections per origin, and each open SSE stream holds one. Serve streams over HTTP/2, which multiplexes them on one connection.
  • EventSource limitations. The browser's built-in EventSource only does GET and can't set custom headers like Authorization. Most chat clients use fetch() with a streaming body reader for the POST and parse SSE themselves, keeping EventSource-style IDs and reconnection logic.
  • Graceful deploys. Rolling deploys kill connections. If generation is decoupled from the connection (next section), the client just reconnects and resumes.

Server-side orchestration (tool calls, logging) then happens over a parallel WebSocket or webhook channel. The Real-time Voice Agent breakdown goes deeper.

Resumable streams

The single most important streaming design decision: decouple generation from the client connection. If the model call lives inside the HTTP handler, a dropped connection loses the answer you're paying for, and a reconnect has to start over.

  1. The send request creates a response_id and enqueues generation on a worker (or starts it in a detached task).
  2. The worker streams from the model and appends each event to a per-response event log with a monotonically increasing sequence number. A Redis Stream works well (XADD with a TTL of minutes to hours); Kafka or a database table also work at different cost points.
  3. The stream endpoint reads from the log and relays events to the client as SSE with id: set to the sequence number.
  4. On reconnect, the browser (or your client code) sends Last-Event-ID: 42; the endpoint replays from event 43 and then tails new events. Any server instance can serve the reconnect because state is in the log, not in memory.
  5. When generation finishes, the worker writes the final message to the message store. Clients that come back later just fetch it.

OpenAI's background mode exposes the same idea publicly: you track the sequence_number of each event and resume a stream from a cursor (OpenAI background mode).

Policy decision: if the client disconnects, does generation continue? For chat, a reasonable default is to keep generating (the user probably switched networks or tabs) and persist the result, but cancel if nobody reattaches within, say, 60 seconds of a long response. For agent runs, keep going; the run is a job, not a stream.

Cancellation and backpressure

Cancellation

Users hit "Stop" constantly, and every token generated after that is wasted money and GPU time. Cancellation has to propagate all the way down:

  • The client calls POST /responses/{id}/cancel (and aborts its fetch).
  • The API sets a short-lived cancel flag (or publishes a cancel message).
  • The worker checks the flag between chunks and aborts the upstream model stream. Closing the HTTP connection to a provider usually stops generation; on self-hosted engines like vLLM, aborting the request frees its KV cache blocks immediately.
  • The worker persists the partial message, marked stopped_by_user, and bills only the tokens actually generated.

Backpressure

Generation rarely outruns the client for text (models emit tens to hundreds of tokens per second), but slow mobile clients, long tool outputs and fan-out to many viewers can. With an event log in between, the worker never blocks on a slow socket: it appends at model speed, and each connection reads at its own pace. Set a cap: if a client falls too far behind (or the log exceeds its size limit), drop the connection and let it resume from its last ID. Some UIs also smooth bursty token arrival into a steady typing rhythm client-side, which looks better than chunks arriving in clumps.

Streaming tool calls and structured output

When the model calls a tool or produces JSON, its arguments arrive as partial JSON: {"query": "refund pol. Two rules:

  • Don't act on partial arguments. Buffer deltas and parse only when the tool call is marked complete. Schema-constrained decoding (structured outputs) guarantees the final JSON parses, not that the values are right, so validate before executing.
  • Do render partial structure if it helps the UI. A tolerant partial-JSON parser can show fields as they fill in (a form being completed, a table growing). Libraries for this exist in most languages.

For server-side tools, emit status events ("Searching 3 sources…") so the stream doesn't go silent during a 4-second tool call. For client-side tools (the browser or IDE executes them), the stream ends with a tool request, the client runs it, and posts the result back to continue the response, which is one reason agent IDEs often prefer WebSockets.

Errors after the first token

Once a stream starts, the HTTP status is already 200. Errors after that point must travel as events, and the client must handle a partially rendered answer.

WhenSignalClient behavior
Before streaming: invalid request, auth, not found400, 401/403, 404Show error; don't retry
Before streaming: input too long for the context window400/413 with a specific codeTrigger compaction or ask the user to shorten
Before streaming: idempotency key reused with a different body409Bug in the client; don't retry
Before streaming: rate limited or overloaded429 or 503 (some providers use 529) with Retry-AfterRetry with backoff and jitter; show "busy" after a few seconds
Mid-stream: provider failure, timeoutevent: error with retryable: trueKeep partial text, mark the message incomplete, offer "Continue" or "Retry"
Mid-stream: output limit reachedCompleted with stop_reason: max_tokensOffer "Continue"
Mid-stream: output blocked by safety filterCompleted with a refusal / content_filter reasonReplace or redact the partial text as the policy requires

Never silently retry a stream after text has been shown. The retry generates a different answer, and splicing it onto the first half produces nonsense. Either continue from the partial output (send it back as the start of the assistant turn, where the model supports prefill; many newer models, including recent Claude models, reject a prefilled assistant turn) or regenerate visibly.

Rate-limit headers and usage reporting

Because limits are on tokens, not just requests (see Gateways, Routing & Reliability), tell clients where they stand. Providers return headers such as x-ratelimit-remaining-tokens and x-ratelimit-reset-tokens (OpenAI) or anthropic-ratelimit-input-tokens-remaining (Anthropic), plus Retry-After on 429. Your own API should do the same per API key, and report usage (input, cached input, output and reasoning tokens) in the final event so clients can show cost and you can reconcile billing against provider invoices.

Long-running work: jobs and webhooks

Agent runs, deep research and document pipelines take minutes to hours. Model them as jobs (see Common Patterns for durable execution):

POST /v1/runs   { task, inputs, webhook_url? }      → 202 { run_id, status: "queued" }
GET  /v1/runs/{id}                                  → { status, progress, result? }
GET  /v1/runs/{id}/events                           // SSE progress, resumable
POST /v1/runs/{id}/cancel

// webhook delivery
POST {webhook_url}
  webhook-id: evt_8812                 // consumers de-duplicate on this
  webhook-timestamp: 1763542861        // reject if older than ~5 minutes (replay protection)
  webhook-signature: v1,base64(HMAC_SHA256(secret, id.timestamp.body))
  { "type": "run.completed", "run_id": "...", "result_url": "..." }
  • Sign webhooks with an HMAC over ID, timestamp and body; reject stale timestamps. The open Standard Webhooks spec codifies this.
  • Retry with backoff for hours, then dead-letter; expose delivery logs to customers.
  • Consumers must be idempotent: at-least-once delivery means duplicates.
  • Return results by reference (a signed URL) when they're large.

Versioning and compatibility

  • Version the API explicitly, by URL (/v1) or by a dated header (Anthropic's anthropic-version header is an example), so behavior changes are opt-in.
  • Pin model versions behind aliases. Clients ask for "support-default"; you map it to a dated model snapshot and move the alias only after evals pass. Never let a provider's floating alias change your product's behavior silently.
  • Additive events only. New event types and fields are fine because clients ignore unknowns; renaming or removing them is a breaking change.

Client-side concerns

  • Streaming Markdown. Partial Markdown is often invalid: an unclosed code fence turns the rest of the message into code; half a table renders as pipes. Use a renderer that tolerates incomplete input (or temporarily closes open blocks), and re-render at most once per animation frame rather than per token.
  • Optimistic UI. Show the user's message instantly with a client-generated ID (the same value as the idempotency key), then reconcile with the server's copy.
  • Scroll behavior. Auto-scroll only if the user is already at the bottom; never yank them away from what they're reading.
  • Reconnect logic. On network change or tab wake, reattach with Last-Event-ID; back off exponentially on repeated failures.
  • Accessibility. Announce streamed content politely (aria-live="polite") and in sentence-sized chunks, not per token.

API Design & Streaming in System Design Interviews

When to bring it up

  • In the API step of every LLM design. "Sending a message returns an SSE stream of typed events; the response has its own ID so the client can reattach or cancel."
  • When the interviewer asks about reliability. "Generation is decoupled from the connection via an event log, so refreshes and deploys don't lose answers."
  • When work is long. "Agent runs are jobs: 202 with a run ID, SSE for progress, webhooks on completion."
  • When cost comes up. "Idempotency keys stop double generation on retries; cancellation stops billing when users hit Stop."

How to introduce it

  1. Name the interaction shape and why (who consumes the output, how long it takes).
  2. Sketch the resources: conversation, message, response or run.
  3. Show the streaming contract: typed events, IDs, the completion event with usage.
  4. Cover failure: idempotent sends, resumable streams, mid-stream errors, cancellation.
  5. Mention the operational details briefly: heartbeats, buffering, HTTP/2.

Common deep-dive questions

"The user refreshes the page halfway through a long answer. What happens?"

Bad Solution
The stream dies with the connection; the user asks again

Challenges: you paid for half an answer, the user waits again, and the conversation now has a missing or duplicated turn.

Good Solution
Persist the message when generation completes

Approach: generation continues server-side; when the page reloads, the client polls until the message appears.

Challenges: the user sees nothing until the end; generation still lives in one process, so a crash or deploy loses it.

Great Solution
Generation workers write to a sequence-numbered event log; any server can replay

Approach: on reload, the client fetches the conversation, sees an in-progress response ID, and opens GET /responses/{id}/events with the last event ID it rendered (or 0). The endpoint replays from the log and tails new events. The final message is persisted on completion; the log expires after a TTL.

Challenges: one extra write per event (batch deltas into ~50 ms chunks to keep Redis load reasonable); log retention sizing; a policy for abandoned responses.

"How do you bill a stream the user cancelled?"

Bill the tokens actually consumed: the input tokens (all of them; prefill already ran) plus output tokens generated before the cancel reached the model. That requires cancellation to propagate quickly and the worker to record usage from the provider's final usage event or its own token count when aborting. Reconcile against provider invoices daily.

"Enterprise customers say streaming doesn't work behind their proxy."

Their proxy buffers or times out long responses. Options: heartbeats every ~10 seconds, disable compression on the stream, offer a fallback mode that long-polls the response resource (GET /responses/{id}?wait=25s returning the latest chunks), and document a WebSocket option where allowed. Detect buffering client-side (no events for N seconds while the server reports progress) and switch modes automatically.

"Design the API for an AI agent product."

Runs as first-class resources with status, budget and cost; SSE events for steps (model output, tool call, tool result summary, approval request); POST /runs/{id}/messages to steer; POST /runs/{id}/approvals/{aid} to approve or deny a risky action; cancellation; webhooks on completion; and artifacts (diffs, files, reports) as separate resources with signed download URLs. See AI Coding Agent and Design Claude Code.

Summary

  • Pick the shape by consumer and duration: synchronous for code-consumed short outputs, streaming for people, jobs for anything that can outlive a connection.
  • Make responses and runs resources with IDs; make sends idempotent with client-generated keys.
  • Stream typed events over SSE with sequence IDs, heartbeats and no proxy buffering; prefer HTTP/2.
  • Decouple generation from the connection with an event log so streams survive refreshes, deploys and network changes.
  • Propagate cancellation to the model; bill only what was generated.
  • Errors after the first token are events; never silently splice a retry onto a partial answer.

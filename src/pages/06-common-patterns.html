Common Patterns

The recurring architectures behind most LLM system design answers. Learn to recognize the problem each one solves, draw it in under a minute, and explain its trade-offs.

Most LLM interview prompts are combinations of a small number of patterns. "Design a support assistant" is RAG + guarded tool execution + an eval flywheel. "Design a coding agent" is the agent loop + long-running durable tasks + sandboxing. When you see the patterns, the design starts to assemble itself and you can spend your energy on trade-offs.

Retrieval-Augmented Generation

Problem: the model needs knowledge it wasn't trained on (private, recent, or too large to fit in the prompt), and answers must be traceable to sources.

Solution: two paths. The offline ingestion path turns documents into searchable chunks. The online query path retrieves the best chunks for each question and generates a cited answer from them.

  • Ingestion is a queue-driven worker pipeline triggered by change events: parse (layout-aware for PDFs and tables), chunk, enrich (titles, contextual summaries, ACLs), embed, upsert into vector and keyword indexes. Re-embedding the corpus is a backfill job, so version your embeddings.
  • Query: rewrite the query using conversation context, run vector and BM25 search in parallel with permission filters, fuse, rerank the top ~50–100, keep the best 5–20, and prompt the model to answer only from them with citations. Abstain if nothing scores well.

Trade-offs: each stage adds latency (rewriting adds an LLM call; reranking adds roughly 50–200 ms) in exchange for precision. Bigger top-k improves recall but costs tokens and can distract the model. Shows up in: support bots, enterprise search, document Q&A, code assistants, Perplexity-style answer engines.

Streaming Responses

Problem: generating a full answer takes seconds; users won't stare at a spinner, and connections drop mid-answer.

Solution: stream token deltas to the client over SSE as they're generated, while a writer persists the growing message. Number each event so a reconnecting client can resume from the last event ID.

  • Decouple generation from the client connection. The generation worker writes deltas to a short-lived buffer (for example a Redis stream keyed by message ID); the edge server relays them. If the client reconnects, possibly to a different server, it replays from the buffer.
  • If the user navigates away, decide deliberately: cancel generation to save tokens, or finish and store the answer so it's there when they return.
  • Run output guardrails on chunks (sentences or paragraphs) as they stream, accepting that a rare violation may need to be retracted from the screen.

Shows up in: every chat product, the Playground, agent progress feeds.

Agent Loop with Guarded Tool Execution

Problem: the task needs multiple steps and real actions (search, query a database, call an API, edit a file) whose sequence can't be known in advance.

Solution: loop: the model proposes the next step as a structured tool call; your executor validates and authorizes it; the result is appended to context; repeat until the model returns a final answer or a budget runs out.

  • The executor, not the model, enforces permissions (using the end user's identity and scopes), validates arguments against a schema, applies idempotency keys, and routes irreversible actions to a human for approval.
  • Budgets on steps, tokens, time and money stop runaway loops. Detect repetition (the same tool call three times) and break out.
  • Tool results are untrusted input: a web page or ticket can contain injected instructions. Keep them clearly delimited and never let them expand the agent's permissions.
  • Keep the loop's control flow in code: the orchestrator decides when to stop, retry, summarize the context or escalate.

Agentic Workflows

Problem: a fully autonomous agent is unpredictable and expensive, but a single prompt can't do the task.

Solution: compose LLM calls through predefined code paths. Anthropic's Building effective agents names five patterns, and they cover most "multi-step" prompts:

PatternHow it worksUse for
Prompt chainingFixed sequence of calls, with code checks ("gates") between stepsOutline → check → draft; extract → validate → summarize
RoutingClassify the input, send it to a specialized prompt or modelSupport triage; easy questions to small models
ParallelizationRun independent calls at once (sectioning) or the same call several times (voting)Guardrails in parallel with the answer; multi-aspect review
Orchestrator-workersA lead LLM decides subtasks at runtime and delegates them to workers, then synthesizesResearch across many sources; multi-file code changes
Evaluator-optimizerOne call generates, another critiques against criteria, loop until it passesTranslation, writing with clear quality criteria, code against tests

Orchestrator-workers is how Anthropic's Research feature works: a lead agent plans and spawns parallel subagents that each search one thread, then a citation pass. The multi-agent setup beat a single agent by 90.2% on their internal research eval, at roughly 15× the tokens of a chat (Anthropic Engineering). That trade-off, breadth and quality for cost, is exactly what interviewers want you to weigh.

Managing Long-Running Agent Tasks

Problem: a task runs for minutes or hours across dozens of LLM and tool calls. Servers restart, providers rate-limit, and some steps wait for a human.

Solution: make the HTTP request asynchronous and the run durable. Return a run ID immediately, execute the run as a durable workflow that checkpoints after every step, stream progress events, and notify on completion.

  • Each LLM call and tool call is an activity with its own timeout and retry policy; completed steps aren't re-executed after a crash.
  • Human approval is a pause: the workflow waits on a signal, possibly for days, without holding a thread or GPU.
  • Persist the agent's context (or its compacted summary) with each checkpoint so the next worker can resume the conversation with the model.
  • Enforce per-run and per-tenant concurrency limits so one customer's batch can't starve everyone.

Request Batching for Inference

Problem: a GPU is most efficient when processing many inputs at once, but requests arrive one by one and each caller waits for its own answer.

Solution: requests enter a queue; a batcher forms a batch when it reaches the maximum size or the oldest request has waited a maximum time; a worker runs the batch; a response router completes each caller's pending future by request ID. For autoregressive LLMs, upgrade to continuous batching inside the serving engine.

This is the most-reported frontier-lab infrastructure question. See the full Inference Batching breakdown.

Layered Caching

Problem: LLM calls are slow and costly, and much of what you send is repeated.

Solution: stack caches from cheapest to most specific, checking each before paying for the next.

  • Order your prompt so the longest stable part comes first. Prefix caching only hits on an exact prefix, so a timestamp at the top of the system prompt destroys your hit rate.
  • Scope every cache key by tenant (and user, when content is personal). A shared semantic cache that returns one customer's answer to another is a data leak.
  • Semantic caching is risky for anything personalized or time-sensitive; reserve it for FAQ-like traffic with a high similarity threshold.

Model Routing, Cascades and Fallbacks

Problem: the best model is too slow and expensive for every request, and any single provider will eventually have an outage or rate-limit you.

Solution: put a gateway in front of all models. Route by task type and difficulty; cascade from small to large models when a check fails; fail over across providers or regions when a backend is unhealthy.

  • The confidence check must be cheap and reliable: a schema validator, a classifier score, retrieval scores, tests passing. A second LLM judging every answer can cost more than it saves.
  • Fallback models produce different outputs. Run your eval set against fallback paths too, and keep prompts portable.
  • Circuit breakers and per-backend concurrency limits keep a slow provider from tying up all your workers.

Guardrail Sandwich

Problem: inputs may be malicious or contain sensitive data; outputs may be unsafe, malformed or ungrounded; tool calls may be harmful.

Solution: independent checks before the model, around tool execution, and after the model, with the strongest controls enforced in code rather than in the prompt.

  • Run input classifiers in parallel with retrieval or the main call, and cancel if they flag. Sequential checks add their full latency.
  • Output checks: JSON schema, policy classifier, PII scan, citation verification (does each cited chunk support the claim?).
  • Log every guardrail decision. Over-blocking is a quality bug you can only find by measuring it.

The Eval Flywheel

Problem: you can't tell whether a prompt tweak, model upgrade or retrieval change made things better or worse, and quality drifts silently in production.

Solution: a closed loop between production and development. Production traces and feedback surface failures; failures become labeled eval cases; every change is gated on the eval suite; shipped changes are monitored online.

In interviews, end your design with this loop. It answers "how do you know it works?" and "how does it get better over time?" in one picture.

Multi-Tenant Isolation

Problem: many customers share models, indexes, caches and GPUs. A mistake leaks data; a noisy neighbor ruins latency.

RetrievalPer-tenant namespaces or indexes for large tenants; mandatory tenant + ACL filters inside the search for shared indexes

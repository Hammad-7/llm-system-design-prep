Observability & LLMOps

What to trace, measure and alert on for LLM systems, how to attribute cost, how to version and roll out prompts and models safely, and how to run incidents when the failure is "the answers got worse."

Classic observability answers "is it up and is it fast?" LLM systems add three questions those tools weren't built for: is it right (quality can degrade with zero errors in the logs), what did it cost (one request can cost 1,000× another), and why did it do that (a bad answer is the product of a prompt version, retrieved chunks, tool results and a model version, all of which you need to reconstruct). An interview answer that ends with "and we'd add monitoring" misses all three.

LLMOps is the operational discipline around this: tracing every step, versioning prompts and models like code, rolling changes out gradually behind quality gates, and feeding production failures back into evaluation. This page covers each piece and how to talk about it.

Tracing LLM requests

A single user request in an LLM app fans out into guardrail checks, retrieval (embed, search, rerank), one or more model calls, tool calls, and post-processing. Represent it as a distributed trace: one root span per request, child spans per step, all sharing a trace id that is also attached to the response and to any user feedback.

What each span should record

SpanRecord
Request (root)Tenant, user (pseudonymous id), feature/endpoint, app version, conversation id, final status, total latency, total cost
Model callProvider, requested and actual model version, prompt template id and version, parameters (temperature, max tokens, reasoning effort), input/output/cached token counts, TTFT, total duration, finish reason (stop, length, tool_use, content filter), retries and fallbacks, cost
RetrievalQuery (rewritten), index and embedding model versions, filters applied, candidate ids and scores before and after reranking, chunks actually placed in the prompt
Tool callTool name, validated arguments, result size, latency, error, whether human approval was required and given
GuardrailWhich check, verdict, score, action taken (block, redact, warn)
Agent runStep count, budget consumed, termination reason (done, budget, loop detected, user cancelled)

Whether to store full prompt and completion text is a policy decision (see PII below). Many teams store full payloads for a sampled or opted-in fraction and metadata for everything.

OpenTelemetry and the GenAI conventions

Use OpenTelemetry for transport so LLM spans sit in the same traces as your HTTP, database and queue spans. OpenTelemetry defines GenAI semantic conventions for model, agent and tool spans, with attributes such as gen_ai.operation.name, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens and gen_ai.usage.output_tokens. As of late 2026 these conventions are still marked Development (not stable) and moved to a dedicated semantic-conventions-genai repository in mid-2026, so expect attribute names to change. Pin an instrumentation version and map to your own stable internal names in the collector. Several vendors' SDKs (OpenLLMetry, OpenInference) emit OTel-compatible spans.

Alert on quality and cost, not just errors. "Faithfulness score on sampled support traces fell from 0.93 to 0.81 in the last hour" and "tenant X has spent 6× its daily average by noon" are the alerts that catch real LLM incidents.

The telemetry pipeline

  • Emit from two places: the application SDK (business context: feature, user, conversation, retrieval details) and the LLM gateway (authoritative usage, cost, provider, retries). Join them by trace id.
  • Collector: redact PII, drop or sample payloads, batch, and route. Tail-based sampling keeps 100% of errors, slow requests, flagged and low-scored traces, and a small fraction of the rest.
  • Stores: a trace store for debugging individual requests; a metrics time-series database for dashboards and alerts; a warehouse (ClickHouse, BigQuery, Snowflake) for cost attribution, cohort analysis and joining with product data. Token and cost records belong in the warehouse unsampled, because billing and budgets need exact totals.
  • Online evals read sampled traces, run judges, and write scores back as span attributes or metrics.

Cost attribution

LLM spend is variable and concentrated: a few tenants, features or agent runs often dominate. Attribute every token:

cost = uncached_input_tokens × in_price + cache_read_tokens × cache_read_price
     + cache_write_tokens × cache_write_price + output_tokens × out_price
     (reasoning tokens are billed as output and, on most APIs, already counted in output_tokens)

tag every call with: tenant_id, feature, model, prompt_version, agent_run_id
  • Keep a price table versioned by model and date in the gateway; never hard-code prices in services.
  • Report unit costs that map to value: cost per resolved ticket, per merged PR, per active user per month. A model that costs 2× per call but resolves twice as many tickets without escalation is cheaper per outcome.
  • For self-hosted models, allocate GPU-hours by each tenant's share of tokens (weighting prefill and decode differently if you want precision).
  • Feed attribution into budgets and quotas: per-tenant monthly caps, per-run agent budgets, alerts at 50/80/100%.

Versioning prompts and models

A prompt is code that runs on someone else's computer, with a behavior you can only measure statistically. Manage it accordingly:

  • Prompt registry. Templates live in version control or a registry with immutable versions (support-answer@v14), owners, change descriptions and linked eval results. Services reference a version or a label (production, canary), never inline strings.
  • Configuration bundle. Version the whole behavior, not just the text: prompt, model id (pinned to a dated snapshot, not a floating alias), parameters, tool definitions, retrieval settings. A change to any of them is a release.
  • Record versions on every trace so you can slice quality by version and answer "when did this start?"
  • Provider model updates are releases you didn't write. Pin snapshots, track deprecation dates, and run the full eval suite before moving to a new snapshot.

Safe rollouts

  1. Offline evals gate the change (see Evaluation).
  2. Shadow mode: the new version runs on a copy of live traffic; outputs are scored but not shown. Catches distribution differences your eval set missed. Costs double inference for the shadowed slice, so shadow a sample, and never let shadow runs execute side-effecting tools.
  3. Canary: serve a small percentage of users or low-risk tenants via feature flags, sticky per user or conversation so experiences are consistent. Compare quality scores, implicit feedback, refusal and guardrail rates, latency and cost against control.
  4. Ramp to 100% with automatic rollback when guardrail metrics breach thresholds. Rollback must be a flag flip, not a deploy.

Drift and quality monitoring

  • Input drift: cluster incoming queries by embedding and watch for new clusters (a product launch, a new language, an outage driving questions) where your eval coverage is thin.
  • Retrieval drift: falling top retrieval scores or rising "no relevant documents" rates point to stale or missing content.
  • Output drift: changes in response length, refusal rate, tool-call mix or format errors, often caused by a provider-side model change.
  • Quality scores over time from sampled judges and implicit feedback, per slice. Use control charts or rolling baselines rather than fixed thresholds, since scores vary by day and traffic mix.

PII, retention and access

LLM traces are full of user content: support conversations, documents, code. Treat the trace store as a production database of sensitive data.

  • Redact at the collector (emails, phone numbers, card numbers, secrets) before data leaves the service boundary; keep a reversible token vault only if a workflow truly needs re-identification.
  • Tiered retention: metadata and metrics for months; full payloads for days or weeks unless the customer opts in for longer; honor deletion requests across traces, eval datasets and fine-tuning sets.
  • Access control and audit for anyone reading payloads; enterprise customers will ask, and some will require zero retention of content.
  • Consent before using production traces in eval sets or training data, per your terms and the customer's contract.

Closing the loop

Observability is the input to improvement. A healthy loop looks like: alerts and sampled judging surface bad traces, someone triages and labels the failure mode, the case lands in the golden dataset, a fix is developed against it, the fix passes the gate, and the canary confirms it in production. Track the loop itself: time from a failure report to a regression test, and the share of eval cases that came from production.

Observability in System Design Interviews

When to bring it up

  • When you finish the high-level design: "Every step emits a span with versions and token counts, so we can debug any bad answer end to end."
  • When cost comes up: "The gateway attributes cost per tenant and feature, and enforces budgets."
  • When the interviewer asks how you'd ship changes or handle a provider outage, or "how would you know if quality dropped?"

How to introduce it

  1. Tracing: one trace per request, spans for retrieval, model and tool calls, with prompt and model versions and token counts.
  2. Metrics and alerts: TTFT/TPOT, errors and fallbacks, cost per unit of value, cache hit rate, guardrail rates, sampled quality scores.
  3. Release process: versioned prompt and model bundles, offline gate, shadow, canary, flag-based rollback.
  4. Data handling: redaction, retention tiers, access audit.
  5. Loop: bad traces become eval cases.

Common deep-dive questions

"Support tickets say answers got worse yesterday, but there were no errors. What do you do?"

Bad Solution
Read some logs and tweak the prompt

Challenges: no way to localize the cause or confirm the fix; the tweak may break other cases.

Good Solution
Check recent deploys and roll back

Approach: look for prompt or code changes in the window and revert them.

Challenges: misses causes outside your deploys: provider model updates, stale indexes, new traffic patterns.

Great Solution
Slice quality by every versioned dimension, then fix and gate

Approach: plot sampled judge scores and implicit feedback by prompt version, model snapshot, index version, tenant and query cluster to localize the change; inspect low-scoring traces (retrieved chunks, tool results); roll back the responsible flag; add the failing traces to the golden set; ship the real fix through the gate and canary.

Challenges: requires versions on every span and online quality scoring, which is why you build them up front.

"How do you stop one agent run from spending $500?"

Budgets enforced outside the model (in the gateway or orchestrator): max steps, tokens and wall-clock per run, per-tenant daily caps, loop detection on repeated tool calls, real-time spend metrics per run with alerts, and a kill switch.

"What would you put on the on-call dashboard?"

TTFT and TPOT percentiles, error and fallback rates per provider, tokens per second vs rate limits, cost burn vs budget, prompt cache hit rate, guardrail and refusal rates, sampled quality score, and agent budget hits, each sliceable by tenant, feature and version.

Summary

  • Trace every request end to end with versions, tokens, retrieval results and tool calls; use OpenTelemetry, knowing the GenAI conventions are still evolving.
  • Monitor quality and cost as first-class signals alongside latency and errors.
  • Attribute cost per tenant, feature and outcome; enforce budgets in the gateway.
  • Version prompt, model and retrieval config as one bundle; roll out via shadow and canary with flag-based rollback.
  • Redact, tier retention and audit access: traces are sensitive data.
  • Close the loop: production failures become eval cases (see Evaluation), and the gateway that emits much of this telemetry is covered in Gateways, Routing & Reliability.

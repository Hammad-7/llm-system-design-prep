Question Breakdown · Medium

Design ChatGPT

A consumer chat assistant serving a frontier LLM to a very large user base. Reported at OpenAI and Anthropic (as "Design the Claude chat service") and widely used elsewhere.

Understanding the Problem

ChatGPT-style assistants let users hold multi-turn conversations with an LLM, see responses stream in token by token, return to past conversations, and choose between model tiers. Under the chat-app surface, the interesting problems are streaming reliability, managing ever-growing conversations against a finite context window, and admitting traffic to a scarce, expensive GPU fleet fairly.

Functional Requirements

Core requirements

  1. Users should be able to send a message in a conversation and receive the model's response streamed in real time.
  2. Users should be able to view their conversation list and continue any past conversation.
  3. Users should be able to choose a model tier (for example a fast default and a slower, stronger model), subject to their plan's limits.

Below the line (out of scope)

  • File uploads, image generation, voice, web browsing and tools
  • Long-term memory across conversations
  • Sharing conversations, team workspaces
  • Training or fine-tuning the model

Non-Functional Requirements

  1. Low perceived latency: time to first token under ~1 s at p95 for the default model under normal load; streaming at reading speed or faster.
  2. High availability: 99.9%+ for chat; when GPUs are saturated, degrade (queue briefly, fall back to a smaller model, or return a clear retry) rather than fail opaquely.
  3. Scale: ~100M daily active users, ~1B messages/day.
  4. Durability: conversations are never lost once the response completes; partial responses survive disconnects.
  5. Fairness and abuse resistance: per-user and per-plan limits; one heavy user can't starve others. Safety moderation on inputs and outputs.

Notice what we didn't say: strong consistency. A conversation is written by one user from one device at a time, so per-conversation ordering is enough. That lets us choose a horizontally scalable store partitioned by conversation.

Capacity estimation

One quick pass tells us the GPU fleet is the dominant cost and design constraint:

1B messages/day                      ≈ 11.6K/s avg, ~35K/s peak (3×)
Output: ~500 tokens/message          ≈ 5.8M output tokens/s avg
Input per call: ~3K tokens (history + system prompt), mostly prefix-cacheable
# Assume ~10K output tokens/s per 8-GPU node at interactive speeds (stated assumption)
5.8M / 10K ≈ 580 nodes avg  → ~1,700 nodes at peak ≈ ~14K GPUs for one model tier
Storage: 1B messages × ~2 KB ≈ 2 TB/day of conversation text

The storage is ordinary; the GPU number is not. Every deep dive that saves GPU time (prefix caching, smart context trimming, admission control) pays for itself.

The Set Up

Core Entities

  • User: plan (free, plus, team), quotas.
  • Conversation: owner, title, model tier, created/updated time, optional rolling summary.
  • Message: conversation ID, sequence number, role (user/assistant), content, status (streaming, complete, incomplete, blocked), token counts, model version.
  • Quota: per-user token and message budgets per window.

API

POST /conversations                                → 201 { conversationId }
GET  /conversations?cursor=                        → [{ conversationId, title, updatedAt }]
GET  /conversations/{id}/messages?cursor=          → [Message]
POST /conversations/{id}/messages                  // returns text/event-stream
     { content, modelTier, clientMessageId }
     event: message_start  { messageId, seq }
     event: delta          { text }          // id: <n> on every event for resume
     event: message_stop   { status, usage }
GET  /messages/{messageId}/stream                  // resume with Last-Event-ID

The user comes from the auth token. clientMessageId makes the send idempotent: a retried POST after a network blip returns the existing stream instead of creating a second turn.

High-Level Design

1) Users can send a message and receive a streamed response

Start simple. The client opens an SSE request to a stateless Chat Service, which loads recent messages, builds the prompt (system prompt + history + new message), and calls the model through an LLM Gateway. The gateway picks a healthy inference pool for the requested tier. Tokens stream back through the gateway and the Chat Service to the client.

When generation finishes, the Chat Service writes both the user message and the assistant message. Input moderation runs in parallel with prompt assembly; output moderation runs on streamed chunks.

2) Users can view and continue past conversations

Conversations and messages go in a Conversation Store. The access patterns are simple: "messages of conversation X in order" and "conversations of user Y, most recent first." A wide-column store such as Cassandra or DynamoDB fits: partition messages by conversationId, sort by seq; keep a second table partitioned by userId, sorted by updatedAt. Postgres sharded by user also works at smaller scale. Conversation titles are generated asynchronously by a small model after the first exchange.

3) Users can choose a model tier

The client sends a tier, not a model name. The gateway maps tier → model version → inference pool, and enforces the user's plan: token quotas per window, concurrency caps, and which tiers they can use. Each tier has its own GPU pool because models have different hardware footprints. Pinning the model version on each message lets us debug and evaluate later.

Potential Deep Dives

1) How do we make streaming reliable when connections drop?

Mobile users switch networks; laptops sleep; load balancers recycle connections. A 30-second generation will regularly outlive the connection that started it.

Bad Solution
Generate, then return the whole response

Approach: the Chat Service waits for the full completion and returns it in one HTTP response.

Challenges: users stare at a spinner for the full generation time, and any disconnect throws the whole response away after we've paid for it.

Good Solution
Proxy the token stream over SSE

Approach: the Chat Service relays tokens from the gateway to the client as SSE events and persists the final message.

Challenges: generation is tied to one connection on one server. If the client drops, either generation is cancelled (wasted work, lost answer) or it finishes with nobody to receive it. Reconnecting to a different server has no way to pick up the stream.

Great Solution
Decouple generation from delivery with a resumable stream buffer

Approach: a generation worker owns the model call and appends sequence-numbered deltas to a short-lived buffer keyed by message ID (for example a Redis stream with a TTL of a few minutes), periodically checkpointing the partial text to the Conversation Store. Any Chat Service instance can serve the SSE connection by reading from the buffer. On reconnect, the client sends Last-Event-ID and the server replays from there. If no client is attached for a while, the worker can finish and store the answer (so it appears when the user returns) or cancel to save GPU time, depending on product choice. The message's status field (streaming, complete, incomplete) tells every device what to render.

Challenges: one extra hop adds a few milliseconds per token; buffer memory must be bounded; cancellation must propagate to the inference server to actually free the GPU slot.

2) How do we handle conversations longer than the context window?

Every turn re-sends the conversation. Long chats get slow and expensive long before they hit the hard context limit, and quality drops as the context fills with stale detail.

Bad Solution
Send the full history every time

Approach: concatenate all messages into the prompt.

Challenges: cost and TTFT grow linearly with conversation length, KV-cache memory per sequence grows with it (fewer concurrent users per GPU), and the request eventually fails at the context limit.

Good Solution
Sliding window with a token budget

Approach: keep the system prompt and as many recent turns as fit in a budget (say 8K tokens), counted with the model's tokenizer.

Challenges: the model forgets early facts ("my name is…", the original task). Users notice.

Great Solution
Rolling summary + recent window + prefix-cache-friendly layout

Approach: when history exceeds a threshold, a small model compacts older turns into a running summary stored on the conversation (decisions, facts, open questions). The prompt is: stable system prompt → summary → last N turns verbatim → new message. Optionally embed old turns and retrieve the few relevant ones. Because the prefix (system prompt + summary + earlier turns) is identical on the next turn, prompt caching and cache-aware routing (send a conversation's turns to the replica holding its KV cache) cut TTFT and cost substantially.

Challenges: summaries lose detail and can drift; regenerate them from source occasionally. Summarization is extra LLM spend, so trigger it on thresholds rather than every turn.

3) How do we admit traffic to a scarce GPU fleet fairly?

GPU capacity can't scale up in seconds the way stateless web servers can; new nodes take minutes to provision and load weights. A viral moment or an outage in one region can push demand far above capacity.

Bad Solution
Unbounded queue plus autoscaling

Approach: queue every request and let the autoscaler add GPUs.

Challenges: queues grow faster than capacity arrives; everyone's TTFT climbs to tens of seconds, clients time out and retry, adding more load. Heavy users dominate.

Good Solution
Per-user token rate limits and fast rejection

Approach: token-bucket limits per user and plan at the gateway (on estimated input + max output tokens); return 429 with Retry-After when exceeded; cap queue wait time.

Challenges: protects against individuals but not against aggregate overload; doesn't distinguish paying from free traffic when the whole fleet is saturated.

Great Solution
Capacity-aware admission control with priorities and graceful degradation

Approach: the gateway tracks real-time capacity signals from each pool (queue depth, KV-cache utilization, observed TTFT). Requests carry a priority class (paid interactive, free interactive, background). When utilization crosses thresholds: shed background work first, then route free-tier traffic to a smaller model or show a "high demand" notice, while paid traffic keeps its SLO. Token quotas reserve estimated tokens on admission and reconcile on completion. Routing is load- and cache-aware rather than round-robin, and autoscaling keys on queue depth and KV utilization with warm spare capacity, since cold starts are slow.

Challenges: priority policies are product decisions; communicate degradation clearly in the UI. Smaller-model fallbacks need their own eval coverage.

4) How do we keep conversation history fast at this scale?

Writes are ~2 per message (user + assistant) at tens of thousands per second; reads happen on every turn (load context) and when opening the app (list conversations).

  • Partition messages by conversationId with seq as the sort key; a conversation is small and hot only while active, so partitions stay balanced.
  • Cache the active conversation's recent turns and summary in Redis for the duration of the session; the Chat Service reads the cache first.
  • Assign seq in the Chat Service with a conditional write (only if seq doesn't exist) to prevent two devices from interleaving turns.
  • Archive old conversations to cheaper storage; search over history is a separate index built asynchronously.

5) How do we handle safety without adding latency?

  • Input moderation runs in parallel with history loading and prompt assembly; if it flags, cancel the model call before tokens stream.
  • Output moderation runs on sentence- or paragraph-sized chunks as they stream; a violation stops generation and replaces the message with a notice (status = blocked).
  • Abuse signals (rate of flagged inputs, automation patterns) feed per-account limits.

What is Expected at Each Level?

Mid-level

A clear working design: SSE streaming, a conversation store with a sensible key, a gateway or service that calls the model. With prompting, discusses context trimming and basic per-user rate limits.

Senior

Drives two or three deep dives without prompting. Explains why generation must be decoupled from the connection, proposes summary + window + prefix caching with reasons, and quantifies GPU needs to motivate admission control.

Staff+

Frames the system around GPU economics: capacity-aware admission with priority classes, cache-aware routing, multi-region capacity and failover, model version rollouts with eval gates, and the product trade-offs of degradation.

Question Breakdown · Hard

Design Claude Code (an AI Coding Harness)

An agentic coding tool that runs in the developer's terminal or IDE, reads and edits the local repository, runs commands, and asks before doing anything risky. Representative of "design Claude Code / Codex CLI / Gemini CLI" and the broader "design an agent harness" prompt.

Understanding the Problem

A developer opens a terminal in their repository and types "the date parser test is flaky, find out why and fix it." The tool explores the code, reads the test, runs it a few times, edits two files, re-runs the tests, and reports back, streaming every step so the developer can interrupt or redirect it. The model does the thinking; everything around the model is the harness: the loop that calls the model, the tools it can use, the context it sees, the rules about what it may do, and the extension points teams use to customize it.

The interesting part of this problem is that the hard engineering is not scale in the usual sense. The harness runs on one laptop for one user. The hard parts are: giving a model good-enough context about a huge codebase through a finite window, letting it run real shell commands on a machine that holds the user's SSH keys and cloud credentials, keeping long sessions affordable, and making edits that never silently corrupt code.

How this differs from the cloud coding agent

The AI Coding Agent breakdown is "issue in, pull request out" in a cloud sandbox. Clarify early which one the interviewer wants. The differences drive the whole design:

Functional Requirements

  1. Developers should be able to give a natural-language task in an interactive terminal session, watch the agent's text, tool calls and diffs stream live, and interrupt or steer at any time.
  2. The agent should be able to explore the codebase, edit files, and run commands (build, tests, git, package managers) on the developer's machine.
  3. Developers and organizations should control what the agent may do without asking: per-tool rules, permission modes, and managed policy.
  4. Sessions should persist: resume a past conversation, and rewind file changes the agent made.
  5. Teams should be able to extend it: project instructions, custom commands, deterministic hooks, external tools over MCP, skills and specialized subagents.
  6. The same engine should run headless (a CLI flag or an SDK) for CI and scripted automation.

Below the line: training the model, running the inference fleet (see Inference Batching), cloud sandboxes (see AI Coding Agent), keystroke-level autocomplete (see Copilot-style Autocomplete), billing.

Non-Functional Requirements

  1. Responsiveness: the UI reacts to keystrokes and Esc within ~100 ms; the first streamed token of a turn arrives in ~1–2 s; local tools such as search and read return in tens of milliseconds.
  2. Safety: nothing destructive or outward-facing happens without consent or an explicit rule; a hijacked agent's blast radius is bounded by OS enforcement, not by the model behaving well.
  3. Local-first privacy: code leaves the machine only as context sent to the model API (optionally through the customer's own cloud provider); no repository index is uploaded.
  4. Works on huge repos: millions of lines, no pre-built index required, startup in about a second.
  5. Affordable long sessions: 50–200 model calls per session must not cost dollars per step; target a prompt-cache hit rate above 90% of input tokens.
  6. Reliability: a crash, network drop or Ctrl-C never leaves a half-written file; sessions are resumable; transient API errors are retried with backoff.
  7. Cross-platform: macOS, Linux and Windows, many shells and terminals.

The Set Up

Core Entities

  • Session: id, working directory, model, permission mode, token and cost counters.
  • Message: user text, assistant text, tool_use and tool_result blocks; the ordered list of messages is the agent's state.
  • Tool: name, description, JSON schema, read-only or mutating, concurrency-safe or not.
  • ToolCall: tool, arguments, permission decision, result (possibly truncated), duration.
  • PermissionRule: allow, ask or deny, a tool pattern such as Bash(npm run test:*) or Read(./.env), and the scope it came from (managed, command line, local, project, user).
  • Hook: lifecycle event, matcher, command to run, timeout.
  • Subagent: name, description, system prompt, allowed tools, model.
  • Skill: folder with a SKILL.md (name, description, instructions) plus optional scripts and reference files.
  • MCP server: transport (stdio or HTTP), command or URL, credentials, the tools and resources it exposes.
  • Checkpoint: snapshot of files before an edit, tied to a message, so code and conversation can be rewound together.

Interface

The "API" here is two surfaces: the CLI the developer uses, and the model API the harness calls. Claude Code's public CLI looks like this:

claude                                   # interactive session in the current repo
claude "fix the flaky date parser test"  # start with a first prompt
claude --continue | --resume <session>   # reload a past transcript
claude -p "summarize this diff" --output-format stream-json --verbose  # headless, scriptable
/compact  /rewind  /permissions  /agents  /mcp                         # in-session slash commands

Underneath, every step of the agent is one streaming call to a tool-use API:

POST /v1/messages   stream: true
{ system:   [ ...harness prompt..., cache_control ],      // stable, cached
  tools:    [ Read, Edit, Write, Glob, Grep, Bash, ... ],  // stable, cached
  messages: [ user, assistant(tool_use), user(tool_result), ... ] }
→ SSE: text deltas, tool_use input deltas,
       stop_reason: "tool_use" | "end_turn",
       usage: { input_tokens, cache_read_input_tokens, cache_creation_input_tokens, output_tokens }

Edit { file_path, old_string, new_string, replace_all? }
  // in this design: fails if the file wasn't read this session, changed since it was read,
  // or old_string is not unique

Back-of-envelope: tokens and cost per session

Assume one session of 40 model calls. The stable prefix (system prompt, tool definitions, memory) is ~20K tokens; the conversation grows to ~100K, so the average call carries ~60K input tokens and writes ~300 output tokens. Prices are Sonnet 5.5 list prices: $2 per million input and $10 per million output tokens, with cache writes at 1.25× and cache reads at 0.05× of input (Claude pricing; check current numbers before quoting).

input processed  = 40 calls × 60K           = 2.4M tokens
output           = 40 × 300                 = 12K tokens  → $0.12

no caching:      2.4M × $2/M                = $4.80  (+ $0.12) ≈ $4.90 / session
with caching:    new tokens written ≈ 100K × $2.50/M  = $0.25
                 reads ≈ 2.3M × $0.10/M               = $0.23
                 total (+ output)                     ≈ $0.60 / session
cache hit rate   ≈ 2.3M / 2.4M                         ≈ 96%

fleet: 1M developers × 3 sessions/day × 2.4M = 7.2T input tokens/day
       uncached share ~4% → ~0.3T tokens/day of real prefill (~3.5M tokens/s)
       output: 1M × 3 × 12K = 36B tokens/day (~420K tokens/s)

Two conclusions shape the design. First, agent loops are input-heavy: each step re-sends the whole conversation, so prompt caching cuts session cost roughly 8× and the harness must be built to keep the cache warm. Second, anything that rewrites early context (editing old messages, reordering tools, a timestamp in the system prompt) silently multiplies cost. See Caching for LLMs and Inference & Serving for the provider-side mechanics.

High-Level Design

1) Interactive tasks: the agent loop

The core is deliberately simple: one loop, one message list. Anthropic describes the loop behind Claude Code and its Agent SDK as gather context → take action → verify work → repeat (Building agents with the Claude Agent SDK). One reasonable implementation:

  1. The user submits a prompt; it is appended to the message list.
  2. The context manager builds the request (system prompt, tools, memory, messages) and checks the token count; if it is near the limit, it compacts first.
  3. The loop streams the model response, rendering text deltas immediately and buffering tool_use blocks.
  4. If the response ends with end_turn, the turn is over and control returns to the user.
  5. Otherwise, each tool call goes through the permission pipeline and runs. Read-only, concurrency-safe calls (several greps or reads) can run in parallel; mutating calls run one at a time in order.
  6. Results, truncated to a budget, are appended as tool_result blocks, and the loop goes back to step 2.

Why a single-threaded master loop rather than a graph of agents? Debuggability and predictability: the transcript is a complete, linear record of what happened, every decision is visible to the user, and there is exactly one place where budgets, interrupts and permissions are enforced. Parallelism is added in controlled places (parallel read-only tools, subagents) instead of everywhere.

Interrupts and steering. Esc aborts the HTTP stream and sends SIGINT/SIGTERM to any running child process, then appends a marker ("the user interrupted") so the model knows its last action may be incomplete. A message typed while the agent is working is queued and injected at the next step boundary, never mid-tool, so tool_use/tool_result pairs stay well-formed.

2) Exploring, editing and running

The model can only act through tools, so tool design is product design. Anthropic's guidance: a small set of clearly distinct tools, outputs that are token-efficient (truncation, pagination, sensible defaults), and error messages that tell the model how to recover (Writing effective tools for agents). A typical set:

ReadRead a file or a line rangeLine numbers in output so edits can be precise; large files paginated; images and PDFs supported

What the model sees on every call is assembled by the context manager. The order matters as much as the content, because the provider caches by exact prefix:

Memory files. Claude Code loads CLAUDE.md files at launch from the directory hierarchy above the working directory (plus a user-level file and organization-managed policy), and loads CLAUDE.md files in subdirectories on demand when the agent reads files there (Claude Code memory docs). Codex CLI does the same with AGENTS.md. These files are the team's curated map: build and test commands, conventions, "never touch the generated folder." They are paid for on every call, so they should be short.

3) Controlling what the agent may do

Every tool call passes through a permission engine before it runs. Claude Code checks each call in a fixed order: PreToolUse hooks, deny rules, ask rules, the permission mode, allow rules, and finally a prompt (the canUseTool callback in the Agent SDK) for anything still undecided (Agent SDK permissions):

  • Rules are patterns per tool: allow Bash(npm run test:*), ask for Bash(git push:*), deny Read(./.env). Deny always wins.
  • Scopes layer, highest precedence first: organization-managed settings (which nothing can override), command-line arguments, personal local project overrides, shared project settings checked into the repo, then user settings. Rule lists merge across scopes, so a deny from any scope still wins.
  • Modes set the default for everything the rules don't cover: ask for anything that changes state; auto-accept file edits; plan mode (read-only research and a proposed plan, no edits); a classifier-reviewed auto mode; and a bypass mode meant only for throwaway containers.
  • Hooks are the deterministic escape hatch: a PreToolUse hook can block a call (exit code 2, with stderr fed back to the model) regardless of mode (hooks reference).

Rules alone are not a security boundary, which is the subject of deep dive 2.

4) Sessions, resume and rewind

Each session is an append-only transcript on local disk (Claude Code keeps them per project under ~/.claude/projects). Append-only matters twice: a crash loses at most the in-flight step, and resume is just "reload the messages and continue," which also keeps the prompt-cache prefix identical. Before an edit the harness snapshots the affected file into a checkpoint tied to the user prompt that started the turn; /rewind restores code, conversation, or both to that point.

Checkpoints only track files the agent edited through its file tools. A Bash command that deletes other files, runs a migration or pushes to a remote is outside them. Say this in the interview: git (and the permission system) is the real safety net for shell side effects, and the harness should encourage committing before risky steps.

5) Extensibility and 6) headless mode

Extension points (hooks, MCP, skills, subagents, slash commands, plugins) plug into the same loop and are covered in deep dive 5. Headless mode is the same engine without the TUI: claude -p reads a prompt, runs the loop, and emits text or a JSON event stream; the Agent SDK exposes the loop as a library. Because nobody is there to answer a permission prompt, everything the run may do must be declared up front (deep dive 6). Putting it together:

Everything except the model API runs on the developer's machine. That is the defining property: the harness has the user's full local power, and the design's job is to channel that power safely.

Potential Deep Dives

1) How does the agent find the right code in a huge repo?

Bad Solution
Put the repository (or as much as fits) in the prompt

Challenges: real repos are millions of tokens; even a 1M-token window would cost dollars per step and bury the relevant lines. Model accuracy degrades as context fills with irrelevant text ("context rot," Anthropic).

Good Solution
Embedding index of code chunks, retrieved per task

Approach: chunk by function or class, embed, store in a local or hosted vector index, retrieve the top-k chunks for each query.

Challenges: indexing a monorepo takes minutes and must be kept fresh as the agent itself edits files; uploading embeddings or code to a service conflicts with local-first privacy; semantic similarity misses exact identifiers, call sites and config keys; retrieved chunks lack the surrounding context an engineer would read.

Great Solution
Agentic search: fast tools, a curated map, and subagents

Approach: give the model the same tools an engineer uses (glob, ripgrep, read with line ranges, git log/blame through Bash) and let it search iteratively: grep for the error string, read the test, follow the import. The CLAUDE.md file acts as a hand-written map of the repo. For broad questions ("how does auth work across these services?") the agent spawns a subagent that explores in its own context and returns a 1–2K-token summary, so the main context stays clean. Anthropic recommends starting with agentic search and adding semantic search only if you need faster results, because it is more accurate, easier to maintain and more transparent (Agent SDK post). A semantic or LSP-backed tool can still be added over MCP.

Challenges: more model calls per task (mitigated by prompt caching and cheap, fast tools), and quality depends heavily on tool output design: a grep that returns 5,000 lines is worse than none.

2) How do we let it run shell commands safely on a developer's laptop?

The threat model has two parts: the model making a mistake (rm -rf in the wrong directory, force-pushing), and prompt injection, where text in a README, issue, dependency or web page instructs the agent to exfiltrate ~/.ssh or .env. Simon Willison's "lethal trifecta" frames it: private data + untrusted content + a way to communicate externally. A coding agent has all three by default, so the design must cut at least one leg.

Bad Solution
Ask for approval on every command, or approve everything

Challenges: constant prompts train users to click yes; Anthropic's telemetry showed users approved roughly 93% of permission prompts, and attention drops as approvals pile up (Anthropic, How we contain Claude). Approving everything removes the only check.

Good Solution
Allow/deny rules, permission modes and plan mode

Approach: safe, frequent commands (tests, linters, read-only git) are allow-listed; pushes and deploys always ask; secrets files are denied; plan mode lets the agent research without changing anything.

Challenges: rules match strings, but shells are programmable. npm test runs whatever package.json says, a build script can curl anywhere, and a prefix rule like git:* also allows options that execute commands. Rules reduce mistakes; they don't contain an adversary.

Great Solution
OS-level sandbox for filesystem and network, with prompts only at the boundary

Approach: run Bash and every child process inside an OS sandbox: Seatbelt on macOS, bubblewrap on Linux and WSL2 (Claude Code sandboxing docs). Writes are allowed only inside the project directory and a temp directory; sensitive paths can be blocked for reads; network traffic goes through a proxy outside the sandbox that only allows approved domains (package registries, the git host). Inside the boundary, commands run without prompts; anything that needs to cross it asks. Anthropic reports that sandboxing cut permission prompts by 84% in internal use (Anthropic, sandboxing post) and open-sourced the runtime. OpenAI's Codex CLI takes the same approach with Seatbelt on macOS and bubblewrap on Linux and WSL2 (Codex docs). Both legs matter: without network isolation a compromised agent can exfiltrate keys; without filesystem isolation it can modify shell config or other system files to get network access later.

Layer the rest on top: enterprise-managed deny rules users can't override; hooks for org policy (block edits to .github/workflows, scan commands for secrets); the model API key and other credentials never placed in context; and, for fewer interruptions outside the sandbox, a separate classifier model that reviews each proposed action before it runs, as Claude Code's auto mode does (Simon Willison's write-up).

Challenges: platform gaps (WSL1 and some container setups lack the needed kernel features, so the harness must detect that and fall back to stricter prompting); allowlisted domains can still be abused (a package registry is a place to upload data), so keep the list tight; tools that legitimately need broad access (Docker, cloud CLIs) need explicit, visible exceptions.

3) How do we manage the context window over a two-hour session?

Bad Solution
Drop the oldest messages when the window fills

Challenges: the oldest messages contain the task itself and the key decisions; dropping them can orphan tool_use/tool_result pairs (an API error), and every drop changes the prefix, so the cache misses on every subsequent call.

Good Solution
Summarize the history near the limit and cap tool outputs

Approach: when usage crosses a threshold, ask the model to summarize the conversation, replace the history with the summary, and continue. Truncate long tool outputs to a fixed budget.

Challenges: naive summaries lose file paths, exact error messages and the user's constraints; the agent then repeats work or violates an instruction it no longer sees.

Great Solution
Prevent, offload, externalize, then compact with structure, all cache-aware

Approach:

  • Prevent bloat: tools return compact output by default (paths before contents, head and tail of logs, pagination), so a test run costs 2K tokens, not 40K.
  • Offload: subagents explore in their own context window and return short findings; the parent never sees the 30 files they read.
  • Externalize state: a todo list, notes files and CLAUDE.md hold plans and decisions outside the window, and are re-read after compaction.
  • Compact with a schema: the summary keeps the user's goal and constraints, decisions made, files modified, open tasks and the last errors verbatim; recently read files are re-attached. Users can trigger it manually (/compact with instructions) at a natural breakpoint.
  • Stay cache-friendly: the history is append-only; the system prompt and tool list are byte-stable (no timestamps or random ordering at the top); cache breakpoints sit at the end of the stable prefix and at the latest turn. Compaction is one deliberate cache break, not a stream of small ones.

Challenges: the default 5-minute cache lifetime means a developer who reads a diff for ten minutes pays a cache write on the next step (a 1-hour cache tier exists at a higher write price); compaction quality needs its own evals.

Session (40 calls, avg 60K context)Input costRelative

4) How do we make edits reliable?

Bad Solution
The model rewrites the whole file

Challenges: an 800-line file is ~10K output tokens: at ~60 tokens/s that is close to three minutes and ~$0.15 per edit, versus a few seconds for a 20-line change. Models also "helpfully" elide unchanged code (// ... rest unchanged) and silently drop functions.

Good Solution
Diffs or patches

Approach: the model emits a unified diff or a patch format with context anchors (Codex CLI uses an apply_patch tool with its own format). Output is small and multi-hunk changes are one call.

Challenges: models miscount line numbers and context lines; patches fail to apply after the file drifts, and fuzzy application can apply a hunk in the wrong place.

Great Solution
Exact-string replace with guardrails, feedback and checkpoints

Approach: Edit(old_string, new_string) must match exactly once, so ambiguity becomes an error the model can fix by including more surrounding lines. The harness enforces read-before-edit (the model must have seen the current content) and staleness detection (if the file's hash or mtime changed since the last read, because the user or a formatter touched it, the edit fails with "re-read the file"). Writes are atomic (temp file + rename) so a crash never leaves half a file. After each edit, a PostToolUse hook or language server can run the formatter, linter or type checker and return diagnostics, so the model fixes its own errors in the next step. Every edit is checkpointed for /rewind. Whole-file Write remains for new files.

Challenges: many small edits mean more round trips; a common alternative is a "fast apply" step where the large model sketches the change and a small, fast model merges it into the file.

5) How do teams extend it without bloating every prompt?

The key question for every extension point is who decides when it runs, and when its text enters the context.

MechanismWho triggers itContext costUse for

Slash commandsThe userOnly when invokedReusable prompts: /review, /release-notes

Bad Solution
Put every instruction and tool into the system prompt

Challenges: context cost on every call, conflicting instructions, and "should" rules the model may ignore when the rule must hold every time.

Good Solution
Expose everything as MCP tools

Challenges: a few servers can add tens of thousands of tokens of tool definitions to every call, and tool choice degrades as the list grows. MCP servers are also third-party code with access to your context (supply-chain risk, Guardrails & Security).

Great Solution
Match the mechanism to the guarantee, and load lazily

Approach: anything that must happen goes in a hook (code, not a prompt). Always-relevant facts go in a short memory file. Procedures go in skills with progressive disclosure: only metadata sits in context until the task matches, then the body loads, then referenced files or scripts as needed (Anthropic, Agent Skills). Large tool catalogs are deferred behind a tool-search step so definitions load on demand. Isolated or parallel work goes to subagents with restricted tool lists. Organizations allowlist MCP servers and plugins through managed settings and pin versions.

Challenges: skill and subagent descriptions are the routing signal, so vague descriptions mean they never trigger; extension behavior needs the same evals as the core prompt.

6) How does it run in CI and in parallel?

Bad Solution
Run several agents in the same checkout, or the interactive tool in CI with permissions bypassed

Challenges: agents overwrite each other's files and fight over build outputs and ports; a bypassed agent in CI with repository secrets in the environment is a prompt-injection target with real credentials.

Good Solution
Headless mode with pre-declared permissions and separate clones

Approach: claude -p with an explicit allowed-tools list, a max-turns budget and JSON output, run per job; parallel work in separate clones.

Challenges: full clones are slow and disk-hungry for large repos.

Great Solution
One engine, three front ends, isolated workspaces

Approach: the loop is a library (Claude's Agent SDK), and the TUI, IDE extension and CLI -p are thin clients over its event stream. In CI it runs with least privilege: read-only token by default, scoped write token only for posting a comment or pushing a branch, network allowlist, turn and cost caps. Parallel sessions each get a git worktree (a separate working directory sharing one object store), their own ports and env, and background tasks for long-running dev servers whose output the agent polls. Work that should outlive the laptop is handed to a cloud runner (the cloud coding agent design).

Challenges: merging the results of parallel agents is still a human review problem; cost multiplies with parallelism.

7) How do we know a harness change made it better?

Bad Solution
Try a few prompts by hand

Challenges: agent runs are long and stochastic; a change to one tool description can help one task family and hurt another.

Good Solution
Public benchmarks

Approach: SWE-bench Verified (500 human-validated GitHub issues scored by hidden tests, OpenAI) and Terminal-Bench (tbench.ai) for terminal tasks.

Challenges: they measure model + harness on someone else's tasks, are at risk of contamination, and don't measure interactive qualities like asking good questions or respecting permissions.

Great Solution
A harness eval suite, A/B gates and privacy-respecting telemetry

Approach: build an internal suite of hundreds of tasks with verifiable outcomes (tests pass, the right file changed, no forbidden command ran), each in a container snapshot. Run every harness change (system prompt, tool descriptions, compaction prompt, defaults) and every new model across it several times and track pass rate, cost and tokens per solved task, turns, wall-clock, and permission prompts per task. Anthropic reports that refining tool descriptions measurably improved SWE-bench results, which is why tools get the same rigor as prompts (Writing effective tools). Online, track opt-in signals: interrupts, rewinds, "that's wrong" follow-ups, accepted versus reverted edits, session abandonment. See Evaluation.

Challenges: environment setup dominates the cost of the suite; flaky tasks must be quarantined or they drown real signal.

What is Expected at Each Level?

Mid-level

A clear agent loop with read, search, edit and shell tools; streaming output; a permission prompt before running commands; session transcripts. Mentions the context limit and truncating tool output when asked.

Senior

Distinguishes local harness from cloud agent; agentic search over embeddings with reasons; permission rules and modes plus an OS-level sandbox with network control; structured compaction and cache-friendly context ordering with cost math; reliable edit semantics with read-before-edit and checkpoints.

Staff+

Treats the harness as a platform: one engine behind TUI, IDE, CI and SDK; an extension model chosen by guarantee and context cost; enterprise policy and supply-chain controls for MCP and plugins; threat model built on the lethal trifecta; a harness eval suite and release gates for every prompt, tool and model change.

Caching for LLMs

Where to cache in an LLM system, how provider prompt caching and engine prefix caching actually work, when semantic caching is safe, and how to estimate the savings in an interview.

In classic system design, caching protects a database from read load and shaves milliseconds. In LLM systems the stakes are much higher. A single uncached model call can cost cents and take seconds; with a cached prefix, those input tokens cost a tenth as much or less and the call starts streaming sooner. For a product serving a million requests a day, caching decisions routinely move the bill by tens of thousands of dollars per day and move time to first token (TTFT) by hundreds of milliseconds.

There are also more kinds of cache. Some store final answers (like a classic response cache), some store intermediate computation (the model's attention state for a prompt prefix), and some store expensive side products (embeddings, retrieval results, tool outputs). Each has a different key, hit rate, failure mode and privacy risk. This page walks through them in the same order you'd discuss them in an interview: where to cache, how each layer works, eviction, common problems, and how to bring it up.

The two layers that matter most in nearly every design are the ones that cache computation, not answers: provider prompt caching and engine prefix caching. They're safe (the model still generates a fresh answer), they apply to every request with a shared prefix, and they're invisible to the user. Answer caches are the riskier, more situational layer.

Provider prompt caching

How it works

When a model processes a prompt, prefill computes keys and values for every token at every layer: the KV cache (see Inference & Serving). Prompt caching keeps that state after the request finishes. If a later request begins with the exact same tokens, the provider loads the stored state instead of recomputing it, then only prefills the new suffix. You pay a reduced rate for the cached tokens, and TTFT drops because less prefill work is done.

  • Exact prefix match. Matching is on tokens from the very start of the prompt. A single different token early on means everything after it is a miss.
  • Minimum size. Providers only cache prefixes above a minimum length (roughly 512 to 4,096 tokens, varying by model and provider).
  • Lifetime. Cached prefixes expire after minutes of inactivity unless refreshed by use; some providers offer longer, paid retention.
  • Scope. Caches are scoped to your organization (or tighter), so one customer can't hit another's cache. This matters for privacy; see common problems below.
  • Explicit vs automatic. Some APIs cache automatically; others let you mark cache breakpoints in the request so you control what's stored, and Anthropic and OpenAI (on newer models) offer both.

Break-even math

If a cache write costs w× base input and a read costs r×, caching a prefix that's reused k times is cheaper than not caching when:

w + k·r  <  1 + k      →      k  >  (w − 1) / (1 − r)

5-minute cache  (w = 1.25, r = 0.05–0.1):  k > 0.26–0.28  → pays off after 1 reuse
1-hour cache    (w = 2.0,  r = 0.05–0.1):  k > 1.05–1.11  → pays off after 2 reuses

So the question is never "should we cache?" but "what's stable enough to reuse within the lifetime?" For a chat product, the system prompt and tools are reused by every request. For an agent, the entire growing trajectory is reused by the next step a few seconds later, which is why agents see the largest savings (the Context Engineering page works through an 89% saving on a 40-step run).

Designing prompts for cache hits

  • Order content from most to least stable: tools → system prompt → examples → per-session context → history → new input.
  • Keep timestamps, request IDs and per-user data out of the prefix.
  • Place breakpoints (where explicit) after each stable block, and one at the end of the conversation so the next turn reuses this turn.
  • Route a user or conversation consistently (e.g. OpenAI's prompt_cache_key) so requests land where their cache lives.
  • Monitor cache-read tokens ÷ input tokens per route. Providers return cached-token counts in the usage object; a sudden drop means someone broke the prefix.

Engine prefix caching (self-hosted)

When you run your own models, the serving engine does the same thing inside your GPUs, and you control the policy.

vLLM: hashed blocks

vLLM stores the KV cache in fixed-size blocks (PagedAttention). With automatic prefix caching, each full block is identified by a hash of its own tokens plus the hash of everything before it, and a global table maps hashes to physical blocks. A new request walks its prompt block by block; every block whose hash is already in the table is reused. Blocks no longer referenced by any running request become evictable, and the least recently used is evicted first, ending blocks of long prefixes before shared early ones (vLLM prefix caching design). For multi-tenant deployments, use a cryptographic hash (SHA-256, the default in recent vLLM versions) to make collisions impractical, and a per-request cache_salt so tenants never share cached blocks.

SGLang: a radix tree

SGLang's RadixAttention keeps cached prefixes in a radix tree keyed by token sequences, so shared prefixes are stored once and branches diverge where prompts differ. Eviction removes least-recently-used leaves first, so the widely shared root (system prompt, tools) is the last to go (SGLang paper). vLLM's block policy behaves similarly for standard attention models.

Cache-aware routing

A prefix cache only helps if the request reaches the replica that holds the prefix. With 50 replicas and round-robin load balancing, a multi-turn conversation lands on a cold replica most of the time. Options:

  • Session affinity: hash the conversation ID to a replica. Simple; uneven when some sessions are much heavier.
  • Prefix-aware routing: hash the first few blocks of the prompt (e.g. system prompt + tenant documents) so requests sharing a long prefix go together.
  • KV-aware scoring: the router tracks which replicas hold which prefix blocks and scores each replica by expected cache hit minus current load. Projects such as llm-d, NVIDIA Dynamo and the SGLang router implement variants of this.
  • Bounded load: any affinity scheme needs a cap so a viral prefix doesn't melt one replica. Consistent hashing with bounded loads (spill to the next replica once one exceeds, say, 1.25× average load) is the classic fix.

KV offload tiers: GPU → CPU → SSD

GPU memory (HBM) is the smallest and most expensive tier, and it's also where running sequences need space, so cached prefixes get evicted quickly under load. Offloading evicted KV blocks to CPU DRAM and then local SSD or a shared store keeps them reusable. LMCache is a widely used layer for this with vLLM; its authors report multi-fold TTFT reductions on multi-round chat and document-analysis workloads (LMCache paper, vendor-run benchmarks). Whether loading beats recomputing is simple arithmetic:

Llama-3-70B-class model, FP16 KV ≈ 320 KB per token. A 32K-token shared prefix:
  KV size      = 32,000 × 320 KB          ≈ 10.5 GB

Recompute (prefill) ≈ 2 × params × tokens  = 2 × 70e9 × 32e3 ≈ 4.5e15 FLOPs
  8 × H100 at ~40% of ~990 dense BF16 TFLOPS ≈ 3.2e15 FLOP/s  → ~1.4 s (more with attention)

Load from CPU DRAM over PCIe Gen5 (~50 GB/s usable per GPU, 8 GPUs in parallel,
  each loading its 1/8 tensor-parallel shard)  ≈ 1.3 GB per GPU ÷ 50 GB/s → ~0.03 s

Even with generous overheads, reloading a long prefix from host memory is an order of magnitude faster than recomputing it. SSD and network tiers are slower but still competitive for long prefixes. The cost is engineering complexity and host memory.

Response caches

Exact response cache

Hash the full request (model, version, sampling parameters, normalized messages, tool definitions, tenant) and store the output. It's a plain key-value cache (Redis, the gateway's built-in cache) with a TTL.

  • Good fit: deterministic tasks at temperature 0 (classification, extraction, moderation), batch pipelines that re-run over the same data, eval suites, popular pre-computable prompts ("summarize this public page").
  • Poor fit: open-ended chat, where almost no two requests are identical, and any request where the user expects a fresh sample ("regenerate" must bypass the cache).
  • Normalization (trim whitespace, lowercase where safe, canonical JSON) raises hit rate. Be conservative: normalizing away meaning produces wrong hits.

Semantic cache

A semantic cache embeds the incoming query, searches past queries in the same scope, and returns the stored answer if the nearest neighbor's similarity exceeds a threshold τ. It turns "How do I reset my password?" and "password reset steps?" into one model call. Open-source options include GPTCache, Redis vector search and gateway plugins (Kong, Portkey and others offer one).

The danger is false hits: embeddings place "How do I reset my password?" and "How do I reset my 2FA device?" close together, but the answers differ. Treat the threshold as a precision/recall trade-off you measure, not a constant you guess:

  1. Collect a few thousand real query pairs with labels "same answer is correct" or not.
  2. Sweep τ and plot hit rate against false-hit rate.
  3. Pick the τ where false hits are below what the product tolerates (often well under 1% for support content), and accept the lower hit rate that implies.

Ways to make semantic caching safer:

  • Scope tightly: per tenant always; per user if answers include anything personal; per locale and model version.
  • Restrict to cacheable intents: a classifier allows only FAQ-type, non-personal questions into the cache. Never cache answers that depend on account state, the current time, or tool calls with side effects.
  • Verify hits: add an entity/keyword overlap check or a cheap model that confirms "does this cached answer answer this question?" A small-model check is still far cheaper than a frontier-model answer.
  • Cache earlier in the pipeline: caching the retrieval results for similar queries, then still generating the answer, captures much of the latency win with far less correctness risk.
  • Invalidate on content change: tag each cached answer with the document IDs it was grounded on and purge by tag when those documents change.

Embedding, retrieval and tool caches

  • Embedding cache: key on hash(embedding_model_version, text). Identical text with an identical model always yields the same vector, so this cache never goes stale; it's what makes re-ingesting a mostly unchanged corpus cheap. Changing the embedding model invalidates it by construction.
  • Retrieval cache: key on the normalized query, filters (tenant, ACL groups) and the index version. Bumping the index version on each re-index invalidates stale results without explicit purges.
  • Tool-result cache: cache only read-only tools, with a TTL that matches data volatility (a stock price: seconds; a documentation page: hours). Never cache tools with side effects; use idempotency keys for those instead (see Agents, Tools & MCP).
  • Edge-cached AI content: if output doesn't depend on the user (a generated product description, a page summary), generate it offline in a batch job (batch APIs are commonly 50% cheaper) and serve it from a CDN. The model is then out of the request path entirely.

A useful trick for the provider cache: if a prefix is reused every 6–10 minutes (just over the 5-minute lifetime), either switch to 1-hour retention or send a tiny keep-warm request before expiry. Compare the costs: a keep-warm read of a 20K-token prefix every 4.5 minutes costs 20K × the read rate (0.05–0.1×) per ping, about 13 pings per hour, versus one 2× write per hour plus normal reads. Do the multiplication for your prices; for long prefixes and steady traffic either option beats repeated cold writes.

Hit-rate math: a worked example

A support assistant handles 1M requests per day. Each sends 10K input tokens, of which 6K are a stable prefix (system prompt, tools, policies), and returns 300 output tokens. Prices (Sonnet 5.5): $2/M input, $10/M output, cache write 1.25×, read 0.05×.

Before caching
  input  10,000 × $2/M   = $0.0200
  output    300 × $10/M  = $0.0030
  per request            = $0.0230   × 1M/day = $23,000/day

After caching
  exact cache hits:        5% of requests
  semantic cache hits:    15% of the remaining 95%  = 14.25%
  served from response caches: 19.25%   → 807,500 requests still reach the model

  prefix (6K): 90% read at 0.05×, 10% written at 1.25×
     0.9 × 6,000 × $0.10/M + 0.1 × 6,000 × $2.50/M = $0.00054 + $0.0015 = $0.0020
  rest of input (4K) × $2/M                                              = $0.0080
  output                                                                 = $0.0030
  per model request                                                      = $0.0130
  × 807,500                                                              = $10,530/day (−54%)

Notice where the savings come from: about two-thirds (~$8.0K/day) from prompt caching (risk-free) and one-third (~$4.4K/day) from response caches (which carry the false-hit risk). In an interview, say both numbers and that you'd ship prompt caching first. Also note that the remaining cost is dominated by the uncached 4K tokens and output; the next lever is trimming retrieval and history (see Context Engineering) or routing easy requests to a cheaper model (see Gateways, Routing & Reliability).

Common caching problems

Cold-cache stampedes

You deploy a new system prompt. Every in-flight conversation now misses, and thousands of requests in the same second each write the new prefix (paying the write premium) and, on self-hosted fleets, each run full prefill, spiking TTFT across the fleet. Handle it: pre-warm caches with one request per region or replica before shifting traffic, roll prompt changes gradually (canary 1% → 10% → 100%), and use request coalescing (single-flight) for response caches so concurrent identical misses compute once.

Staleness

A policy document changes and the semantic cache keeps serving the old refund window. Handle it: tag cached answers with source document IDs and purge on change events; include index or prompt version in keys; set TTLs by intent; never cache answers to time-sensitive questions.

Privacy and cross-tenant leakage

A response cache keyed without the tenant ID serves one customer's answer to another. More subtly, shared prompt caches leak information through timing: a cache hit has measurably lower TTFT, so an attacker who shares a cache can test whether someone else recently sent a given prefix. An audit of 17 API providers in 2024 detected cache sharing across organizations at 7 of them; several changed their behavior after disclosure (Gu et al., ICML 2025). Handle it: tenant (and user, where personal) in every cache key and partition; per-organization scoping for any shared KV cache you operate; never cache prompts containing secrets.

Cache poisoning

A bad answer, or one shaped by a prompt injection, gets written to a semantic cache and is then served to everyone who asks something similar. Handle it: only write answers that passed output guardrails, consider writing only after positive feedback or for vetted intents, keep a fast purge path, and log which cache entry served each response so you can find affected users.

Hot prefixes and uneven load

Affinity routing sends all requests for a popular tenant's 100K-token knowledge base to one replica, which saturates while others idle. Handle it: bounded-load consistent hashing, replicating hot prefixes to several replicas, and autoscaling decisions based on per-replica queue depth rather than fleet averages.

Measuring the wrong thing

A semantic cache reports a 30% hit rate, but user satisfaction drops. Handle it: measure false-hit rate by sampling hits for LLM-judge or human review, and A/B test the cache like any other model change.

Caching in System Design Interviews

When to bring it up

  • Any design with a long, shared system prompt or documents. "Our 8K-token system prompt and tools are identical across requests, so prompt caching makes them 90–95% cheaper and cuts TTFT."
  • Agents. "Each step re-sends the trajectory, so I'll put cache breakpoints at the end of each turn; most input becomes cache reads."
  • Self-hosted inference. "Prefix caching only helps if requests land on the replica with the cache, so the router does prefix-aware routing with bounded load."
  • Cost reduction questions. "Here's the stack of caches I'd add, in order of risk."
  • High-volume repetitive queries. "FAQ-style questions are a good semantic cache candidate, scoped per tenant, with a threshold we tune on labeled pairs."

How to introduce it

  1. Find the reuse. What's identical across requests (prefix), across steps (trajectory), or across users (answers)?
  2. Start with computation caches. Prompt or prefix caching first: no correctness risk.
  3. Add answer caches only where safe. Exact caching for deterministic tasks; semantic caching for scoped, non-personal intents with a measured threshold.
  4. Define keys, scope and invalidation. Tenant in every key; versions in keys; purge on content change.
  5. Quantify. Estimate hit rates and show the cost and latency math; name the metric you'd monitor (cache-read share, false-hit rate).

Common deep-dive questions

"Your LLM bill is too high. Cut it by half."

Bad Solution
Add a semantic cache in front of everything

Challenges: chat traffic rarely repeats exactly; an aggressive threshold creates wrong answers; personal and stateful requests can't be cached; you've added risk for an uncertain saving.

Good Solution
Prompt caching plus a model router

Approach: reorder prompts so the system prompt, tools and documents form a stable prefix; enable provider caching; route simple requests to a cheaper model.

Challenges: needs measurement to prove quality holds on the cheaper model; cache hit rate depends on traffic patterns.

Great Solution
Measure, then stack levers by risk

Approach: break the bill down by route into prefix input, variable input and output tokens. Apply prompt caching and cache-friendly ordering (often 20–40% alone for long prompts); trim history and retrieval; route easy traffic to small models behind an eval gate; move offline work to batch APIs; add exact caching for deterministic pipelines and a narrowly scoped semantic cache for FAQ intents with a measured false-hit rate. Show the per-request math and track cost per successful task, not just cost per call.

Challenges: each lever needs its own monitoring; savings interact (caching reduces the benefit of trimming), so re-measure after each step.

"Would you add a semantic cache to this support bot?"

Strong answer: "Only for a subset. I'd classify intents and cache only non-personal FAQ answers, scoped per tenant and locale, with a threshold tuned on labeled query pairs to keep false hits under, say, 0.5%. Each entry is tagged with the articles it cites and purged when they change. I'd A/B it and watch resolution rate and thumbs-down, and I'd also consider caching retrieval results instead, which captures much of the latency win with less risk."

"How do you maximize prefix cache hits across a fleet of 100 GPU replicas?"

Strong answer: cache-aware routing (hash on conversation or on the leading prefix blocks), bounded load to avoid hotspots, KV offload to CPU memory so evicted prefixes are cheap to restore, a shared system prompt kept identical across products where possible, and metrics per replica: prefix hit rate, KV memory utilization and TTFT. At larger scale, a KV-aware router that knows which replica holds which blocks (llm-d, Dynamo) and disaggregated prefill so prefill replicas specialize (see Inference & Serving and Inference Batching).

Summary

  • Cache computation before answers. Prompt and prefix caching are safe, broad and usually the biggest win.
  • Prefix caches need exact token prefixes: order prompts from stable to volatile and keep volatile values out of the front.
  • Break-even is one reuse for a 1.25× write and a 0.05–0.1× read; agents benefit most because each step reuses the last.
  • Self-hosted: prefix caching plus cache-aware routing with bounded load, plus CPU/SSD offload for long prefixes.
  • Answer caches (exact, semantic) need tight scoping, measured thresholds, tag-based invalidation and poisoning defenses.
  • Always put tenant (and user, where personal) in the key, and remember that shared caches can leak through timing.

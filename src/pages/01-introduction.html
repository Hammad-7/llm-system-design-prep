LLM System Design · Fast Track

Introduction

Learn to design LLM-powered applications for interviews, fast. The essentials of retrieval, agents, inference, evaluation and safety, organized the way interviewers actually grade.

A few years ago the canonical system design prompt was "Design YouTube." Today a growing share of loops open with "Design ChatGPT," "Design a support bot over our knowledge base," or "Design an inference batching service." Prep companies now report that LLM infrastructure prompts have spread beyond ML roles into general software engineering loops (Aced (formerly Exponent), 2026), and practitioner guides describe "design an LLM-based system for X" as the most common ML system design question of 2026 (techinterview.org).

This guide works backwards from those interviews. It keeps the bones of a classic system design interview (requirements, APIs, data, scale) and adds the parts that are new when one of your components is a probabilistic, expensive, GPU-bound text generator. It's useful for two reasons:

  1. If your interview is soon, you get the highest-leverage material first: a delivery framework, the concepts that come up every time, and twelve fully worked examples.
  2. If you build LLM features at work, everything here maps to real production decisions. Nothing is interview theater.
Not the right spot?
  • Need classic distributed-systems fundamentals first (sharding, caching, queues)? Start with Hello Interview's System Design in a Hurry, then come back.
  • Interviewing for model training, ranking or recommendation roles? Classic ML system design still applies; this guide focuses on applications built on top of LLMs and on the infrastructure that serves them.

What are LLM system design interviews?

An LLM system design interview asks you to design a production system where a large language model does part of the work. Like any design round it's open-ended: you get a vague prompt and are expected to drive toward a working architecture in about 45 minutes while explaining your trade-offs.

What changes is the shape of the hard problems. Your new component is non-deterministic (the same input can produce different outputs), slow and expensive per call (seconds and anywhere from fractions of a cent to several cents, metered in tokens), bounded by a context window, wrong in fluent ways (hallucination), and steerable by its inputs, including attacker-controlled inputs. Most of the interview is about building deterministic scaffolding around that component so the overall system is fast, affordable, measurable and safe.

Types of LLM system design interviews

Prompts cluster into six families. Knowing which one you're in tells you where the deep dives will go.

  1. LLM product design. "Design ChatGPT," "Design the Claude chat service," "Design the OpenAI Playground." Conversation state, streaming, model selection, storage, rate limits and safety at consumer scale.
  2. Retrieval & knowledge systems. "Design a RAG system for a customer-support chatbot," "Design LLM-powered enterprise search." Ingestion, chunking, hybrid retrieval, reranking, permissions, citations, freshness, evaluation. This is the single most common family.
  3. Agentic systems. "Design an AI coding agent," "Design an agent that takes actions across tools." The agent loop, tool contracts, sandboxes, budgets, durable execution and human-in-the-loop.
  4. Inference & platform infrastructure. "Design an inference batching system," "Design a high-concurrency inference API," "Design GPU scheduling." Queues, batching, KV cache, routing, autoscaling, failover. Common at frontier labs, where interviewers want you to strip away the AI vocabulary and solve the infrastructure problem underneath (Exponent's Anthropic guide).
  5. Evaluation, safety & governance platforms. "Design an LLM evaluation pipeline," "Design content-policy detection," "Design guardrails for an enterprise assistant."
  6. AI-flavored classic design. A classic prompt with an LLM somewhere in the path: a distributed search system with LLM inference in the query path, a token-based rate limiter, a prompt-management platform, a model-artifact distribution system.

Many AI companies, frontier labs included, still ask plenty of classic prompts (webhooks, payments, CI/CD, chat, rate limiters) for general software roles. Treat this guide as an add-on to classic preparation, not a replacement.

Assessment

Rubrics vary by company, but they converge on four areas. Under each, here's what changes when the system contains an LLM.

Problem Navigation

Can you turn a vague prompt into measurable goals, and focus on what matters? For LLM systems this starts with questions most candidates skip: does this even need an LLM, or just a part of it? What does "good answer" mean and how will we measure it? Which mistakes are reversible (a bad summary) and which are not (a refund, a deleted file, a leaked document)? Clarifying requirements before drawing boxes is the most commonly reported gap in these rounds (KDnuggets field guide).

Solution Design

Can you produce a working architecture with sensible components? Strong candidates put the model where judgment is needed and deterministic code everywhere else. They keep control flow in an orchestrator rather than in a prompt, validate every tool call in application code, and know when retrieval beats fine-tuning.

Technical Excellence

Do you know the mechanics that drive cost, latency and quality? Expect probes on tokens and context windows, KV cache and batching, embeddings and vector indexes, hybrid retrieval and reranking, caching layers, evaluation methods and prompt injection. You don't need to derive attention math, but you should be able to estimate how many concurrent conversations a GPU can hold, or why a reranker helps.

Communication and Collaboration

Can you explain trade-offs clearly and adapt when the interviewer pushes? LLM rounds reward stating assumptions out loud ("I'll assume a hosted frontier model behind an API, and revisit self-hosting if cost becomes the constraint") and naming what you'd measure to decide.

How expectations change by level

Mid-level

A clean, working end-to-end design. Correct use of retrieval, streaming and a basic eval story. Reasonable answers when probed, even if the interviewer leads the deep dives.

Senior

Drives the design and picks the deep dives. Quantifies latency and cost, explains retrieval quality trade-offs, designs evaluation and guardrails, anticipates failure modes (provider outage, injection, bad retrieval).

Staff+

Sets scope in a near-silent interview. Reasons about the platform (shared gateway, eval flywheel, multi-tenant isolation), build-vs-buy for models, migration between model versions, and how the system degrades safely.
Red flags interviewers report
  • Treating the LLM as a source of truth instead of grounding it in data you control.
  • No evaluation plan, or "we'll look at outputs."
  • Reaching for fine-tuning before trying prompting and retrieval.
  • Ignoring prompt injection, data leakage between tenants, and abuse.
  • Ignoring cost and latency until the interviewer asks.
  • Putting business logic and permissions in the prompt instead of in code.

These recur across interviewer write-ups such as IGotAnOffer's GenAI guide and the AI Engineering Field Guide.

Conclusion

LLM system design is classic system design with a new, strange component in the middle. If you can reason about tokens the way you reason about bytes, treat quality as something you measure, and treat every model input as untrusted, you'll stand out. Mark this page as read and move on to preparation.

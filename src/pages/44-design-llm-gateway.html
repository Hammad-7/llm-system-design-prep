Question Breakdown · Medium

Design an LLM Gateway

An internal platform that every team's LLM traffic flows through: one API across providers, per-team keys and budgets, routing and failover, and a complete record of who spent what. Representative of "design an AI gateway", "design a multi-provider LLM proxy" and "how would you control LLM spend across a company" prompts.

Understanding the Problem

A company has dozens of teams shipping LLM features. Each one signed up for providers separately, provider API keys live in a dozen repos, nobody knows which team caused last month's bill, one team's batch job hit the shared rate limit and took down another team's chat feature, and when a provider had an outage every feature broke at once. The platform team is asked to build a gateway: a service in the path of every model call that standardizes access, enforces limits, survives provider failures and attributes cost.

This prompt is popular for founding-engineer and platform roles because it mixes classic distributed-systems problems (rate limiting, high availability, config distribution, event pipelines) with LLM-specific ones: limits measured in tokens rather than requests, responses that stream for a minute, output length you don't know in advance, and provider features such as prompt caching that a careless proxy silently breaks.

Open-source and commercial gateways exist (LiteLLM, Portkey, Envoy AI Gateway, Kong AI Gateway, Cloudflare AI Gateway, and the cloud providers' own). Say so, and say what would make you build rather than buy: scale, latency overhead, data-residency rules, or deep integration with internal identity and billing. Then design it, because that's the interview.

Functional Requirements

  1. Teams should be able to call any approved model (hosted providers and self-hosted) through one API using a gateway-issued virtual key.
  2. The platform should enforce per-team token rate limits and spend budgets, and route requests with automatic failover across deployments and providers.
  3. Every request should be attributed (team, app, model, tokens, cost) and auditable, and admins should be able to change keys, routes and policies without a deploy.

Below the line: a prompt registry, an evaluation platform, fine-tuning, and running the model servers themselves (see Inference Batching Service).

Non-Functional Requirements

  1. Low overhead: p99 added latency under ~10–20 ms excluding the provider; streaming is never buffered, so time to first token is unchanged.
  2. Availability: 99.99%, higher than any single provider. The gateway must not become the single point of failure for every AI feature in the company.
  3. Scale: 5K requests/s at peak; at ~10 s average duration, Little's law gives 5,000 × 10 s = 50K concurrent connections.
  4. Accurate accounting: budgets enforced within a small overrun; usage records complete and deduplicated.
  5. Security and compliance: provider credentials never leave the gateway; PII handling, logging and data residency set by policy per team.

The Set Up

Core Entities

  • Team / App: owner, cost center, default policies.
  • VirtualKey: hashed secret, team, allowed model aliases, limits, expiry, tags.
  • ModelAlias: a stable name such as chat-default that maps to an ordered, weighted list of deployments.
  • Deployment: provider, region, concrete model ID, credential reference, provider limits, data-retention terms.
  • Limit / Budget: scope (key, app, team), metric (input tokens, output tokens, dollars, concurrency), window.
  • UsageRecord: request ID, key, alias, deployment, input / cached / output tokens, cost, latency, status.
  • Policy: redaction mode, prompt logging level, allowed regions, response caching rules.

API

// Data plane: provider-compatible endpoints, so existing SDKs work by changing base URL and key
POST /v1/chat/completions      // OpenAI-compatible; model = alias or concrete model
POST /v1/messages              // Anthropic-native passthrough (keeps cache_control, thinking, etc.)
POST /v1/embeddings
  Authorization: Bearer vk_live_...
  X-Request-Id: 7f3c...        // idempotency and tracing
  X-Gateway-Tags: app=search,env=prod
  → response headers: x-gateway-deployment, x-ratelimit-remaining-tokens, retry-after

// Control plane
POST /admin/keys               { team, aliases[], limits }
PUT  /admin/aliases/{name}     { deployments: [{ id, weight, priority }] }
PUT  /admin/budgets/{scope}    { metric, limit, window }
GET  /usage?team=&from=&to=&groupBy=model

A key design decision hides in the first two lines: unified schema or native passthrough? A single OpenAI-style schema makes switching providers easy but forces a lowest common denominator: provider-specific features (Anthropic's cache_control breakpoints, extended thinking, citations; provider-specific structured output options) get lost in translation. The practical answer is both: native passthrough endpoints per provider for teams that need those features, plus a unified endpoint for portable workloads, with translation only where semantics truly match.

High-Level Design

1) One API across providers with virtual keys

The data plane is a fleet of stateless gateway pods behind a regional load balancer. On each request a pod hashes the virtual key and looks it up in an in-memory snapshot of configuration (keys, aliases, deployments, policies), so authentication costs microseconds, not a database round trip. Provider credentials come from a secrets manager into pod memory; teams only ever hold virtual keys, which can be rotated, scoped to specific aliases and revoked instantly. The pod resolves the alias to a deployment, translates if needed, and forwards the request over a pooled, warm HTTP/2 connection to the provider.

2) Budgets, rate limits and routing

Every request passes through the same pipeline inside the pod:

  • Reserve, then reconcile. Output length is unknown up front, so the pod reserves input_tokens + max_tokens against the key's token limits atomically in Redis before forwarding, and refunds the unused part when the response ends. The algorithms (token buckets, sliding windows, reservation) are covered in Gateways, Routing & Reliability.
  • Routing: pick a deployment for the alias by priority and weight among healthy deployments, steering away from ones near their provider rate limit or with rising latency.
  • Fallback: on a retryable error before any bytes have reached the client, try the next deployment in the alias (deep dive 3).

3) Attribution, audit and hot-reloaded config

  • When a response finishes, the pod emits a usage event (request ID, key, team, alias, deployment, input, cache-write, cache-read and output tokens, latency, status) to Kafka asynchronously. A stream processor prices it with a versioned price table and loads it into the warehouse for dashboards, chargeback and anomaly alerts. Prompt and response bodies, when a policy allows logging them, go to encrypted object storage with retention rules, referenced by request ID.
  • Admins change configuration through a control plane (admin UI and API backed by a database). It publishes versioned config snapshots that pods pull or receive by watch and swap in atomically, without restarts.

Potential Deep Dives

1) How do we enforce token budgets across hundreds of pods?

Bad Solution
Count requests per pod in local memory

Challenges: requests are the wrong unit (one request can be 100× another in tokens), and each pod sees only its share of traffic, so the effective limit scales with the number of pods and changes every time the fleet autoscales.

Good Solution
A central Redis counter, incremented after each response

Approach: after the response completes, add actual tokens to a per-key counter in Redis; reject new requests when the window's total exceeds the limit.

Challenges: admission is based on the past. A burst of 200 concurrent long requests all pass the check before any of them finishes, then overshoot the budget together.

Great Solution
Atomic reservation, reconciliation and local leases for hot keys

Approach: a Redis Lua script atomically checks and reserves input + max_tokens per limit in one round trip; the pod reconciles with actual usage on completion and refunds the difference. Reservations carry a TTL so a crashed pod's holds expire. Encourage realistic max_tokens values, since over-reserving throttles a team early. For very hot keys, a pod leases a block of tokens (say 50K) from Redis and spends it locally, returning the remainder, which cuts Redis round trips at the cost of slight imprecision. Dollar budgets (daily, monthly) are enforced separately from per-minute limits, from the priced usage stream, with alerts at 50/80/100%.

Mirror provider semantics where they matter: Anthropic, for example, doesn't count cache-read input tokens toward its input-tokens-per-minute limit (Claude rate limits), so a gateway that counts them would throttle well-cached workloads for no reason.

Challenges: Redis is now on the hot path; decide per limit what happens if it's unavailable (deep dive 6).

2) How do we proxy streams without adding latency?

Bad Solution
Buffer the full response, then count, scan and return it

Challenges: destroys streaming: the user waits for the whole generation (often 5–30 s) instead of ~1 s to first token. Also holds every response in memory.

Good Solution
Pass chunks through as they arrive

Approach: an async proxy reads each SSE chunk from the provider and writes it to the client immediately; token counts come from the provider's final usage event.

Challenges: intermediate proxies and load balancers often buffer by default; broken streams never deliver the final usage event; client disconnects keep paying for tokens nobody reads.

Great Solution
A purpose-built streaming data plane

Approach:

  • An event-loop runtime (Go, Rust, or Envoy with filters) handles 50K mostly idle concurrent streams per region with modest memory; disable response buffering at every hop and flush per chunk.
  • Read usage from the provider's final usage event; if the stream breaks, estimate with the model's tokenizer and mark the record estimated.
  • Propagate client disconnects as upstream cancellation.
  • Keep warm connection pools to each provider so TLS handshakes aren't on the critical path.
  • For deploys, drain pods gracefully: stop accepting new requests, let in-flight streams finish (with a cap of a few minutes).
  • Any output guardrail scans in sliding windows of the stream rather than blocking on the full response (see Guardrails & Security).

Challenges: long-lived connections make load balancing uneven; use least-connections balancing and cap streams per pod.

3) How do retries and fallbacks work?

Bad Solution
Retry every failure three times

Challenges: during a provider incident, retries triple the load on a struggling backend and on your own rate limits (a retry storm), and retrying after tokens have streamed sends the client duplicated, contradictory text.

Good Solution
Retry 429 and 5xx with backoff, then a secondary deployment

Approach: exponential backoff with jitter, honoring Retry-After, then fall back to the next deployment in the alias.

Challenges: no global cap on retries; no memory of which deployments are unhealthy, so every request rediscovers the outage.

Great Solution
Retry budgets, circuit breakers and eval-gated fallback chains

Approach:

  • Retry only before the first byte reaches the client; after that, end the stream with an error event and let the application offer "regenerate".
  • Cap retries with a retry budget (for example, retries may add at most 10% to traffic).
  • Track error rates and latency per deployment with circuit breakers shared across pods, so traffic shifts away from an unhealthy region within seconds and probes test recovery.
  • Prefer the same model in another region or account first (same behavior, same prompt format), then a different provider.
  • Allow cross-provider fallback only for aliases whose prompts have been evaluated on both models, because a prompt tuned for one model can degrade quietly on another.

Challenges: cross-provider fallback changes cost, behavior and data-processing terms; make it an explicit, per-alias opt-in that the owning team signs off.

4) How do we avoid breaking prompt caching, and when do we cache responses?

Provider prompt caching is often the largest cost lever a team has, and a gateway can silently destroy it:

  • Don't mutate the prefix. Injecting a timestamp or request ID into the system prompt, reordering tool definitions, or applying non-deterministic redaction changes the bytes and turns every request into a cache miss.
  • Preserve provider controls. Anthropic caching is opt-in through cache_control (a top-level field or per-block breakpoints), which a unified schema must carry through; OpenAI caches automatically for prompts of 1,024 tokens or more and offers a prompt_cache_key to improve hit rates (OpenAI prompt caching).
  • Route with affinity. Caches are scoped to an account or organization and often to a region, so spreading one app's traffic across many accounts for rate-limit headroom lowers hit rates. Route by a hash of the stable prefix or a session key so related requests land on the same account and region.
  • Record cache tokens separately (cache writes, cache reads, uncached input) in usage events; otherwise cost attribution is wrong by up to an order of magnitude for heavily cached apps.

Response caching at the gateway (returning a stored completion) is a different thing and should be opt-in per alias: exact-match on a hash of tenant plus the full request, only for deterministic workloads such as classification, extraction and embeddings. Semantic caching is riskier and belongs in the application, which knows when two questions really mean the same thing.

5) How do we handle PII, logging and data residency?

Bad Solution
Log every prompt and response in plain text for debugging

Challenges: the gateway becomes the company's largest store of customer PII and secrets, outside any team's data controls.

Good Solution
Redact all traffic inline before it reaches providers

Approach: regex and NER detectors (for example Microsoft Presidio) replace emails, phone numbers and IDs before forwarding.

Challenges: adds latency to every call, breaks prompt caching when redaction varies, and degrades quality for tasks that legitimately need the data (a support bot needs the order number).

Great Solution
Policy tiers per team and route

Approach: each key or app gets a policy: metadata only (default: log usage, not content), redacted logging (content logged after redaction, asynchronously, off the hot path), or redact before provider (for regulated data, using consistent placeholders like <EMAIL_1> that are restored in the output so the prompt stays deterministic). Deployments carry data-processing attributes (region, zero-data-retention agreement), and policies restrict which deployments a request may use, so EU-only data is never routed to a US region, even during fallback.

Challenges: detectors miss things; treat redaction as risk reduction, and combine it with retention limits and access controls on stored logs.

6) How do we keep the gateway from becoming a single point of failure?

Once every AI feature depends on it, the gateway's availability caps the company's. Design each dependency to degrade rather than fail:

Component downBehavior
A gateway pod or AZStateless pods across ≥3 AZs per region; the LB health-checks and drains. Clients retry idempotently with the same X-Request-Id.
A whole regionClients use regional endpoints with DNS or anycast failover; each region has its own pods, Redis and Kafka.
Control plane / config DBPods keep serving from the last-known-good snapshot cached in memory and on local disk. Config changes pause; traffic doesn't.
Redis (limits)Per-limit choice: rate limits fail open to conservative per-pod local limits (degraded accuracy beats an outage); hard dollar caps for risky keys fail closed.
Kafka (usage)Pods buffer usage events to local disk and replay later; consumers dedupe by request ID so replays don't double-count.
A providerCircuit breakers and fallback chains (deep dive 3).

Config hot reload deserves its own care because a bad config push is the most likely way to take everything down at once. Validate configs against a schema and dry-run route resolution before publishing; publish immutable, versioned snapshots; roll out to canary pods first and watch error rates; swap atomically in each pod; roll back by pointing at the previous version. A bad push then breaks a canary, not the company.

7) How do we make cost attribution trustworthy?

  • Usage events are the source of truth. Request-time cost estimates drive budgets; the authoritative cost is computed in the pipeline with a price table that has effective dates, so a price change mid-month is applied correctly and history can be recomputed.
  • Exactly-once in effect: at-least-once delivery from pods plus deduplication by request ID in the warehouse load.
  • Tags for chargeback: team, app, environment and feature tags on keys and headers let finance allocate spend, and let teams see cost per feature, per user or per successful task.
  • Reconcile against invoices monthly; drift reveals missing records or pricing bugs.
  • Anomaly alerts: spend 3× baseline, sudden drop in cache-hit rate, a key used from a new network. Leaked virtual keys are a real risk; short expiries and per-key limits contain the damage. More in Observability & LLMOps.

What is Expected at Each Level?

Mid-level

A stateless proxy with virtual keys, provider credentials held centrally, token-based rate limits in Redis, simple retries and fallback, streaming passthrough, and usage logging for cost reports.

Senior

Reserve-then-reconcile limits, retries only before first byte with circuit breakers, no-buffering streaming, prompt-cache-safe proxying, a Kafka-to-warehouse usage pipeline with dedupe, policy-driven PII handling, and explicit degradation when Redis, config or Kafka fail.

Staff+

Treats the gateway as company infrastructure: build-vs-buy reasoning, availability higher than any provider, safe config rollout, eval-gated cross-provider fallback, data-residency guarantees through failover, and chargeback that drives teams toward cheaper designs.

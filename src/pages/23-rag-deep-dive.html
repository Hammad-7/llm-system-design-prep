RAG in Depth

The full retrieval-augmented generation stack: how documents get in, how queries get answered, where RAG systems fail, and how to evaluate and budget them.

Retrieval-augmented generation is the most common shape behind LLM interview prompts: support assistants, enterprise search, legal and medical Q&A, "chat with your docs," answer engines. The basic idea fits on a napkin (retrieve relevant passages, put them in the prompt, ask the model to answer from them), and that's exactly why interviewers dig. A napkin RAG demo works on ten PDFs; a production RAG system has to parse messy documents, respect permissions, stay fresh as content changes, find the right passage among millions, and prove that its answers are grounded.

Think of RAG as two pipelines that share an index: an offline ingestion pipeline that turns source content into searchable chunks, and an online query pipeline that turns a question into a cited answer. Most quality problems trace back to ingestion; most latency problems live in the query path. The vector index itself is covered in Embeddings & Vector Search; this page covers everything around it.

The ingestion pipeline

Connectors and change detection

Content lives in Google Drive, SharePoint, Confluence, Notion, Zendesk, Salesforce, Slack, Git repos, S3 buckets and databases. Each connector handles auth (usually OAuth on behalf of the customer's admin), pagination, rate limits and the source's permission model. How you learn about changes decides freshness:

  • Webhooks / event subscriptions (Drive change notifications, Zendesk webhooks, Slack Events): seconds of latency, but they can be dropped, so pair them with a periodic reconciliation crawl.
  • Change data capture (CDC) from your own databases (Debezium on the Postgres WAL, DynamoDB Streams): reliable, ordered, low latency.
  • Polling with cursors ("modified since T"): simplest, minutes of latency, and the only option for some sources.

Put all change events on a durable queue (Kafka, SQS) keyed by document id, so a burst (a customer connecting 2 million files) is absorbed and processed at a controlled rate, and updates to the same document are processed in order.

Parsing

Parsing is where most RAG quality is silently lost. A PDF is a set of positioned glyphs, not a document with paragraphs, so naive text extraction interleaves columns, splits tables into nonsense and drops figures.

  • Layout-aware parsing recovers reading order, headings, lists and tables. Options include open-source libraries (Docling, Unstructured, PyMuPDF-based tooling) and cloud services (AWS Textract, Azure Document Intelligence, Google Document AI). Vision-language models are now also used to transcribe complex pages directly into Markdown.
  • OCR for scanned documents and images; record OCR confidence so you can flag low-quality sources.
  • Tables: convert to Markdown or HTML tables and keep a table as one chunk with its caption and header row; a row without its header is meaningless.
  • Images and charts: generate a text description with a vision model so the content is searchable, or embed page images directly (see multimodal RAG below).
  • HTML and wikis: strip navigation, footers and boilerplate; keep heading hierarchy.

Cleaning and deduplication

Enterprise corpora are full of near-duplicates: the same policy in five versions, email threads quoting each other, templated pages. Duplicates waste index space and, worse, fill the top-k with copies of one passage. Use exact hashing for identical chunks and MinHash/SimHash or embedding similarity for near-duplicates; keep the newest or most authoritative copy and record the others as aliases. Also strip personal data you shouldn't index, and tag content with its source authority (official policy page vs a Slack message) for ranking later.

There's no universally best chunk size. Smaller chunks retrieve more precisely but carry less context; larger chunks dilute the embedding. Pick a size from your content type, then tune it against a retrieval eval set rather than by intuition.

Enrichment and metadata

Store with every chunk: document id and version, source system, URL, title and section path ("Billing > Refunds > EU"), timestamps, language, content type, authority tier, tenant id and the ACL (users and groups allowed to read it). Then enrich:

  • Contextual chunk headers. Prepend the document title and section path to the chunk text before embedding, so a chunk that says "The limit is 30 days" is embedded as "Refund policy > EU customers: The limit is 30 days."
  • Contextual retrieval. Anthropic's version uses an LLM to write a short situating context (usually 50–100 tokens) per chunk; combined with BM25 and reranking it cut top-20 retrieval failures by 67% in their tests (Contextual Retrieval). Prompt caching of the full document keeps the ingestion cost manageable.
  • Generated questions or summaries per chunk, indexed alongside the text, help when users phrase questions very differently from the source.

Then embed (dense, and sparse if you use a learned sparse model), and upsert into the vector and BM25 indexes. Keep the chunk text in a document store keyed by chunk id; the index holds vectors and filterable metadata, the store holds what you put in prompts and show as citations.

Permissions, updates and deletions

Three things break naive ingestion pipelines:

  • ACL sync. Permissions change more often than content (someone is removed from a group, a folder is un-shared). Sync permission changes as their own event type, and update chunk ACL metadata without re-embedding. Resolve group memberships at query time from an identity service, or denormalize them carefully with a short refresh interval.
  • Deletion propagation. A deleted or un-shared document must disappear from search quickly, and for privacy requests (GDPR erasure) provably. Deletions flow through the same queue as tombstones, remove chunks from every index and cache (including semantic caches and conversation memory that may quote them), and are verified by a reconciliation job.
  • Idempotent, versioned upserts. Key chunks by (doc_id, chunk_index) plus a content hash so re-processing the same version is a no-op, and replace all chunks of a document atomically when it changes (old chunk counts may differ from new ones).

The query pipeline

Understanding the query

  • Rewriting. Turn the conversational turn into a standalone search query using history: "what about for EU customers?" becomes "refund window for EU customers." A small, fast model does this in a couple of hundred milliseconds.
  • Decomposition. Split multi-part or comparative questions ("compare our 2024 and 2025 parental leave policies") into sub-queries, retrieve for each, then answer over the union.
  • HyDE. Hypothetical Document Embeddings: have the model draft a plausible answer and embed that instead of the question, since answers look more like documents than questions do. Useful for short or vague queries; adds an LLM call of latency.
  • Routing. Decide which sources and tools to hit: the policy index, the product catalog (structured, via SQL), the ticket history, or none at all (chit-chat, or questions the model can answer without retrieval). Routing can be rules, a classifier, or the LLM itself choosing tools.
  • Filters from the query. Extract structured constraints ("tickets from last week about Android") into metadata filters instead of hoping embeddings capture them.

Hybrid retrieval and fusion

Run dense ANN and BM25 (or learned sparse) in parallel, each with the caller's tenant and ACL filters applied inside the search, and fetch maybe 50–100 candidates each. Their scores are on incomparable scales, so fuse by rank. Reciprocal rank fusion (Cormack et al., SIGIR 2009) is the standard:

RRF(d) = Σ over retrievers r of  1 / (k + rank_r(d))      // k = 60 in the original paper

doc A: rank 1 in BM25, rank 9 in dense → 1/61 + 1/69 = 0.0309
doc B: rank 3 in BM25, rank 2 in dense → 1/63 + 1/62 = 0.0320   // consistent across both → wins
doc C: rank 1 in dense only            → 1/61          = 0.0164

RRF needs no score calibration and rewards documents that both retrievers like. Weighted score fusion (normalize scores, then weight) can do slightly better if you tune it, but is more fragile.

Reranking

First-stage retrievers compare a query vector with precomputed document vectors; they never see query and document together. A cross-encoder reranker reads the query and each candidate jointly and outputs a relevance score, which is far more accurate but costs a model forward pass per candidate. So rerank only the fused top 50–100 and keep the best 5–15 for the prompt. Options: hosted rerank APIs, open cross-encoder models on your own GPUs, or an LLM reranker (ask a model to score or order candidates), which is the most flexible (it can follow instructions like "prefer official policy pages") and the slowest and most expensive. Reranking typically costs 50–200 ms for 50–100 short candidates on a GPU-backed service.

Context assembly

  • Budget. Decide how many tokens retrieved content may use (say 4–8K of the prompt) and fill it by rerank score, not by a fixed k.
  • Expand. Swap small matched chunks for their parent section or neighbors (small-to-big) when they're too terse to answer from.
  • Order. Models use information at the start and end of long contexts better than the middle (Lost in the Middle). Put the strongest passages first (or first and last), and keep the count modest rather than stuffing 50 chunks.
  • Label and fence. Give each passage an id, title, source, date and authority, wrapped in clear delimiters, with an instruction that passages are reference material, not instructions.
  • Keep the prefix stable. System prompt and tool definitions first, retrieved content and the question last, so prompt caching hits.

Citations and verification

Ask the model to cite passage ids for each claim, then verify in code: every cited id must exist in the provided context (no invented citations), and the citation should link to the exact document version and section. For high-stakes domains, add a verification pass: a small model or NLI classifier checks that each sentence is entailed by its cited passage, and unsupported sentences are removed or the answer is regenerated. Some providers offer native citation features that return the exact cited spans of supplied documents, as character ranges, PDF pages or content blocks (for example Claude's citations API), which removes the parsing step. If retrieval scores are low or no passage supports an answer, abstain ("I couldn't find this in the knowledge base") and offer escalation; a confident wrong answer costs more trust than "I don't know."

Advanced patterns

Agentic RAG

Instead of one fixed retrieve-then-answer pass, give the model search tools and let it decide what to look up, read results, and search again. This handles questions where the first search reveals what to search next, and is how deep-research products and coding agents work (see Deep Research Agent and Agents, Tools & MCP). Costs: several model calls per question, latency from seconds to minutes, and less predictability. Cap steps and tokens, and use the fixed pipeline for the common simple questions, escalating to agentic retrieval only when needed.

Multi-hop questions

"Which of our customers in Germany are on the plan that lost SSO last quarter?" needs one fact to find the next. Options in increasing power: query decomposition up front, iterative retrieval (retrieve, extract the bridging entity, retrieve again), or an agent with search and SQL tools.

GraphRAG

Microsoft's GraphRAG uses an LLM to extract entities and relationships from the corpus into a knowledge graph, clusters it into communities, and pre-writes summaries per community. It shines on global questions about a whole corpus ("what are the main themes in these 5,000 customer interviews?"), where chunk retrieval finds fragments but no overview. The costs are a very expensive indexing pass (LLM calls over the whole corpus), painful incremental updates, and little gain for ordinary fact lookups. Bring it up when the prompt involves sensemaking over a corpus or relationship-heavy data; otherwise hybrid retrieval plus reranking is the better default.

Structured data and text-to-SQL

Questions like "how many refunds did we issue in March?" shouldn't be answered from text chunks at all. Route them to a tool that generates SQL (or calls an API) against the source of truth. Make it safe and accurate: a curated semantic layer of approved tables, columns and metric definitions in the prompt; read-only credentials scoped to the user's permissions; query validation (allowed tables, row limits, timeouts); and showing the generated query alongside the answer.

Multimodal RAG

Slides, scanned forms, diagrams and charts lose most of their meaning as extracted text. Two approaches: describe images and tables in text at ingestion (works with any text index), or embed page images directly with a vision retriever such as ColPali and pass the retrieved page images to a vision-capable LLM. The second preserves layout and charts at the cost of larger storage and more expensive prompts.

Long context vs RAG

Context windows of hundreds of thousands to a million tokens make "just put everything in the prompt" viable for small corpora. Compare:

FactorLong context (stuff it all in)RAG
Corpus sizeUp to a few hundred thousand tokensUnbounded
Cost per queryPays for the whole corpus every call (much less with prompt caching)Pays only for retrieved passages
LatencyLong prefill unless cachedRetrieval adds ~100–400 ms (more with query rewriting), prompts stay small
QualityGood at cross-document reasoning; can miss details in very long contextsLimited by retrieval recall
Permissions and freshnessHard: every user's visible set differs, cache invalidates on changeNatural: filter per query, update per chunk
CitationsPossible but coarserBuilt in

The practical answer is usually both: retrieval to select, larger and more numerous chunks than you'd have used two years ago, and long context for the cases that need whole documents (a contract review, a single long report).

Evaluating RAG

Evaluate retrieval and generation separately; otherwise you can't tell which half failed.

StageMetricQuestion it answers
RetrievalRecall@k, hit rate@kWhat fraction of the relevant chunks are in the top k? (Hit rate: is at least one?)
RetrievalMRR, nDCGAre relevant chunks near the top?
RetrievalContext precisionHow much of what we passed to the model was relevant?
GenerationFaithfulness / groundednessIs every claim supported by the provided context?
GenerationAnswer relevance, correctnessDoes it answer the question, and match the reference answer?
GenerationCitation accuracyDo cited passages actually support the sentences that cite them?
End to endAbstention rate, resolution rate, escalationsDoes it help users without bluffing?

Build a golden set of a few hundred real questions with the chunk ids that answer them (for retrieval metrics) and reference answers or rubrics (for generation), stratified by source, question type and difficulty, plus deliberately unanswerable questions to test abstention. LLM-judged versions of faithfulness and context metrics (as popularized by Ragas) make this scale. The method for building and trusting these evals is on the Evaluation page.

So retrieval adds roughly 250–700 ms before the first token. Ways to cut it: run rewrite and a first retrieval in parallel, skip rewriting when the query is self-contained, cache embeddings and retrieval results for popular queries, use a smaller reranker, and stream a "searching…" status so the wait is visible.

RAG in System Design Interviews

When to bring it up

  • The system must answer from private, large, changing or permissioned knowledge: "The model doesn't know our docs and they change daily, so we'll retrieve at query time rather than fine-tune."
  • Answers need citations or auditability: "Agents need to verify answers, so every claim links to its source passage."
  • The interviewer asks about hallucinations: grounding plus abstention is your first answer.

How to introduce it

  1. Sketch both pipelines in one breath: ingestion (connectors → parse → chunk → enrich → embed → index) and query (rewrite → hybrid search with ACL filters → rerank → assemble → answer with citations).
  2. Size it: documents × chunks per document × vector size; ingestion rate; query QPS.
  3. Name the hard parts for this prompt: permissions for enterprise search, freshness for news or support, tables for financial documents, multi-hop for research.
  4. Close with evaluation: retrieval and generation metrics, a golden set, regression gates.

Common deep-dive questions

"Users say the bot can't find answers that are definitely in the docs."

Bad Solution
Increase top-k and switch to a bigger LLM

Challenges: if the right chunk isn't retrieved, a bigger model can't use it; more chunks add noise, cost and latency.

Good Solution
Measure retrieval, then add hybrid search and reranking

Approach: build a labeled set from the failing questions, measure recall@k, add BM25 alongside dense retrieval with RRF, and rerank a larger candidate pool.

Challenges: doesn't fix chunks that were badly parsed or lack context.

Great Solution
Diagnose by stage, fix ingestion, then retrieval, then generation

Approach: classify failures: not indexed (connector or parsing gap), indexed but not retrieved (query rewrite, hybrid, contextual headers, chunking), retrieved but not ranked (reranker, candidate pool), ranked but not used (context ordering, prompt). Fix the dominant class, add the cases to the golden set, and gate future changes on recall@k and faithfulness.

Challenges: requires tracing every stage per query, which you should have anyway (see Observability).

"How do you keep answers fresh when documents change hourly?"

Webhooks or CDC into a keyed queue, per-document atomic chunk replacement, freshness SLOs measured as source-change-to-searchable lag, deletion tombstones that also purge caches, and recency boosts or version metadata so the newest policy wins conflicts.

"How do you handle permissions in enterprise search?"

Sync ACLs from each source as first-class events, store them on chunks, resolve the user's groups at query time, filter inside retrieval, scope caches by user or permission set, and run an automated test that queries as low-privilege users and asserts no restricted chunk appears.

"When would you not use RAG?"

When the knowledge fits in a cached prompt (small, stable corpus), when the problem is behavior or format rather than missing facts (fine-tune or prompt; see Fine-tuning), or when the answer comes from structured data (text-to-SQL or an API tool).

Summary

  • RAG is two pipelines sharing an index. Ingestion quality (parsing, chunking, enrichment, ACLs, deletions) sets the ceiling; the query path decides latency.
  • Hybrid retrieval with RRF, then cross-encoder reranking, then a small, well-ordered context is the strong default.
  • Permissions are filtered inside retrieval; deletions propagate to indexes and caches.
  • Verify citations in code and abstain when evidence is weak.
  • Agentic RAG, GraphRAG, text-to-SQL and multimodal retrieval are tools for specific question types, not defaults.
  • Evaluate retrieval and generation separately with a golden set, and gate every change on it (see Evaluation). The worked Support Assistant and Answer Engine breakdowns apply all of this.

Question Breakdown · Hard

Design an Inference Batching Service

Batch synchronous inference requests onto GPUs and route every result back to the right caller. Candidates report this as the most common Anthropic system design prompt, in several variants (Exponent, PracHub).

Understanding the Problem

We run a model on a fleet of GPUs. A GPU processes a batch of up to 100 inputs in one pass, and a pass takes roughly 100 ms regardless of how many inputs are in it. Callers hit a synchronous API: they send one input and wait for its output. Design the system that accepts requests, forms batches, runs them, and returns each result to the caller who's waiting for it.

Interviewers use AI vocabulary here, but they're testing classic infrastructure: queues, batching, request/response correlation, load balancing, failure handling and backpressure. Say so early: "The model is a black box that takes up to 100 inputs and 100 ms. This is a batching queue with a fan-in/fan-out correlation problem." That framing is the abstraction signal they look for.

Functional Requirements

  1. Clients should be able to submit a single input and synchronously receive its output.
  2. The system should group requests into batches of up to 100 and run them on available GPUs.
  3. Each output should be returned to exactly the caller that submitted the input.

Below the line: model loading and versioning, multi-model routing, streaming outputs (we'll revisit for LLMs at the end), billing.

Non-Functional Requirements

  1. Latency: p99 end-to-end under ~300 ms at normal load.
  2. Throughput / efficiency: keep GPUs busy; batch as full as latency allows.
  3. Scale: 10K requests/s peak.
  4. Fault tolerance: GPU, worker or server failures shouldn't lose requests silently; one bad input shouldn't fail 99 others.
  5. Graceful overload: above capacity, reject fast instead of letting latency explode.

Capacity estimation

One GPU at full batches: 100 inputs / 100 ms = 1,000 req/s
Peak 10K req/s → 10 GPUs at 100% utilization
Target ~60–70% utilization + N+2 for failures → ~16–18 GPUs
Latency floor: 100 ms compute + queue wait + network ≈ 120–200 ms

High-Level Design

1) Accept a request and hold the caller

Stateless API servers behind a load balancer accept the request, assign a requestId, and register a pending future in an in-memory map requestId → future. The HTTP handler awaits that future (with the request's deadline as a timeout). Thousands of waiting requests per server are cheap with async I/O.

2) Form batches and run them on GPUs

API servers push requests onto a request queue. Each GPU worker runs a small batcher loop: when its GPU is free, it pulls up to 100 requests from the queue, runs the batch, and emits results. Pull-based workers give us load balancing for free: a GPU only takes work when it has capacity, which answers the interviewer's favorite probe, "how do you find a GPU with spare capacity?"

3) Return each result to the right caller

Each request carries its originServer. The worker publishes results to that server's reply channel. The API server's listener looks up requestId in its map, completes the future, and the handler returns the response.

Potential Deep Dives

1) When should a batch be dispatched?

This is the core trade-off: bigger batches are more efficient, but waiting to fill them adds latency.

Bad Solution
Wait until 100 requests arrive

Challenges: at low traffic, a request can wait indefinitely. At 50 req/s a batch takes two seconds just to fill.

Good Solution
Size-or-timeout

Approach: dispatch when the batch hits 100 or the oldest request has waited, say, 20 ms. Worst-case added latency is bounded by the timeout.

Challenges: a fixed timeout is wrong at both extremes: at low load it adds pointless delay to an idle GPU; at high load batches fill instantly anyway.

Great Solution
Work-conserving, deadline-aware batching

Approach: since a pass costs ~100 ms regardless of size, an idle GPU should start immediately with whatever is queued (up to 100). While a GPU is busy, new arrivals accumulate on their own, so the 100 ms pass is the batching window. Under heavy load batches are naturally full; under light load nobody waits. Order the queue by deadline, drop requests whose deadline has already passed before spending GPU time on them, and only add a short wait when the queue is tiny and a partially full batch would waste a scarce GPU (rarely worth it when compute cost is flat).

Challenges: if pass time grows with batch size (as it does for many models), the optimal policy shifts toward bounded waits; measure the pass-time curve and tune.

2) How do results find their way back?

Bad Solution
Write results to a database and poll

Challenges: polling adds latency (half the poll interval on average) and a database write and read per inference for no durability benefit.

Good Solution
Per-server reply queues with correlation IDs

Approach: each API server subscribes to its own reply topic; workers publish {requestId, output} there; the server completes the matching future.

Challenges: one broker hop each way; if an API server dies, its pending callers' connections die with it and results go nowhere.

Great Solution
Direct streams, deadlines and idempotent retries

Approach: API servers hold long-lived bidirectional gRPC streams to the batch workers (or to a thin dispatcher in front of them). Requests flow down the stream; results come back on the same stream, so routing is implicit and there's no extra broker hop. Every request carries a deadline; servers time out futures and send a cancel so workers skip expired work. If an API server crashes, clients retry with the same Idempotency-Key; workers keep a short-lived result cache by key so a retry that arrives after the original finished is served without recomputing.

Challenges: stream management (reconnects, flow control) is more complex than a queue; keep a queue as the buffer for bursts if needed.

3) What happens when GPUs fail or a batch partially fails?

  • Worker crash mid-batch: workers take batches under a lease (visibility timeout). If the lease expires without results, the requests return to the queue, unless their deadlines have passed. Inference is a pure function of the input, so at-least-once execution is safe; results are de-duplicated by request ID.
  • Hung GPU: a per-batch watchdog (for example 3× the expected pass time) marks the worker unhealthy, re-queues its batch and drains it from rotation.
  • Poison input: one malformed or oversized input can crash the whole batch. Validate size and shape at the API server. If a batch still fails, split it in half and retry each half to isolate the bad request in log₂(100) ≈ 7 rounds; return an error to that caller only.
  • Zone failure: spread workers across zones; queue and API tier are multi-zone; capacity plan for N+2.

4) What happens above capacity?

Bad Solution
Let the queue grow

Challenges: latency grows without bound, callers time out, then retry, so the queue fills with requests nobody is waiting for. The GPUs spend their time on dead work.

Great Solution
Admission control and load shedding by deadline

Approach: estimate wait at admission (queue_depth ÷ fleet_throughput); if it exceeds the request's deadline, reject immediately with 429 and a Retry-After. Bound the queue. Use separate priority queues so interactive traffic preempts batch traffic. Drop expired requests at dequeue. Autoscale on queue depth and wait time, accepting that GPUs take minutes to add. Clients retry with jittered exponential backoff.

5) Follow-up: what changes for an autoregressive LLM?

Interviewers often end with "now make it an LLM." Three things change:

  1. Work is variable-length. One request generates 10 tokens, another 2,000. A fixed batch holds GPU slots until its longest member finishes, so you move to continuous batching: schedule per decode step, admit new sequences as others finish (see Core Concepts).
  2. Memory, not batch size, becomes the limit. Each active sequence holds its KV cache. Admission control now asks "is there KV memory for this prompt plus its max output?" and the scheduler may preempt and recompute or swap sequences under pressure.
  3. Latency splits into TTFT and per-token speed, and batch size trades one user's speed for aggregate throughput:
Bigger decode batches: more tokens per GPU, slower tokens per user

What is Expected at Each Level?

Mid-level

Queue + batcher with size-or-timeout, request IDs to route results back, horizontal scaling of API servers and GPU workers. Handles basic retries when prompted.

Senior

Abstracts the problem quickly, derives GPU count from the numbers, explains pull-based dispatch, leases and re-queueing, partial-failure isolation, and deadline-based admission control without being led.

Staff+

Drives a near-silent interview: work-conserving batching from first principles, end-to-end deadline propagation and cancellation, idempotent retries, overload economics, and a crisp answer to "now it's an LLM" covering continuous batching, KV memory admission and the throughput-latency curve.
